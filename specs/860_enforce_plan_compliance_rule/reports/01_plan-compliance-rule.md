- **Frontmatter**: 7 of 9 have a `---\npaths: ...\n---` YAML block as the very first thing in the file:
  - Bare string: `.claude/rules/plan-format-enforcement.md:2` (`paths: specs/**/plans/**`), `.claude/rules/project-overview-detection.md:2`, `.claude/rules/pr-prohibition.md:2` (`paths: "**/*"`), `.claude/rules/state-management.md:2`, `.claude/rules/workflows.md:2`, `.claude/rules/error-handling.md:2`.
  - JSON array (multiple globs): `.claude/rules/nix.md:2` (`paths: ["**/*.nix"]`), `.claude/rules/git-workflow.md:2` (`paths: ["specs/**/*", ".claude/**/*"]`).

- **Section ordering**: `# Title` → `## Path Pattern` (or equivalent scope statement) → topic-specific body sections → (optional) `## Enforcement` or `## Do Not` / `## Rationale` closing section → (optional) `## Related Context` pointing at deeper `.claude/context/` docs.
- **`## Enforcement` section**: explicit in `no-task-references-in-deliverables.md:48-55` (names the enforcing hook, `validate-no-task-references.sh`, and states it is advisory/non-blocking) and implicit in `pr-prohibition.md` via `## Required Behavior` / `## Rationale` (`pr-prohibition.md:33-45`). Domain rules like `neovim-lua.md` and `nix.md` instead use a terminal `## Do Not` bullet list (`neovim-lua.md:133-140`, `nix.md:208-217`) rather than a formal Enforcement section.
- **`## Do Not` sections**: two-word imperative bullets, no prose justification per bullet — this is the closest existing template for the task's requirement (3), "explicitly ban common divergence patterns."

#### Auto-apply / registration mechanism (concretely verified)

1. **Native consumption of `paths:`**: no script anywhere under `.claude/scripts/` or `.claude/hooks/` parses the `paths:` frontmatter key or the `## Path Pattern` prose for glob-matching (`grep -rn "paths:" .claude/scripts/*.sh` and hook directory returned nothing). The only place `.claude/rules/*.md` content is read programmatically is `.claude/scripts/check-extension-docs.sh:477` (`check_dangling_contract_references`), which scans rule files for dangling `.claude/context/contracts/*.md` references — unrelated to glob application. This confirms the `paths:` frontmatter is consumed by the Claude Code harness itself (a native rules-file convention), not by any bespoke tooling in this repo.
2. **CLAUDE.md `Rules References` `@`-import**: `.claude/CLAUDE.md`'s "Rules References" section explicitly `@`-imports 7 files — `state-management.md`, `git-workflow.md`, `error-handling.md`, `artifact-formats.md`, `workflows.md`, `plan-format-enforcement.md`, `no-task-references-in-deliverables.md`. This is a *separate*, unconditional-load mechanism (the imported file's full text is inlined into CLAUDE.md, which is itself always in context) — distinct from path-glob auto-apply. Notably, `pr-prohibition.md` and `project-overview-detection.md` are **not** in this `@`-import list despite being core rules, which is consistent with the hypothesis that path-glob-scoped rules (`pr-prohibition.md` matches `**/*`, i.e. always relevant; `project-overview-detection.md` matches one specific file) don't need the redundant unconditional `@`-import, while the seven listed rules are ones the system wants guaranteed present in every session regardless of what files get touched.
3. **Extension packaging is the actual sync unit**: a rule's canonical source lives at `.claude/extensions/{ext}/rules/{name}.md`, and the file must be listed in that extension's `manifest.json` `provides.rules` array (e.g. `.claude/extensions/lean/manifest.json:29` lists `"lean4.md"`; `.claude/extensions/cslib/manifest.json:32-35` lists `["cslib.md", "cslib-lint-fix.md"]`; `.claude/extensions/nvim/manifest.json` lists `["neovim-lua.md"]`). On extension load, the extension loader copies the file into the live `.claude/rules/{name}.md` and records it in `.claude/extensions.json`'s per-extension `installed_files` array (directly observed for the `nvim` extension: `.claude/rules/neovim-lua.md` is listed under `installed_dirs`/`installed_files` after `neovim-lua.md` was copied from `.claude/extensions/nvim/rules/neovim-lua.md`). `.claude/docs/architecture/extension-system.md:168-181` documents this: "Rules copied to `.claude/rules/`" on load, "All copied files removed" on unload.
4. **Whole-directory copy for propagating to consuming repos**: `.claude/docs/guides/copy-claude-directory.md:47-63` lists `rules/` under "Core Files (Always Copy)" when installing/propagating `.claude/` to a new or existing project. This is the "syncs out to consuming repos" mechanism referenced in the task's provenance note — a raw directory copy (or the repo's "Load Core" sync operation referenced in CLAUDE.md's `## Syncprotect` section) would pick up whatever is physically present under `.claude/rules/` or `.claude/extensions/*/rules/`, **regardless of manifest registration**.
5. **Concrete registration bug found (relevant caution for task 860)**: `.claude/extensions/core/rules/` on disk contains 8 files including `pr-prohibition.md`, but `.claude/extensions/core/manifest.json`'s `provides.rules` array lists only 7 (`artifact-formats.md`, `error-handling.md`, `git-workflow.md`, `plan-format-enforcement.md`, `state-management.md`, `workflows.md`, `project-overview-detection.md` — `pr-prohibition.md` is absent). Separately, `.claude/rules/no-task-references-in-deliverables.md` has **no** corresponding file under `.claude/extensions/core/rules/` at all — it exists only as a deployed copy in this repo's live `.claude/rules/`, with no canonical extension source. **Implication for task 860**: dropping a new rule file only into `.claude/rules/` (this repo's live/deployed copy) without also (a) creating the canonical source under the appropriate `.claude/extensions/{ext}/rules/` directory and (b) registering it in that extension's `manifest.json` `provides.rules` array would reproduce exactly this gap — the rule would work in *this* repo but not reliably propagate to a fresh extension-driven install in a consuming repo (though it would still propagate via a raw directory copy).

**Bottom line — what must be edited for the new rule to take effect and sync**: create the rule content file under the chosen extension's `rules/` source directory (see "Which extension should own it" below), add its filename to that extension's `manifest.json` `provides.rules` array, and copy/install the same file into this repo's live `.claude/rules/` (or `.claude/extensions/{ext}/rules/` if the extension isn't currently active here — this repo has no `.lean` files, so the rule need not be "active" in the live `.claude/rules/` for THIS repo to be correct). If core-scoped, also consider whether it warrants a `Rules References` `@`-import entry in `.claude/CLAUDE.md` (likely unnecessary given the glob is narrow and self-limiting to `.lean` files, matching the `pr-prohibition.md`/`project-overview-detection.md` precedent of not needing the redundant unconditional import).

### Glob Generalization (Requirement 4)

- `**/*.lean` (no directory prefix, matches any `.lean` file at any depth) is the exact glob already in production use by two independent extension rules that target Lean/formal-proof files: `.claude/extensions/lean/rules/lean4.md:2` and `.claude/extensions/cslib/rules/cslib.md:2` (also `.claude/extensions/cslib/rules/cslib-lint-fix.md:2`). `Theories/**` (the BimodalLogic-specific directory layout named in the task description as an anti-example) does not appear anywhere under `.claude/` in this repo.
- Path patterns are **advisory prose to the Claude Code harness's native rule-loading feature** (see Findings #2 above) — not machine-consumed by any script in this repo. This means the exact glob syntax should follow the existing convention precisely (a bare quoted string, e.g. `paths: "**/*.lean"`) for consistency and to avoid introducing a third frontmatter style.
- **Recommendation**: reuse `paths: "**/*.lean"` verbatim — it is already proven portable (works identically whether the consuming repo lays out proofs under `Theories/`, `Cslib/`, or any other directory name) and matches the two closest existing analogs exactly. No additional glob variants (e.g. `**/*.olean`, build artifacts) are warranted; `.lean` source files are the only place plan-compliance behavior is relevant.

- `.claude/extensions/formal/manifest.json`'s `provides.agents` is `["formal-research-agent.md", "logic-research-agent.md", "math-research-agent.md", "physics-research-agent.md"]` — **research-only**, no implementation agents, and `dependencies` is unset (does not auto-load `lean`). "Formal implementation agents" as a distinct category from `lean-implementation-agent`/`cslib-implementation-agent` does not exist in this codebase; the task description's "and other formal implementation agents" phrase most plausibly refers to `lean-implementation-agent`/`lean-implementation-hard-agent` and `cslib-implementation-agent`/`cslib-implementation-hard-agent` collectively, not a separate `formal-implementation-agent`.

**Recommendation for how to handle the naming gap**: bind the rule by **role via glob**, not by agent name. Because Claude Code rules attach to file paths (`**/*.lean`) rather than to named agents, the rule automatically applies to whichever agent is editing a `.lean` file — `lean-implementation-agent`, `lean-implementation-hard-agent`, `cslib-implementation-agent`, `cslib-implementation-hard-agent`, and any future formal-proof implementation agent — without needing to enumerate agent names in the rule body at all. This sidesteps the "may not exist in this repo" problem entirely and is forward-compatible: the rule's prose can mention `lean-implementation-agent` and "CSLib/formal implementation agents" as illustrative context (motivation, not a gate), while the actual binding mechanism (the glob) requires no agent-name maintenance.

### Overlap / Prior Art (Requirement 5 grounding + duplication check)

Three existing mechanisms brush against "plan compliance" / "anti-divergence" but none covers it directly:

1. **Literature Fidelity** (`.claude/extensions/lean/rules/lean4.md`, lines under `## Literature Fidelity`, backed by `.claude/extensions/lean/context/project/lean4/standards/literature-fidelity-policy.md`; duplicated near-verbatim in `.claude/extensions/cslib/rules/cslib.md`). This forbids shortcut-seeking, easier-route substitution, premature abandonment, and silent mixing — but scoped explicitly to following a **literature source** (a paper/textbook/proof sketch), with an explicit "First-Principles Mode" fallback when no literature is referenced (`literature-fidelity-policy.md:17-19,102-110`) that lifts all restrictions. It does **not** mention plans at all. The new rule is about a different document (the implementation *plan*, which exists on essentially every implementation dispatch, not just literature-guided ones) and must not be conflated with or silently duplicate this policy — it should cross-reference it as an adjacent, non-overlapping concern.
2. **H2 Anti-Analysis Contract** (`.claude/context/contracts/anti-analysis.md`). This governs read budget (first edit within 15-20% of tool calls) and forbids analysis-only conclusions without accompanying implementation — a *pace/output* concern, not a *sequence-fidelity* concern. Its "Settled-Design Preamble Protocol" (`anti-analysis.md`, near end) requires restating decided design and ruled-out alternatives at dispatch start, which is the closest existing language to "don't re-litigate settled decisions" — but it's `--hard`-only (loaded exclusively by `skill-implementer-hard`/`general-implementation-hard-agent`/`skill-orchestrate-hard`) and domain-agnostic (a `lean4`-specific override file exists at `.claude/extensions/lean/context/contracts/anti-analysis.md` but was not read in depth here). The new rule, by contrast, per the task description must apply unconditionally via glob (not gated behind `--hard`), which is a meaningful difference worth stating explicitly: today, nothing constrains plan-sequence fidelity in STANDARD mode at all, formal or otherwise.
3. **`plan-format-enforcement.md`** (`.claude/rules/plan-format-enforcement.md`) governs only the *format* of plan files (required metadata fields, phase heading syntax) — it says nothing about whether an agent must follow the plan's content once it exists. Not overlapping.
4. **Direct tension — the sanctioned "Plan Deviations" mechanism**: both `.claude/agents/general-implementation-agent.md:180-186` and `.claude/agents/cslib-implementation-agent.md:99-104` (and the extension-source mirror at `.claude/extensions/cslib/agents/cslib-implementation-agent.md`) document a formal, sanctioned way for an implementation agent to unilaterally **skip**, **alter**, or **defer** any plan step, with only a post-hoc inline annotation (`*(deviation: skipped -- {reason})*`) and a progress-file `deviations` array entry — no pre-approval gate, no escalation requirement. This is a deliberate, general-purpose escape hatch (referenced from `.claude/rules/plan-format-enforcement.md` for its annotation format). **The new rule, once bound to `**/*.lean` via a path glob, will apply whenever `cslib-implementation-agent` (STANDARD mode, not just `--hard`) touches a `.lean` file — meaning it directly narrows/overrides this general deviation-permissive default for the formal-proof domain specifically.** This is very likely the *intended* effect (the task's whole motivation is that this general permissiveness caused repeated divergence failures in a formal-proof repo), but the rule text should say so explicitly — e.g., "For files matching this rule's glob, the Plan Deviations annotation mechanism in `general-implementation-agent.md`/`cslib-implementation-agent.md` is not a substitute for compliance: any would-be skip/alter/defer must first be flagged as a blocker to the user, not silently annotated and proceeded past" — so the rule reads as an intentional, scoped tightening rather than an unexplained contradiction of documented general policy.

**Conclusion**: the new rule is genuinely missing from the codebase — no existing rule or contract prohibits "assessing what's truly minimal," inventing alternative approaches, skipping intermediate theorems, inlining proofs against a plan's decomposition, or "cleaner approach" rationalizations, scoped to formal proof files, in STANDARD mode. It should be written as a **new, small, focused rule** that (a) cross-references Literature Fidelity and H2 as adjacent-but-distinct, and (b) explicitly states its relationship to (narrowing of) the general Plan Deviations mechanism for its glob scope.

## Decisions

- The glob to use is `paths: "**/*.lean"` (bare-string frontmatter form, matching `lean4.md`/`cslib.md` exactly) plus an identical `## Path Pattern` prose line `Applies to: **/*.lean` — no repo-specific directory prefix.
- The rule should bind by **role via the glob**, not by literal agent-name enumeration, to remain correct regardless of which formal-proof agents (`lean-implementation-agent`, `cslib-implementation-agent`, and hard-mode variants) are active in a given consuming repo.
- The rule must **not** cite "BimodalLogic task 157" or any task number — `.claude/rules/no-task-references-in-deliverables.md` applies to it directly (it is a deliverable under `.claude/`, not under `specs/**`). See Recommendations for the durable-anchor substitute.

## Risks & Mitigations

- **Risk**: placing the rule only in `.claude/rules/` (this repo's live copy) without a canonical extension source + manifest registration reproduces the exact `pr-prohibition.md`/`no-task-references-in-deliverables.md` registration gap found above, risking the rule silently failing to propagate via a fresh extension-driven install in a consuming repo (though a raw directory copy would still work). **Mitigation**: author the canonical source under the chosen extension's `rules/` directory and add it to that extension's `manifest.json` `provides.rules` array (see Recommendations for the extension choice).
- **Risk**: an unqualified "ban all divergence" rule contradicts the documented, sanctioned Plan Deviations mechanism used by the same agents in non-`.lean` contexts, potentially confusing implementers or triggering an apparent policy conflict during review. **Mitigation**: explicitly scope the override statement as described in Findings #4 above.
- **Risk**: citing the motivating task number directly violates `no-task-references-in-deliverables.md`. **Mitigation**: see Recommendations below for durable-anchor phrasing.

## Recommendations

1. **Extension placement**: place the canonical rule source under `.claude/extensions/lean/rules/` (new file, e.g. `lean-plan-compliance.md`, or a new section appended to `lean4.md`) rather than top-level `.claude/rules/`. Rationale: the glob is meaningless outside Lean/formal-proof repos; `cslib` transitively receives it because `cslib`'s manifest declares a dependency on `lean` (auto-loaded); this repo (nvim config) has no `.lean` files so nothing is lost by not having it "live" here. If the task's explicit `.claude/rules/` instruction is taken literally instead, that also works (the glob self-limits to `.lean` files, so a core rule is harmless even in non-formal repos) — but then the plan/implementation phase must still register it in `.claude/extensions/core/manifest.json`'s `provides.rules` to avoid the exact registration gap found above. Either choice is defensible; the trade-off (universal-but-core vs. scoped-but-extension-gated) should be an explicit decision recorded in the implementation plan, not left implicit.
2. **Cross-reference, don't duplicate**: add a short "Related" pointer from the new rule to `## Literature Fidelity` (in `lean4.md`/`cslib.md`) and to `anti-analysis.md`'s Settled-Design Preamble, clarifying: Literature Fidelity = follow the *source*; H2 = pace/output during `--hard`; this new rule = follow the *plan's task sequence*, unconditionally (not `--hard`-gated).
3. **State the Plan Deviations override explicitly** in the rule body (see Findings #4) so it reads as an intentional, scoped tightening of the general-purpose deviation-annotation mechanism, not an unexplained contradiction.
