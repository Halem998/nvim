## Key Findings

1. **The task's core premise — "a confirmed cleanup decision reveals a durable sender preference" — is asserted, not validated anywhere in the task description or capture-point design.** Nothing in `skill-email-cleanup` distinguishes a transactional confirm ("archive this one receipt") from a preference-shaped confirm ("junk everything from this sender forever"). Every approval, per-message or per-bucket, is being fed into the same aggregation pipe with no signal for durability.

2. **The bucket-approval UI in `--all` mode (Stage 2.5) already aggregates by sender/domain for a different purpose (review ergonomics), and the design conflates that with aggregation for preference storage** — but a review-time bucket and a preference-storage key are not obligated to be the same partition, and the SKILL.md's own domain-bucketing rule ("for freemail/shared domains ... bucket by the full sender address instead") shows the author already knows one aggregation key is wrong for some senders. The research task doesn't ask whether the *memory* key should differ from the *review* key.

3. **The manifest schema's `sender` field is a bare string (`"sender": "a@b.com"`, wrapper-contracts.md line 46) with no normalization contract** — no guarantee of lower-casing, no separation of display-name from address, no handling of plus-addressing, DMARC-rewritten From headers, or mailing-list envelope senders (List-Id vs From). This is a concrete, checkable gap the design must resolve, not a hypothetical.

4. **Memory retrieval is corpus-wide and keyword-driven** (`memory-retrieve.sh`: extracts top-10 non-stopword tokens >4 chars from the task description, scores ALL active memories by keyword overlap, injects top 5 into `<memory-context>` for `/research`, `/plan`, `/implement`). There is no task-type partition and no domain/sender namespace exclusion. A memory like "user always junks mail from notifications@github.com" contains tokens (`github`, `notifications`) that can plausibly overlap with an unrelated software task description mentioning GitHub Actions, webhooks, or notifications — surfacing a personal email-triage preference into an unrelated coding task's context.

5. **No success metric or feedback-loop audit mechanism is specified anywhere in the 2-task chain (821 design → 822 implement).** The design task's own "Output" line (chosen capture point, schema, dedup/update strategy, opt-in/gate behavior) omits any notion of measuring whether the learned preferences are *correct* over time, and 822 has no corresponding verification phase implied.

## Recommended Approach (mitigations per gap)

### Gap 1 — Transactional vs. preference signal conflation
- Do not treat "1 confirmed action on 1 message" as sufficient evidence to write or strengthen a sender-level memory. Require an evidentiary threshold before a memory is created/strengthened: e.g. only synthesize/update a sender-preference memory when the AGGREGATE PATTERN across the confirmed set for that sender is uniform (all messages from the sender in this approval batch resolved the same way) OR when a rolling count/consistency ratio across multiple approvals reaches a threshold (e.g. N≥3 confirmations, ≥80% same action). Store a running tally per sender (confirmed_delete_count, confirmed_keep_count, confirmed_archive_count, last_seen) inside the memory itself — this is exactly the EXTEND operation's use case (append evidence, don't jump straight to a confident UPDATE) — rather than promoting to a stated "preference" after a single confirm.
- Explicitly flag GENUINELY MIXED senders (e.g. "GitHub notifications: security alerts=keep, marketing digests=junk") as a first-class outcome, not an edge case to average away. When confirmed actions for one sender disagree beyond a noise threshold, the memory should record the split (e.g. by subject-line pattern or notification-category token) rather than force a single scalar preference, or should decline to aggregate at all and stay per-subject/keyword-scoped under that sender. The design doc must specify this branch, since `--all` mode's own bucketing already demonstrates same-sender heterogeneity is expected, not exceptional.

### Gap 2 — Feedback-loop hazard / self-reinforcing bias
- Per general feedback-loop-bias literature (see Sources), implicit-labeling systems that reuse their own downstream classification as future training signal without an independent correction channel amplify early errors monotonically. Concretely here: if a stored sender preference feeds back into `email-classify`'s `proposed_action`/`confidence` (a natural next step, and the obvious reason to build this at all), and the human then reviews a pre-biased proposal, review-fatigue and default-approval behavior (well documented in the same literature as "automation bias") make it increasingly likely the human rubber-stamps the classifier's now-confident proposal rather than re-evaluating the sender from scratch. This is model drift/bias amplification, not aggregation-key bookkeeping, and belongs in the design's decision list, not deferred to 822.
- Mitigation to specify in the design: (a) cap the confidence contribution a stored preference memory may add to a proposed_action (i.e., memory-derived priors nudge but never alone justify the >=0.90 bulk-delete gate that already exists in the skill); (b) require the review UI to visibly surface "per memory: sender X has been junked N times, kept M times" rather than silently pre-selecting an action, so the human evaluates evidence rather than a foregone conclusion; (c) define an explicit REVERSAL/CORRECTION path — a later confirmed action that contradicts a stored preference must be able to depreciate or reset the preference's confidence (decay, not just accretion), otherwise one early bad approval (e.g. an accidental bulk-approve) becomes permanently entrenched. None of skill-memory's UPDATE/EXTEND/CREATE operations currently model "weaken/contradict an existing memory" — only replace-or-append. This is a genuine gap in the reusable memory API this design depends on, and 821 should either scope a minimal contradiction-handling convention (e.g., an explicit "counter-evidence" section in the memory template) or flag it to 822 as a required primitive, not silently inherit UPDATE-only semantics.

### Gap 3 — Identity/aggregation key instability
- The design must pick ONE explicit, documented key and its normalization rule, because the manifest gives you only a raw `sender` string:
  - Recommend: lower-cased, plus-tag-stripped LOCAL-PART@DOMAIN as the primary key (i.e., strip `+anything` before `@` per RFC 5233 sub-addressing convention), with DOMAIN alone as a fallback/rollup key for cases where the full address is too sparse to accumulate evidence (a middle tier between the SKILL.md's existing "domain vs full-address for freemail" split).
  - Explicitly call out and test against known breakage cases: (a) plus-addressing (`user+tag@domain.com` — same person, must collapse to one key); (b) mailing-list senders where From varies per message but List-Id is stable (aggregation should prefer List-Id when present, not From); (c) DMARC-rewritten forwarders (From rewritten to the forwarding service's domain — the "true" sender is lost unless Reply-To or original-From headers are inspected, which `email-census`/`email-classify` may not currently expose — verify before assuming this is solvable with the current manifest schema); (d) display-name spoofing/variance (same address, different display name across messages — must not fork the key).
  - This is squarely a research-task deliverable (schema decision), and should be verified against actual `email-census`/`email-classify` output samples, not assumed from the wrapper contract doc alone — the design should include a step that pulls a real census/classify sample and checks how "sender" is actually formatted in practice (raw address? "Display Name <addr>"? already-stripped?) before committing to a parsing rule.

### Gap 4 — Privacy/scope of email content in a general memory vault
- Recommend a segregated namespace/prefix (e.g. a dedicated tag `[EMAIL-PREF]` or a distinct directory such as `.memory/email-preferences/` outside `10-Memories/`, or at minimum a `topic: email-triage` field) so that (a) `memory-retrieve.sh`'s keyword-overlap scoring can be given an explicit task-type exclusion or de-weighting for this namespace when the invoking task_type isn't `email`, and (b) `/distill`, `/learn --task N`, and general memory search/list operations can filter it out of general-purpose surfacing by default. Storing raw email addresses and possibly subject-line fragments as memory `content` also means they get vacuumed into `/distill --compress`, `--merge`, and TTL/purge scoring alongside unrelated technical memories — the design should decide whether email-address content should be redacted/hashed in the stored memory (e.g. store domain + a stable pseudonymous sender-hash rather than the literal address) or accepted as plaintext PII living in a config-repo-adjacent vault. This tradeoff is currently undiscussed in the task description and is a real design decision, not an implementation detail — it determines the schema.
- Note that `memory-retrieve.sh`'s stop-word filter and >4-character token filter do NOT filter out proper nouns/domain fragments (e.ks. "github", "google", "notifications" all pass the filter), so the cross-contamination risk in Finding 4 is not hypothetical — it is a mechanical consequence of the existing scoring algorithm as written today.

### Gap 5 — Measurement / success signal
- The design (821) should explicitly define what "working" means, even if 822 implements the instrumentation minimally: candidates include (a) reduction in per-sender re-classification churn over time (does `email-classify`'s proposed_action for a previously-seen sender converge to the human's actual decision faster / need fewer manual overrides?), (b) a simple confirmed-vs-predicted agreement rate logged per sender at review time, (c) a periodic (`/distill`-adjacent) audit surfacing senders whose stored preference has been contradicted by recent confirms above some rate, prompting a re-review rather than silent decay. Right now the 2-task plan has no phase that reads back "did the memory help," which means correctness regressions would be invisible until a human notices misclassification.

- `memory-retrieve.sh` keyword extraction (`.claude/scripts/memory-retrieve.sh`, Phase 1) has no task-type namespace filter — it scores against `.memory/memory-index.json` globally, filtering only by `status == active`, not by any subject-domain segregation.
- `skill-memory`'s three operations (UPDATE/EXTEND/CREATE, `.claude/extensions/memory/skills/skill-memory/SKILL.md` lines ~245-360) have no documented "weaken/contradict" operation — UPDATE replaces, EXTEND appends; neither models reducing confidence in light of a contradicting new confirm.
- General feedback-loop bias literature confirms the mechanism described in Gap 2 is a known, named failure mode, not speculative: "Self-reinforcing feedback loops are dynamics where system outputs cyclically enhance inputs, leading to amplified behavior and potential runaway effects," and implicit-labeling systems specifically are called out as bias-prone because "user behavior may not accurately reflect actual spam versus legitimate email classifications, particularly when users have inconsistent email management practices" (see Sources below).
- DMARC/forwarding research confirms sender-identity instability is a live, documented problem class for email systems generally (rewritten From headers under forwarding, alignment-relaxed matching), supporting the identity-key critique in Gap 3 as grounded rather than speculative.

## Scope Completeness — what the 2-task plan (821 design → 822 implement) is overlooking

- **No revocation/opt-out UX**: nothing in either task considers how a user reviews, edits, or deletes an accumulated sender-preference memory once it exists (distinct from `/distill --purge`'s generic staleness-based tombstoning, which isn't targeted at "this preference is simply wrong").
- **No cross-account handling**: the email extension is explicitly multi-account (`gmail`/`logos`). The design doesn't say whether sender preferences are account-scoped or global — the same sender address could reasonably have different treatment per account/context, and nothing in 821's description asks this question.
- **No interaction with the existing `--archive` scope risk gates**: archive-scope sweeps are described elsewhere in SKILL.md as having a "much higher blast radius" with content the classifier's inbox-tuned rules were never validated against; if archive-scope confirms feed the same aggregation pipe as inbox confirms, a preference learned from stale archive mail (different era, different relevance) could bias current inbox classification. This interaction is not discussed in the task 821 description.
- **No explicit test/validation plan for 822**: the meta task's description is entirely about mechanism (capture point, schema, dedup/update strategy, gate behavior) with no mention of how correctness will be validated post-implementation (this overlaps with Gap 5 above but is worth flagging as a structural omission in the task breakdown itself, not just the design content).

## Confidence Level

**High** for Findings 1, 3, 4 (grounded directly in read source files with exact line/schema citations). **Medium-high** for Finding 2 (the feedback-loop mechanism is well-established in the general ML literature and the specific pathway — stored preference biasing `proposed_action`, which is then re-confirmed — is a highly plausible next-step design the task description gestures at ("system learns... preferences over time") even though it isn't explicitly stated as feeding back into classification; if the design team confirms preferences are NEVER fed back into classification confidence, this risk is moot, but the task description's stated purpose ("learns preferences over time") strongly implies eventual feedback use). **Medium** for Finding 5 and the scope-completeness section (these are process/completeness observations rather than technical facts, so "confidence" is really about relevance-to-decision-quality judgment).
