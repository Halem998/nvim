## Executive Summary

- Task 935 is fully landed and deployed: the admission verdict schema is now `orchestrate-batch-admit-v3`, the self-modification trigger is same-cycle co-dispatch-scoped (`${#eligible_tasks[@]}`), `deferred_self_modifying` is an append-only observation log (not a permanent exclusion), a bounded 3-cycle convergence guard (`consecutive_no_dispatch_cycles`) already exists, and `--allow-self-modifying` is live. This task's scope must build on all of that — it does not touch admission logic.
- **The zero-dispatch failure mode still reproduces under v3**, and is not a corner case: it reproduces empirically whenever every member of a wave/cycle's `eligible_tasks` is independently self-modifying (each one's own `file_scope` names a critical path) with no dependency edges forcing sequential eligibility — e.g. this session's own `/orchestrate 934,935,937` run, which deferred all three with `defer_reason: self_modifying` and dispatched nothing. The narrowing fixed a *false-positive* class (edge-connected pairs firing when they structurally never co-occur); it does not and cannot fix the *true-positive* case of several independent self-modifying candidates genuinely landing in one cycle together — that case is the residual, correctly-functioning gate doing exactly what it is designed to do, just illegibly.
- **The concrete legibility bug is a rendering gap, not a logic gap.** `commands/orchestrate.md`'s live "Consolidated Output" template (Step 5, `## Batch Orchestrate Results`) has table sections for Succeeded / Failed / Skipped / "Deferred (redeploy checkpoint)" — but **no section at all for self-modifying deferrals**, even though `skill-orchestrate/SKILL.md` Stage MT-5 explicitly instructs reporting `deferred_self_modifying` in the consolidated summary. In the reproduced zero-dispatch case, `completed_tasks=[]` and `failed_tasks=[]`, so the rendered table prints `Succeeded: 0 / Failed: 0 / Skipped: 0` with three empty tables and **no visible statement of why**, exactly matching the "silently did nothing" complaint.
- **A detection mechanism for the invariant already exists, unused.** `mt_state_file.dispatch_start_ts` is populated only at the moment a task is actually dispatched (Stage MT-4). If `task_numbers` (validated candidates) is non-empty but `dispatch_start_ts` stays `{}` for the whole invocation, that is the forward-progress invariant violated — already computable from existing state with no new bookkeeping, only a new read-and-report step at Stage MT-5.
- **The status vocabulary is closed and should not be extended.** `.return-meta.json`/`.return-meta-multi.json`'s `status` field is a normatively closed enum (`researched|planned|implemented|partial|failed|blocked`) shared across many consumers. The zero-dispatch outcome already correctly resolves to `"partial"` under existing MT-5 logic; the fix should add a **distinct boolean/field** (e.g. `forward_progress_violated`) plus a loud rendering branch, not a seventh status value.
- **`--dry-run` already renders "nothing admitted" reasonably well** (`0 admitted.` line, per-task exclusion reasons, `defer_reason`-aware text) — better, in fact, than the live path's Consolidated Output. But it computes the self-modification check with `--invocation-count` set to the WHOLE validated-batch size in one static pass, while the live path recomputes per-cycle with a shrinking `${#eligible_tasks[@]}`. This is a *documented, deliberate* divergence (dry-run cannot simulate multi-cycle convergence), but it means dry-run and live can legitimately disagree on which self-modifying tasks are excluded/deferred — Scope E's "agree on how they render nothing-will-dispatch" should target agreement on the render/vocabulary/structure of the no-dispatch state, not force identical per-task verdicts across a fundamentally different (static vs. cycling) computation model.
- Recommended detection locus: **Stage MT-5** (skill's postflight, after the cycling loop exits) is where the invariant should be computed and named, using data the loop already accumulates (`dispatch_start_ts`, `deferred_self_modifying`, `deferred_deploy_checkpoint`, `failed_tasks`); **`commands/orchestrate.md` Step 5** is where it should be rendered distinctly, since that is the human-facing surface and it already reads `mt_state_file`/`.return-meta-multi.json`. Both, not either — consistent with Scope A's own phrasing.

## Context & Scope

This is a meta-task researching how to make a **zero-dispatch** `/orchestrate` batch outcome loud and actionable, without changing any admission decision. The declared file scope is `commands/orchestrate.md`, `skills/skill-orchestrate/SKILL.md`, `scripts/orchestrate-dry-run-report.sh`, and `context/patterns/batch-orchestration-guardrails.md` — all in `agent-system/extensions/core/` (source store; `.claude/` is a disposable, gitignored deploy artifact regenerated from it).

Task 937 depends on task 935, which landed **minutes before this research** and is already deployed. The task description's motivating incidents and CAUTION note both predate 935's landing; this report re-verifies which parts of the original problem statement are still live under the new (v3) semantics before scoping design work, per the delegation context's explicit instruction.

## Findings

### Codebase Patterns

**Current admission schema (v3, confirmed via `scripts/orchestrate-batch-admit.sh` header and `docs/architecture/batch-admit-schema.md`)**:
- `$schema: "orchestrate-batch-admit-v3"` on every verdict.
- `self_modifying: bool|null` present on every verdict (including admits).
- `defer_reason` — required discriminator on every `"defer"` verdict: exactly `"self_modifying"` or `"file_scope_collision"`.
- Self-modification precedence: tested first, short-circuits the collision scan.
- Self-mod trigger: candidate's own `file_scope` names a critical path (`context/reference/orchestrator-critical-paths.json`, 10 entries: the two orchestrate skills, `commands/orchestrate.md`, `skill-base.sh`, `task-lock.sh`, `update-task-status.sh`, `orchestrate-batch-admit.sh` itself, `orchestrate-triage-classify.sh`, `orchestrate-dry-run-report.sh`, `verify-deploy.sh`) **AND** `--invocation-count > 1` for THIS candidate's actual same-cycle co-dispatch set.
- `--allow-self-modifying` (default off): consumer-side-only bypass, threaded through `parse-command-args.sh` → `commands/orchestrate.md` STAGE 0 → skill delegation context `allow_self_modifying` → `skill-orchestrate/SKILL.md` Stage MT-3 step 4.5. Never passed to the script itself; the script always emits the honest verdict.

**Stage MT-3's cycling loop (`skill-orchestrate/SKILL.md`)** already contains substantial convergence machinery from task 935:
- Step 3 no longer excludes self-modifying candidates from `eligible_tasks` pre-admission (that exclusion set is gone).
- Step 4.5 calls `orchestrate-batch-admit.sh --invocation-count "${#eligible_tasks[@]}" "${eligible_tasks[@]}"` **every cycle**, branches on `defer_reason` first, and for `self_modifying` (absent override) removes the candidate from *this cycle's* dispatch batch and appends it to `mt_state_file.deferred_self_modifying` — an **append-only OBSERVATION LOG**, not an exclusion set. The defer clears naturally once the co-dispatched sibling leaves `eligible_tasks`.
- A **convergence guard** already exists for the case where natural clearing does not happen: `consecutive_no_dispatch_cycles` increments whenever `eligible_tasks` was non-empty but the self-mod branch deferred every member (empty actual dispatch batch this cycle); resets to 0 on any cycle with ≥1 real dispatch; at 3 consecutive cycles, breaks the loop with `partial` status and a named diagnostic string logged inline (not surfaced structurally in `mt_state_file` as its own field, and not rendered in the command's Consolidated Output at all today).
- **Stage MT-5** (postflight) already computes `exit_status` from `failed_count`, terminal-state status of every `deferred_self_modifying` entry, and `deferred_deploy_checkpoint` emptiness, and **explicitly instructs** (prose only — not yet reflected in the command's rendered template) reporting `deferred_self_modifying` tasks "as deferred at least one cycle by the self-modification gate — an OBSERVATION" and `deferred_deploy_checkpoint` tasks as a distinct category with a distinct operator remedy.

**The rendering gap (`commands/orchestrate.md` Step 5, "Consolidated Output")**: the actual printed markdown template has exactly these sections: `Succeeded`, `Failed`, `Skipped`, `Deferred (redeploy checkpoint)`, `Next Steps`. There is **no `Deferred (self-modifying)` section**, despite Stage MT-5's own prose saying this category must be reported "in the consolidated summary." In the reproduced zero-dispatch case (see below), `succeeded_count=0`, `failed_count=0`, `skipped_count=0` (skips are pre-dispatch-validation only; mid-loop self-mod defers never populate `failed_tasks` or `skipped_tasks` by design — "defer-not-fail"), so the rendered output is three empty tables and a `Cycles used: N/max` line, with the *only* place the real reason could appear being inline log lines from Stage MT-3 step 4.5's warnings — which are not part of the final consolidated summary artifact and are easy to miss/scroll past. This is precisely the "renders like an ordinary result" bug named in the task description.

**Existing, unused detection primitive**: `mt_state_file.dispatch_start_ts` (a `task_num -> unix_seconds` map, Stage MT-1 init) is written *only* at the moment Stage MT-4 actually dispatches a task (three call sites, each doing `jq ... '.dispatch_start_ts[$t] = $ts'`). If the validated candidate set (`task_numbers`) is non-empty but `dispatch_start_ts` is `{}` at loop exit, no task was ever actually dispatched this invocation — this is a ready-made, already-recorded fact that directly operationalizes Scope A's invariant ("validated-candidate set non-empty, admitted set across all waves empty") without adding new bookkeeping.

**`--dry-run` (`scripts/orchestrate-dry-run-report.sh`)** already renders a reasonably legible no-admission state: an explicit `0 admitted.` line (never a bare empty table), an `Excluded` section with one line per task naming `defer_reason`-specific human text (self-modification hazard vs. file_scope_collision vs. lock vs. out-of-batch predecessor), and a `Recommended split` section giving wave-ordered task groupings. However:
- It calls `orchestrate-batch-admit.sh` **once**, with `--invocation-count` set to the **whole validated-batch size**, explicitly and deliberately (per its own header comment) — this is a *static, single-pass* analysis, not a simulation of the live per-cycle loop where `${#eligible_tasks[@]}` shrinks as tasks complete. Dry-run therefore can, by design, report a different self-modification exclusion set than what the live multi-cycle run will actually produce (e.g., dry-run may show 3 mutually-excluding self-modifying tasks, while live would actually dispatch task N first in cycle 1 if its sibling isn't co-eligible that cycle, then task M in cycle 2, etc.).
- Dry-run has no equivalent of the `consecutive_no_dispatch_cycles` bounded-convergence concept (it cannot — it isn't a loop), and produces no "solo re-run command sequence" — it stops at naming exclusions and reasons, and its `Recommended split` gives wave groupings, not literal runnable `/orchestrate N` command lines in dependency order.
- The multi-task Consolidated Output's shared sibling — `context/patterns/multi-task-operations.md` §9's generic template (used by plain multi-task `/research`, `/plan`, `/implement`, which have no admission gate at all) — also has no "deferred" bucket, for the unrelated reason that those commands never defer anything pre-dispatch. This confirms the missing bucket in `orchestrate.md`'s own template is a `/orchestrate`-specific gap, not an inherited limitation from the shared pattern doc.

**Status vocabulary constraint**: `context/formats/return-metadata-file.md` defines a normatively closed status enum (`researched|planned|implemented|partial|failed|blocked`) shared by `.return-meta.json`, `.return-meta-multi.json`, and `.orchestrator-handoff.json`. Adding an eighth value (e.g., a literal `"no_dispatch"` status) would require touching this cross-cutting, multi-consumer schema doc, which is out of this task's declared file scope and not warranted — the zero-dispatch case already correctly resolves to `"partial"` under existing MT-5 logic (assuming any deferred task remains non-terminal, which is definitionally true if nothing dispatched). The right fix is an **additional field or flag alongside `status`**, not a new enum member.

### Empirical Verification: Do the Original Incidents Still Reproduce?

The task description names two "verified incidents" under the *old* (pre-935) whole-invocation-scoped self-mod exclusion, plus a *third*, live data point from this very session under the *new* (v3, same-cycle) semantics:

1. **This session's own `/orchestrate 934,935,937`** (v3-era, live, reproducible right now): all three candidates were excluded with `defer_reason: self_modifying`, and nothing dispatched. This happened because all three tasks' declared `file_scope` names orchestrator-critical paths (934/935 are prior orchestrator-hardening tasks; 937 itself declares `commands/orchestrate.md`, `skills/skill-orchestrate/SKILL.md`, `scripts/orchestrate-dry-run-report.sh`, `context/patterns/batch-orchestration-guardrails.md` — 3 of the 10 critical paths), and (at the time of that run) no completed dependency chain had yet thinned `eligible_tasks` down to a batch of one. **This is a true positive of the gate working exactly as designed** — hazard 1 (verification gap) is real and each of these tasks genuinely should not run concurrently with another critical-path-touching sibling. The bug is not that they were deferred; the bug is that the resulting report gave no visible reason.
2. **The two originally-named incidents** (885,926,887,931,920; 934-935) predate 935's narrowing and were likely produced by the *old* whole-invocation-scoped exclusion (a broader, more falsely-triggering mechanism). Whether they would reproduce identically today cannot be re-run (some of those tasks are presumably since completed/renumbered), but the mechanism class is unchanged in kind: **any wave/cycle where every eligible candidate is independently self-modifying, with no dependency edges to serialize them, still zero-dispatches** under v3 — the narrowing removed a false-positive trigger (edge-connected pairs, which could never actually co-occur anyway), not the true-positive case of multiple unrelated self-modifying tasks landing in the same cycle. **Conclusion: the full scope A-F of this task remains live and necessary.** Task 935 did not shrink this task's scope; if anything it sharpens the target, because the remaining zero-dispatch cases are now demonstrably real (not artifacts of an over-broad old rule), so the legibility fix is protecting a correct decision, not merely a buggy one.
3. The bounded `consecutive_no_dispatch_cycles` guard (task 935) already prevents this from silently spinning to `MAX_CYCLES_MT` — it breaks after 3 cycles with `partial` and an inline diagnostic. This is real, existing progress toward Scope A/C, but it (a) only covers the *self-modifying-mutual-collision* cause of zero-dispatch, not `file_scope_collision` cross-batch exclusions or out-of-batch unmet-predecessor exclusions that could equally produce zero admits across an entire batch in a single cycle without ever reaching 3 "consecutive" cycles (e.g., a 2-task batch where both collide cross-batch on cycle 1 could plausibly break out via a different existing path — the "no-eligible circuit breaker" at step 4 — worth confirming exhaustively in planning, not assumed complete), and (b) the diagnostic is a log line, not a structured, rendered report field.

### Recommendations (per declared scope)

**A — Define and locate the invariant.** Name it explicitly, e.g. **"zero-dispatch outcome"** or **"forward-progress violation"**: *validated candidates were non-empty, but the invocation dispatched nothing across every cycle it ran.* Recommend defining it precisely as: `task_numbers` (or the validated subset) is non-empty AND `mt_state_file.dispatch_start_ts` is empty at Stage MT-3 loop exit. Detect it in **Stage MT-5** (the skill's postflight, after the loop — where all the accumulated facts already live) and **also** thread a boolean/summary field through to `commands/orchestrate.md` Step 5 for rendering (both loci, matching Scope A's "or both" framing) — detection computation belongs in the skill (single source of truth over `mt_state_file`), rendering belongs in the command (the human-facing surface). Do not touch the already-fixed once-per-invocation-vs-once-per-wave prose in `commands/orchestrate.md`'s wave-split-check subsection — that landed with task 935 and should not be re-touched or duplicated.

**B — No-dispatch report design.** Recommend:
- A structurally distinct, visually loud section — e.g. a `## ZERO-DISPATCH OUTCOME` banner-style header (analogous in spirit to this codebase's existing `[SPARSE COVERAGE ...]`/`[UNVERIFIED ...]`/`[DEGRADED RETRIEVAL ...]` loud-banner family used elsewhere for non-silent degraded states) — inserted into `commands/orchestrate.md`'s Consolidated Output template, conditioned on the new invariant flag, placed before the ordinary Succeeded/Failed/Skipped tables so it cannot be scrolled past or mistaken for a normal empty-batch result.
- It must enumerate **every** excluded/deferred candidate with its `defer_reason` (reusing `deferred_self_modifying` and `deferred_deploy_checkpoint` from `mt_state_file`, plus any `file_scope_collision`/unmet-predecessor exclusions surfaced during the loop — confirm at planning time whether these latter two are currently retained anywhere in `mt_state_file` for post-hoc reporting, or only logged inline and lost; if only logged, that is itself a gap to close).
- It must print the **exact re-run command sequence in dependency order** — this is mechanically derivable: reuse the Kahn/wave computation `commands/orchestrate.md` Step 3 already performs (or dry-run's equivalent) to topologically order the deferred set, then emit literal lines like `/orchestrate 935` then `/orchestrate 937` (predecessor-first). This is new composition, not new algorithm — the topological order already exists elsewhere in the same file.
- Add a `Deferred (self-modifying)` table section to the Consolidated Output template alongside the existing `Deferred (redeploy checkpoint)` one, closing the direct prose/template mismatch found above.

**C — Exit/status contract.** Recommend: reuse the existing `"partial"` status (already correct per current MT-5 logic for this case — do not add a new enum value, given the closed, multi-consumer vocabulary). Add a distinct **additional field** (not a status value) — e.g. `forward_progress_violated: true/false` or `zero_dispatch: true/false` — in `.return-meta-multi.json`'s `metadata` object, to disambiguate "partial because some tasks failed/blocked" from "partial because literally nothing dispatched." Explicitly confirm and document (Scope C asks to confirm, not change): the defer-not-fail invariant already holds for this outcome — no `specs/state.json` mutation, no task marked failed, per the admission script's own "Exit codes" contract and the skill's explicit "never add to failed_tasks... never mutate status" language throughout Stage MT-3/MT-5. Whether the invocation "consumes a cycle": yes, structurally — `cycle_count` still increments even on an all-deferred cycle (Stage MT-3 step 6 runs unconditionally after dispatch); this should be stated plainly in the plan/guardrails doc as a recorded fact, not changed.

**D — Auto-degradation to solo sequence.** Recommend confirming the task description's own PRINT-ONLY presumption: never auto-convert a zero-dispatch batch into N sequential solo `/orchestrate` invocations without consent — this would silently multiply cost (each solo run pays its own research/plan/implement dispatch and possible redeploy-checkpoint cost) and violates the documented "zero synchronous confirmation gates... but human review happens only after the fact" design (`batch-orchestration-guardrails.md`'s "Divergence from External Practice" section) by taking a *bigger*, uninvited action instead of a smaller one. Print the sequence (Scope B); do not execute it.

**E — `--dry-run` parity.** Recommend: give `orchestrate-dry-run-report.sh` the same distinct "zero admitted, here is why, here is the re-run sequence" rendering as the live path gets, reusing its already-present `0 admitted.` line and `Excluded`/`Notes` sections as the foundation, and adding the same dependency-ordered re-run command list. Do **not** attempt to force dry-run's single-pass, whole-batch-sized admission call to numerically match the live path's per-cycle, shrinking-`eligible_tasks` computation — that divergence is deliberate and already documented (dry-run cannot simulate multi-cycle convergence without becoming a second, drifting copy of Stage MT-3's loop, which the file's own header explicitly avoids: "one code path, two consumers"). Parity should mean *rendering convention* parity (same banner, same fields, same command-sequence format), not *identical verdict-set* parity across a static analysis vs. a stateful loop.

**F — Guardrails doc.** Add a new subsection to `context/patterns/batch-orchestration-guardrails.md` (the target file itself) analogous in weight to the existing "The Inter-Cycle Redeploy Checkpoint" subsection: name the forward-progress invariant, its detection locus (Stage MT-5 + Step 5 rendering), its relationship to the existing `consecutive_no_dispatch_cycles` bounded guard (this task's invariant is the *general* outcome-legibility fix; the guard is one *specific* non-convergence-prevention mechanism that is one of several possible causes), and record — per this report's empirical finding — that the narrowing in task 935 did not shrink this task's scope, since the remaining zero-dispatch cases are demonstrated true positives of the gate, not artifacts of the old over-broad rule.

## Decisions

- Treat the forward-progress invariant as **MT-mode-only** by construction: single-task `/orchestrate` has no wave/admission concept at all (a lone task either dispatches or is blocked, and single-task Stage 4 already escalates `blocked` to human review rather than rendering a silent empty table) — Scope A's own phrasing ("validated-candidate set," "admitted set across all waves") is inherently plural/MT-scoped, and this report does not propose extending it to single-task mode.
- Do not introduce a new `.return-meta*.json` `status` enum value; use the existing `"partial"` plus a new boolean/field, per the closed-vocabulary finding above.
- Do not re-touch or duplicate the once-per-invocation-vs-once-per-wave prose fix in `commands/orchestrate.md`'s wave-split-check subsection; task 935 already landed it.
- Treat dry-run/live rendering parity (Scope E) as a **format/vocabulary** parity requirement, not a **verdict-set-identity** requirement, given the documented static-vs-cycling computation divergence.

## Risks & Mitigations

- **Risk**: conflating the new "zero-dispatch" concept with the existing `consecutive_no_dispatch_cycles` guard could lead to only covering the self-modifying-collision cause and missing cross-batch `file_scope_collision` or out-of-batch-predecessor causes of an all-cycle-empty outcome. **Mitigation**: define the invariant at the `dispatch_start_ts`-empty level (cause-agnostic), and treat the existing guard as one contributing mechanism among several, per Scope F's recommended framing.
- **Risk**: adding a loud banner section could be over-triggered on ordinary partial-success batches (some succeeded, some failed) that are not actually zero-dispatch. **Mitigation**: gate the new banner strictly on the precise invariant (validated non-empty AND `dispatch_start_ts` empty), never on "any deferral present" — a batch that dispatched 2 of 3 tasks and deferred the third is a normal partial success, not a zero-dispatch event.
- **Risk**: enumerating the "exact solo re-run command sequence" requires exposing enough dependency-graph state at Stage MT-5/Step 5 to topologically sort the deferred set; if that data isn't retained past Stage MT-3, this could require new bookkeeping beyond the declared file scope. **Mitigation**: `commands/orchestrate.md`'s own `dependency_graph`/wave computation (Steps 2-3) is already available at Step 5 in the same command invocation — reuse it directly rather than reconstructing it inside the skill.

## Context Extension Recommendations

None beyond Scope F itself — `context/patterns/batch-orchestration-guardrails.md` is one of the four declared in-scope files, and this task's own deliverable is to extend it with the forward-progress invariant subsection described above.
