## Key Decisions Made

Two NEW hazard sub-patterns were identified during Phase 7, beyond Phase 6's three documented
classes — these extend the reusable playbook for Phase 8-10 (though Phase 8 is shebang-only and
Phase 9-10 are new test files, so these mainly matter for future strict-mode work):

4. **Standalone `((VAR++))` post-increment as a bare command** (not `VAR=$((VAR + 1))`). Under
   `set -e`, `((expr))` used as a standalone command returns nonzero (failure) whenever `expr`
   evaluates to 0 — for post-increment, that's the PRE-increment value, so `((tab_index++))`
   fails on the very first loop iteration when `tab_index` starts at 0. Found in tts-notify.sh's
   `get_tab_prefix` tab-position loop. Fix: rewrite as `VAR=$((VAR + 1))`, a plain assignment
   which is never subject to this hazard class.

5. **Bare grep/jq capture assignments whose common case IS the no-match/failure case.** Distinct
   from Phase 6's dominant "downstream already has a `[ -z ]` graceful check" framing: several
   Phase 7 sites are hazardous specifically because the NO-MATCH case is the *frequent, ordinary*
   outcome (e.g. `ADD_SEGMENTS=$(echo "$COMMAND" | grep -oE 'git add...')` in
   guard-destructive-git.sh fails on every command that ISN'T `git add` — i.e. almost every real
   invocation). This is the same `|| true` fix as Class 1, but worth naming separately because the
   audit heuristic "is this hazard rare or common" is exactly backwards here: unlike Class 1's
   rare-failure-path framing, these are common-path failures hiding behind grep's specific
   no-match convention (exit 1 with pipefail propagating it past `head`/`cut`/etc).

**Live fixture methodology extended**: for hooks that read PreToolUse/PostToolUse JSON via stdin,
build the fixture command as `jq -n '{tool_input:{...}}' | bash <hook>` rather than a raw echo —
this exercises the exact `.tool_input.*` field paths the hook's own jq extraction expects. For
guard-destructive-git.sh specifically, build a real `mktemp -d` git repo (not just a JSON fixture)
so the dirty-tree / clean-tree / marker-freshness logic is exercised against real `git status
--porcelain` and `git stash`/`git checkout` state, not just mocked.

**Success-path hazards are the highest-priority find of this phase**: several Phase 6 hazards were
on FAILURE/degradation paths (the anti-pattern's whole point was preserving error-branching
logic). Phase 7 found multiple hazards squarely on the SUCCESS path instead — e.g.
`events-log-lifecycle.sh`'s `[ -z "$session_id" ] && exit_success` aborted precisely when a
marker WAS found with a valid session_id (the normal, intended case the hook exists to handle),
and `orchestrate-dry-run-report.sh`'s `task-lock.sh check` anti-pattern aborted whenever a lock
was legitimately held (an everyday occurrence during real orchestration, not an edge case). A
audit pass that only reasons about "what happens on failure" will miss this class; the correct
question is "what happens on EVERY branch this bare statement can take," not just the unhappy one.
