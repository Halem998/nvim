## Key Decisions Made

- Did not sample-check a handful of pairs and extrapolate — verified Message-Id equality across
  ALL 862 pairs programmatically before drawing any conclusion, given the stakes of a wrong
  assumption here (irreversible mail loss).
- Considered and rejected a "blind rename" workaround (strip the colliding `U=NNN` filename token
  on one arbitrary member of each pair, without server verification) because it risks mbsync
  treating the renamed file as new local content and pushing/re-uploading it to the Proton server
  on the next reconcile, which could create a genuinely new server-side duplicate — directly
  against this task's Non-Goal ("no new bloat") and against the spirit of "stop-on-failure,
  scoped reconcile only."
- Chose to stop and document rather than force through Task 2-4, per the orchestrator's explicit
  directive to mark a phase `[PARTIAL]` with a blocker rather than force a destructive/uncertain
  step when a verification gate fails.

  unpredictable behavior on the next `mbsync logos`.
