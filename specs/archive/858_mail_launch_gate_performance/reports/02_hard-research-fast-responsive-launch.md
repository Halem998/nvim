## Executive Summary

One `<leader>me` press runs **two causally-triggered full sync layers back to back**
(`mbsync -a` over all 15 configured channels, then — via the hook-ful `notmuch new` — the
preNew hook's `mail-sync both`, i.e. `mbsync gmail` + `mbsync logos` again), all on the
launch-blocking critical path. The himalaya "Starting sync for inbox" is **not** triggered by
`<leader>me`; it is an independent auto-sync timer that fires 2 s after Neovim startup and
every 15 minutes thereafter, and merely coincides (and contends for the same mbsync channels).

The launch is **permanently blocked by two independent defects**, either of which alone would
block it:

1. The gate's primary arm requires `mbsync -a` exit 0 (`mail.lua:49,72`), which the unrepaired
   duplicate-UID-15 collision in `Gmail/.All_Mail` makes permanently impossible.
2. The gate's fallback arm (`email-census` freshness) is **currently returning a false
   `[STALE]` for logos**: the index is in fact perfectly fresh (337 on-disk = 337 indexed when
   queried with `--exclude=false`), but census's `notmuch search --output=files` silently drops
   22 INBOX messages tagged `trash` by the `/email` triage flow, because default notmuch
   searches honor `search.exclude_tags = deleted;spam;trash`. This is the exact
   documented-but-unheeded trap in `~/Mail/.claude/context/project/email/domain/wrapper-contracts.md:360-379`.

Meanwhile, the only thing aerc (a `notmuch://~/Mail` reader) actually needs before opening —
a completed index reconcile — was **measured at 0.194 s** (`notmuch new --no-hooks`, 65,237-message
DB). The recommended redesign gates the launch on exactly that, opens aerc in sub-second time,
and defers all server syncing to a single backgrounded, flock-serialized `mail-sync` pipeline
whose exit code can warn but never block.

### 1.1 The himalaya layer: independent, NOT triggered by `<leader>me`

`"Starting sync for inbox..." / "Sync completed for inbox"` come from
`himalaya/ui/main.lua:552,605` (`M._perform_sync(channel, 'inbox')`, `main.lua:704`, inside
`M.sync_inbox()`, `main.lua:686`). Verified callers of `sync_inbox`:

- **Auto-sync timer** — `himalaya/sync/manager.lua:395-397`, started unconditionally at plugin
  setup (`himalaya/init.lua:79`). The plugin loads on `VeryLazy`
  (`tools/himalaya-plugin.lua:8`), the timer first fires after `ui.auto_sync_startup_delay`
  (default **2 s**, `manager.lua:330`) and repeats every `ui.auto_sync_interval` (default
  **15 min**, `manager.lua:329`), enabled by default (`manager.lua:320`).
- `:HimalayaSyncInbox` (`himalaya/commands/sync.lua:24`) and the sidebar-local `s` keymap
  (`himalaya/config/ui.lua:380-385`).

None of these is invoked from `mail.lua`'s `<leader>me` block (`mail.lua:111-175`), and
which-key's `<leader>me` entry is annotation-only (`editor/which-key.lua:627-629`). The
observed log ordering (inbox sync completing just before "Syncing all accounts...") matches a
startup-delay or interval firing coinciding with the press.

**It still matters**: himalaya wraps its mbsync in `flock -n /tmp/himalaya-mbsync-<channel>.lock`
(`himalaya/sync/mbsync.lua:321`, `himalaya/sync/lock.lua:16-40`) — a **different lock namespace**
from `mail-sync.lock`, and `mail.lua:47`'s `mbsync -a` takes **no lock at all**. Three
uncoordinated entry points into mbsync can therefore overlap; mbsync's own per-box
`.mbsyncstate.lock` prevents corruption but converts collisions into additional spurious
non-zero exits — which the current gate treats as launch-blocking failures.

## 3. Root-Cause Statement

**Performance problem** (why it is slow): `<leader>me` serializes two redundant full
dual-account server syncs on the launch path — the forbidden-form `mbsync -a` (`mail.lua:47`)
plus, recursively via the preNew hook of the hook-ful `notmuch new` (`mail.lua:30` →
`notmuch.nix:41`), `mail-sync both`. The interaction is emergent: nvim task 857 added the
"reindex on both outcomes" chain while dotfiles task 109 repointed preNew from a no-op-ish
sync to the full serialized `mail-sync both`; each change is sound in isolation, and together
they double minutes-scale work. Nothing is deferred until after the open.

**Correctness/UX problem** (why it never opens): the gate conflates "the server sync
succeeded" with "the index is safe for aerc to read". Its primary arm hard-couples launch to
`mbsync -a`'s exit code (`mail.lua:49` branches on `code == 0`; `mail.lua:72` reports
`on_done(false)` even when the reindex succeeded), so a sync-independent, persistent data
fault (duplicate-UID-15) permanently denies launch. Its fallback arm is exit-code-independent
by design but **broken in implementation**: `email-census`'s freshness computation
(`~/.dotfiles/modules/home/email/agent-tools/census.nix:48-50,59-61`) builds the "indexed"
side of its file diff from default (exclusion-honoring) `notmuch search --output=files`
calls, so the 22 Logos INBOX messages currently tagged `trash` by the `/email` triage flow are
invisible to it — `added=22` → `[STALE]` forever, despite the index being verifiably complete
(§4.5). Two independent permanent reds; the block is total.

## 4. Adversarial Verification of the Seed Report (H4)

### 4.1 Claim (a): "one press causes three distinct sync layers" — PARTIALLY CONFIRMED, REFINED

**Two** sync layers are causally triggered per press (steps 2 and 4a-4d in §1). The himalaya
inbox sync is **refuted as a per-press trigger**: it is an independent timer
(`manager.lua:350`, first fire 2 s after `VeryLazy` setup, then every 15 min) plus manual
triggers, none reachable from `mail.lua`. It is, however, a genuine third *concurrent* sync
layer in the same window (startup-adjacent presses almost always overlap it) and contends for
the same channels under a disjoint lock namespace (§1.1).

### 4.2 Claim (b): hook-ful `notmuch new` recursively drives `mail-sync both` — CONFIRMED

`mail.lua:30` runs `{"notmuch", "new"}` with no `--no-hooks`. The live hook file
`~/.config/notmuch/default/hooks/pre-new` contains exactly `mail-sync both || true`
(matching `notmuch.nix:41`). `mail-sync both` runs `mbsync gmail` then `mbsync logos` under
one flock and reindexes with `--no-hooks` (`mail-sync.nix:149-156`) — so the recursion
terminates at depth 1 (no reentrancy, per `notmuch.nix:38-40`), but the press pays for a
second full dual-account sync.

### 4.3 Claim (c): gate blocks on mbsync EXIT CODE, permanently — CONFIRMED, with refinement

Confirmed for the primary arm: `mail.lua:48-49` branches on `mbsync -a`'s exit code and
`mail.lua:72` propagates `on_done(false)` even after a successful reindex. The refinement is
that the gate does *possess* an exit-code-independent fallback (census, `mail.lua:161`) — the
seed's "(b) honestly reports [STALE] whenever real drift exists" is **refuted**: the fallback
is currently reporting STALE with **zero real drift** (§4.5). The permanent block is therefore
over-determined, and fixing the duplicate-UID alone would NOT reliably unblock `<leader>me`
(the census false-STALE persists as long as any INBOX message carries an excluded tag).

### 4.4 Claim (d): is `notmuch new --no-hooks` alone sufficient and fast? — CONFIRMED (with one tagging caveat)

**Fast**: measured 0.194 s (0.262 s `--full-scan`) vs. minutes for either sync layer.

**Sufficient for aerc-read-safety**: yes. aerc's backend is `notmuch://~/Mail` for both
accounts (`~/.config/aerc/accounts.conf:2,12`). Read-safety requires (i) the index agrees with
the on-disk maildir (no entries pointing at renamed/removed files — the "could not get
MessageInfo" class) and (ii) no reader opens mid-rewrite. A **completed foreground**
`notmuch new --no-hooks` establishes (i) — verified live: immediately after it, the logos
INBOX index is exactly the on-disk set (337 = 337 under `--exclude=false`) — and running it to
completion *before* the open establishes (ii), satisfying the Synchronous/Locked/Uninterruptible
contract (`~/Mail/.claude/context/project/email/domain/index-architecture.md:76-92`) for the
launch barrier without any mbsync in the path.

**Caveat (tagging)**: `--no-hooks` skips postNew, so files it newly indexes carry only
`tag:new` (from `new.tags`, `notmuch.nix:64-65`) and not yet `inbox`/`unread`/account tags —
and aerc's querymap INBOX view filters on `tag:inbox`. This is not a safety issue (messages
are indexed and readable; they appear in INBOX views on the next hook-ful pass, whose postNew
retags by `tag:new` regardless of which run indexed the files). The recommended design (§5)
closes this gap by running one hook-ful `notmuch new` in the background after the open.

### 4.5 NEW FINDING: the census freshness fallback is false-STALE by construction

Live probe sequence (all read-only/index-only):

1. `email-census --account logos` → `on-disk=337 indexed-files=315 divergence=22 ... added=22 [STALE]`
2. `notmuch new --no-hooks --full-scan` → "No new mail" (0.262 s) — census still `[STALE]`, `added=22`
3. The 22 "missing" filenames (e.g. `Logos/cur/1783354873.4003086_145.hamsa,U=145:2,`) are not
   in the non-mail-ignore list; `notmuch search --output=tags --exclude=false id:<one of them>`
   → `gmail logos proposed-archive trash unread` — **indexed, but tagged `trash`**
4. `notmuch search --output=files 'path:Logos/cur or path:Logos/new'` → 315 files;
   the same query with `--exclude=false` → **337 = on-disk count exactly**

Root cause: `search.excludeTags = [deleted, spam, trash]` (`notmuch.nix:73-79`) applies to
every default `notmuch search`, including census's indexed-files queries
(`census.nix:48-50,59-61`). The census comment at `census.nix:55-58` claims its `path:` query
form avoids "the search.exclude_tags false-positive trap" — that claim is **wrong**, and the
correct rule is already documented in the same ecosystem:
`~/Mail/.claude/context/project/email/domain/wrapper-contracts.md:367-379` mandates
`--exclude=false` on any on-disk-vs-indexed audit, citing this exact 22-file Logos case.
`census.nix` violates its own repo's documented audit rule. (Fix is dotfiles-side and out of
scope here; the §5 redesign removes census from the launch path entirely, making the fix
non-blocking for this task.)

## 5. Recommended Redesign

### 5.1 Principles

1. **Gate the launch on index reconciliation only** — a completed foreground
   `notmuch new --no-hooks` (~0.2 s). Never on any mbsync exit code, and never on census.
2. **Open aerc immediately** after the reconcile; aerc is a notmuch reader with its own
   in-client sync affordance (`$` = `mail-sync gmail`, `~/.config/aerc/binds.conf:33`), so
   post-open index writes are already the sanctioned steady state.
3. **All server syncing goes through `mail-sync`** (the task-109 single choke point) and runs
   in the background, deduplicated with an in-flight guard. `mbsync -a` is deleted from the
   codebase (it is the forbidden form: fires `logos-labels` and redundant channels; see
   `mail-sync.nix:15-18,24-28`).
4. **A failing sync warns; it never blocks.** The duplicate-UID collision (out of scope,
   unrepaired) degrades `<leader>me` from "fresh mail" to "current index" — never to refusal.

### 5.2 Concrete sketch (`mail.lua` replacement logic)

```lua
-- Index-only reconcile: the ONLY launch gate. Never triggers preNew/mail-sync.
local function reconcile_index(cb)
  vim.fn.jobstart({ "notmuch", "new", "--no-hooks" }, {
    on_exit = function(_, code) cb(code == 0) end,
  })
end

-- One backgrounded, deduplicated sync pipeline shared by <leader>me (quiet)
-- and <leader>mN (loud). Hook-ful `notmuch new` IS the pipeline: its preNew
-- runs `mail-sync both` (flock-serialized mbsync gmail + logos + --no-hooks
-- reindex), then notmuch's own scan and postNew tagging run — sync, reindex,
-- and inbox/unread tagging in one serialized process, via the canonical
-- single choke point. Never `mbsync -a`.
local sync_in_flight = false
local function background_sync(loud)
  if sync_in_flight then
    if loud then vim.notify("Mail sync already running", vim.log.levels.INFO) end
    return
  end
  sync_in_flight = true
  if loud then vim.notify("Syncing all accounts (mail-sync both)...", vim.log.levels.INFO) end
  vim.fn.jobstart({ "notmuch", "new" }, {   -- hook-ful: preNew = mail-sync both
    on_exit = function(_, code)
      sync_in_flight = false
      if code == 0 then
        vim.notify("Mail sync + reindex complete", vim.log.levels.INFO)
      else
        vim.notify(
          "Background mail sync did not complete cleanly (aerc unaffected; "
            .. "index remains consistent). See `mail-sync` output / <leader>mN.",
          vim.log.levels.WARN
        )
      end
    end,
  })
end

-- <leader>me
reconcile_index(function(ok)
  if not ok then
    -- Rare (e.g. another writer holds the Xapian lock mid-write). Refusing here
    -- is correct and self-healing: retry after the writer finishes.
    vim.notify(
      "aerc launch deferred: notmuch reindex failed (another indexer may be "
        .. "mid-write). Retry <leader>me in a moment.",
      vim.log.levels.WARN
    )
    return
  end
  open_aerc()            -- unchanged toggleterm float
  background_sync(false) -- deferred server sync; warns on failure, never blocks
end)

-- <leader>mN: explicit full sync, same pipeline, loud.
-- (desc: "Sync all accounts (mail-sync both + notmuch)")
background_sync(true)
```

### 5.3 Why this preserves the Xapian reader/writer safety invariant

The decision record's contract (`index-architecture.md:76-92`) requires that the *barrier*
serialize a completed reconcile before a dependent reader opens, because a reader racing a
mid-rewrite index is a second failure mode beyond staleness. The redesign keeps exactly that:
the foreground `notmuch new --no-hooks` runs **to completion, under notmuch's own lock,
before `open_aerc()`** — index-vs-disk agreement at open is what prevents "could not get
MessageInfo" (stale index entries pointing at renamed/moved files). What changes is only the
*scope* of the barrier: mbsync is not, and never was, load-bearing for read-safety — it only
changes what is on disk *before* the reconcile snapshot. Post-open index writes (the
background pipeline) are equivalent to aerc's own sanctioned `$` keybind flow
(`index-architecture.md:90-92` explicitly blesses in-client sync-while-open); notmuch/Xapian
single-writer-multi-reader semantics make concurrent aerc reads see either the old or new
committed revision. The Debian #843127 delivery-during-scan race is also respected: within the
background pipeline, mbsync delivery strictly precedes the reindex (serialized inside one
process via preNew), and any files delivered *during* the foreground gate's 0.2 s scan by an
overlapping himalaya autosync are picked up by the background pass — a staleness-of-content
matter, never an open-safety one.

**Required doc amendment** (part of implementation, in ~/Mail): update
`index-architecture.md`'s "Authoritative Launch Gate" section — the gate marker becomes
"foreground index reconcile completed", explicitly decoupled from mbsync exit codes and from
census; and the Three-Mechanism Barrier text still describes preNew as `mbsync -a`
(`index-architecture.md:62-63`), which is stale (it is `mail-sync both` since dotfiles
task 109), as is its description of aerc's `$` as `mbsync -a && notmuch new`
(`index-architecture.md:90`; live binds.conf says `mail-sync gmail`).

### 5.5 Division of labor (answers seed open question 4)

- **mail.lua** owns: the 0.2 s launch gate, the aerc terminal, the in-flight guard, and
  notifications. It invokes only `notmuch new [--no-hooks]` (index-only) and — indirectly via
  the hook — `mail-sync`. It never invokes `mbsync` directly in any form.
- **dotfiles `mail-sync`** owns: all mbsync policy — group scoping, flock serialization,
  duplicate-UID/auth diagnostics, the internal reindex. (Its `--no-wait` flag is available if
  mail.lua ever wants fail-fast lock behavior instead of the hook path; not needed in the
  recommended variant since the pipeline is backgrounded and deduplicated caller-side.)
- **dotfiles `census.nix`** (companion follow-up task, not a blocker): fix the freshness
  computation to use `--exclude=false` on the indexed-files side per
  `wrapper-contracts.md:377-379`, and correct the `census.nix:55-58` comment. This restores
  census as a trustworthy signal for the `/email` wrappers — its actual consumer — regardless
  of the launch-gate redesign.

## 6. What Could NOT Be Verified (and follow-up needs)

1. **Wall-clock of the mbsync layers** — running `mbsync -a`/`mail-sync both` was explicitly
   forbidden (slow, currently failing). The minutes-scale attribution in §2 is an estimate
   from channel topology (15-channel `-a`, 64k All_Mail near-side load, serial dual-account
   repeat). A follow-up could instrument the *background* pipeline's duration in the redesign's
   `on_exit` (harmless telemetry) rather than pre-measuring.
2. **Which himalaya timer instance fired in the user's observed log** (startup-delay vs 15-min
   interval vs sidebar `s`) — causal independence from `<leader>me` is code-proven, but the
   specific observed firing cannot be reconstructed post-hoc. Irrelevant to the design.
3. **Whether `ui.auto_sync_interval` is overridden anywhere** — no override was found under
   `lua/neotex/plugins/tools/himalaya/` (grep for `auto_sync_interval` shows only the
   `manager.lua:329` default read); a user-config override elsewhere was not exhaustively ruled
   out. Does not affect the redesign.
4. **aerc's behavior on Xapian `DatabaseModified` during background reindex** — asserted from
   notmuch/Xapian single-writer-multi-reader semantics and the sanctioned `$`-keybind
   precedent, not from aerc source. If paranoid, a follow-up could soak-test: open aerc via
   redesigned `<leader>me`, run `mail-sync both` repeatedly, watch for MessageInfo errors.
5. **`notmuch new --no-hooks` failure modes under a held write lock** — the "fails fast, retry"
   branch in §5.2 assumes notmuch errors out rather than deadlocking when another writer holds
   the lock; notmuch does serialize via its own locking, and the gate's `code ~= 0` branch
   handles either way, but the exact UX of that rare branch should be confirmed during
   implementation testing.
