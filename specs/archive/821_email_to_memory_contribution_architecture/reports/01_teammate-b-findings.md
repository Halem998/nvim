# Research Report: Task #821 (Teammate B — Alternatives & Prior Art)

**Task**: 821 - Research and design email-to-memory contribution architecture
**Role**: Alternatives researcher (parallel to primary researcher's recommended-approach track)
**Sources/Inputs**: Codebase (`skill-email-cleanup/SKILL.md`, `skill-memory/SKILL.md`, memory `manifest.json`, `skill-todo/SKILL.md`, `memory-harvest.sh`, email `manifest.json`), WebSearch (July 2026)

---

## Key Findings

1. **Three capture points are all mechanically viable but couple to different failure modes.** The in-skill harvest (A) is the only one that reuses the exact moment the approved manifest + sha256 already exist, but it forces `skill-email-cleanup` to either duplicate or import memory-domain logic, and the email extension's `manifest.json` currently declares no dependency on the memory extension (`"dependencies": ["core"]`), so graceful degradation must be designed in, not assumed.
2. **The lifecycle-hook mechanism (B) is schema-ready but unused.** Both `email/manifest.json` and `memory/manifest.json` have an empty top-level `"hooks": {}` object — the documented lifecycle-hook slot (preflight/context_injection/verification/postflight via `skill-base.sh`) has no current implementation to point to as prior art *within this repo*. This is the cleanest separation of concerns on paper but is the least-proven path here — do not assume the invocation contract (args, failure isolation) already works; it needs verification as part of implementation. Note the distinct, already-used `provides.hooks: ["mail-guard.sh"]` list in email's manifest is a **file-copy-target** hook (a guard script), not a lifecycle hook — the two `hooks` concepts share a name but not a mechanism.
3. **`skill-todo`'s harvest pattern (C) does not map cleanly onto `/email` because ad-hoc email sessions have no task/state.json entry.** `memory-harvest.sh` reads `memory_candidates` off a `project_number` in `specs/state.json`; `/email` runs are direct-execution, not task-tracked. Reusing this pattern requires inventing an equivalent per-session ledger — the dedup/tier/confidence-threshold logic transfers, but the storage substrate does not.
4. **Sender/domain identity is a natural exact key, not a fuzzy-match problem** — but `skill-memory`'s existing Memory Search step is built entirely around keyword-overlap scoring (>60% UPDATE / 30-60% EXTEND / <30% CREATE) for unstructured content. Reusing it as-is for email preferences means either (a) accepting fuzzy-match risk on what should be a deterministic `topic == "email/senders/{addr}"` or `"email/domains/{domain}"` lookup, or (b) adding a deterministic-key short-circuit before the fuzzy path — a small but real deviation from the existing skill-memory contract.
5. **Vault-health scoring cross-contamination is a concrete risk for the vault-memory storage option.** `skill-memory`'s distill scoring treats `retrieval_count == 0 AND age > 30d` as a zero-retrieval purge signal. Email-preference memories are read by `skill-email-cleanup`, not by `/research`/`/plan`/`/implement`'s `memory-retrieve.sh` path — if that read never increments `retrieval_count`/`last_retrieved`, these memories will look "unhealthy" and become `/distill --purge` candidates despite being in active use. This must be resolved (either exempt by topic-prefix, or make the email-side read call the same increment path) regardless of which capture point is chosen.
6. **Prior art converges on three transferable mechanics**: (a) confidence-as-count-not-preference (implicit-feedback framing: a single decision is a weak signal, a recurring pattern is a strong one — directly supports `min()`-style or count-ratio confidence rather than last-write-wins), (b) temporal decay/hybrid weighting so old confirmed decisions don't permanently outweigh a sender's recent behavior change, and (c) explicit conflict-resolution-over-deletion (Mem0-style: mark superseded relations invalid rather than physically overwritten, preserving "why did this change" history) — which maps naturally onto the vault's existing UPDATE-operation `## History` section.

## Recommended Approach (Comparison Tables)

### Capture-Point Alternatives

| | (A) In-skill harvest step | (B) Memory-extension lifecycle hook | (C) Postflight/todo-style harvest |
|---|---|---|---|
| **Where it fires** | Inside `skill-email-cleanup`, right after Stage 5 Execute / Stage 6 Verify, in the same invocation | `postflight` lifecycle stage via `skill-base.sh`, decoupled script | After a cleanup session, via a new harvest step modeled on `memory-harvest.sh` (batch, possibly deferred) |
| **Reuses existing mechanism?** | Partial — reuses the approved-manifest moment, but no existing in-skill-to-memory call exists today | Schema exists (`hooks: {}`) but is empty in both manifests — unproven in this repo | Strong structural reuse of `memory-harvest.sh`'s dedup/tier/confidence logic, but its input source (`state.json` `memory_candidates` keyed by `project_number`) doesn't exist for `/email` |
| **Coupling** | Tight — email skill must know memory schema/dedup, or call into skill-memory logic directly | Loosest — data-only handoff (manifest diff -> hook script), extension-agnostic | Medium — decoupled from cleanup's internals, but needs a new ledger file since there's no task number |
| **Dependency handling** | Needs explicit graceful-degradation check (memory extension not loaded) since email manifest declares no dependency on it | Naturally optional — hook simply doesn't fire / is a no-op if memory extension absent | Same graceful-degradation need as (A), plus needs the new ledger regardless |
| **Failure isolation** | A crash in the harvest step risks affecting the (mutation-carrying) cleanup flow unless carefully sequenced after Stage 6 | Best isolation *if* `skill-base.sh` guarantees non-fatal hook failures (needs verification, not confirmed by reading alone) | Good isolation if async/deferred; but deferred = "never runs" risk (see Prior Art #6) |
| **Batches naturally to sender/domain?** | Yes — `--all` mode's Stage 2.5 bucket review already groups by sender/domain; default mode is per-message and needs an extra grouping step | Yes, if hook receives the same manifest/bucket data | Yes — this is exactly what `--all` mode's bucket approval already aggregates |
| **Implementation cost** | Low-medium (new stage in an existing skill) | Medium-high (first real use of an unproven mechanism) | Medium (new ledger + adapted harvest script) |
| **Best fit given `--all` bucket approval already exists** | Good | Good (if wired to same bucket data) | Good |

### Storage Alternatives

| | (1) Vault memories via `/learn`'s skill-memory API | (2) Dedicated structured store (JSONL/sqlite) | (3) notmuch tags as source of truth, memory as derived cache |
|---|---|---|---|
| **Realizes "one evolving memory per sender/domain, UPDATE/EXTEND"?** | Directly — this is exactly what UPDATE/EXTEND operations do; needs deterministic topic-key lookup instead of fuzzy overlap for correctness | Yes for the counters, but loses the human-readable "evolving narrative" framing (no natural `## History`/`## Extension` prose) | Only if paired with (1) or (2) for the narrative artifact — tags alone give counts, not "why" |
| **Reuses existing infra** | Maximal — markdown format, `memory-index.json`, CREATE/UPDATE/EXTEND, git-tracked postflight commit all already exist | Minimal — no sqlite/JSONL secondary store or sub-index precedent exists today in the memory system; new subsystem | Maximal on the notmuch side (`email-classify` already writes durable `+proposed-*` tags per wrapper-contracts.md §10); zero on the memory side |
| **Aggregation math (counts, ratios, confidence)** | Awkward — frontmatter has no native counter fields; would need ad hoc fields alongside `retrieval_count`/`token_count` | Natural — rows/counters are the native representation | Natural for raw counts (`notmuch count tag:proposed-delete and from:X`), but is local-machine-only |
| **Vault-health scoring interaction** | Real risk (see Key Finding #5) — needs exemption or retrieval-increment fix | None — outside `.memory/10-Memories/`, not subject to `/distill` | None directly, but if it becomes the *only* store, there's no vault entry to score at all |
| **Portability / durability** | Git-tracked, portable across machines | Git-trackable if plain JSONL; less so if sqlite (binary diffs) | Local-machine notmuch DB only — not portable, not git-tracked |
| **Wrapper-only constraint interaction** | N/A — lives outside `skill-email-cleanup` | N/A | Aggregation queries would need either a new sixth read-only wrapper binary (if done inside `skill-email-cleanup`) or a separate non-cleanup component not bound by the five-binaries constraint |
| **Implementation cost** | Low (schema/topic convention change + one dedup-path fix) | High (new subsystem, new index) | Medium if used only as a reconciliation/audit source; high if used as primary aggregation query path per invocation |

**Given the user's already-made decision** (aggregated, evolving, UPDATE/EXTEND memories), storage option (1) is structurally the correct fit and requires the least new machinery — but it is not risk-free: the deterministic-key dedup deviation and the vault-health zero-retrieval exemption are both required fixes, not optional polish. Option (3) is best framed as a complementary reconciliation source (notmuch tags never lie about what was actually decided) rather than a replacement for a vault entry. Option (2) should be considered only if counter-precision needs (e.g., decayed confidence scores recomputed on every read) turn out to exceed what frontmatter fields can reasonably hold — treat it as a future escalation path, not a starting design.

## Evidence/Examples

### Codebase grounding

- `skill-email-cleanup/SKILL.md`: five wrapper binaries only, mandatory human review gate (Stage 3 default / Stage 2.5 `--all`), approved-manifest + sha256 confirm pattern (Stage 4), bucket construction "group deduplicated accumulator records by sender domain; for freemail/shared domains ... bucket by the full sender address instead" and per-bucket `min()` confidence rollup — this bucket-grouping logic is a ready-made template for "sender/domain aggregation."
- `skill-memory/SKILL.md`: Classification Thresholds table (>60% UPDATE / 30–60% EXTEND / <30% CREATE, keyword-overlap based); mandatory `AskUserQuestion` stop per segment ("Do NOT write memory files without explicit user confirmation per segment") — this per-segment interactive gate is designed for open-ended `/learn` content and is friction that a confirmed-decision-driven pipeline (the user already approved the action in the email review gate) should probably bypass or batch, not repeat.
- `.memory` distill scoring: Zero-Retrieval Penalty = "if `retrieval_count == 0 AND days_since_created > 30`: 1.0" — directly supports Key Finding #5.
- `memory/manifest.json` and email `manifest.json`: both `"hooks": {}` — confirms the lifecycle-hook slot is schema-present but empty/unused everywhere in this repo today.
- `skill-todo/SKILL.md` Stage 7 (~181): `memory_candidates` collection, dedup via keyword-overlap against `memory-index.json` (>90% NOOP / >60% UPDATE / else CREATE), tiered `AskUserQuestion`. `memory-harvest.sh`: reads `.active_projects[] | select(.project_number == $task) | .memory_candidates`, filters `confidence >= 0.7`. Confirms Key Finding #3 — the input keys off `project_number`, which `/email` sessions do not have.
- `email/manifest.json`: `"dependencies": ["core"]` (no `memory` dependency declared) and `"provides": {"hooks": ["mail-guard.sh"]}` — the `provides.hooks` file-copy-target list is distinct from the top-level lifecycle `hooks` object per CLAUDE.md's own documented distinction.

### Prior art (WebSearch, July 2026)

- LLM agent memory surveys describe memory construction as "deterministic," "LLM-mediated," or "agentic" write paths, and frameworks like **Mem0** perform conflict detection with an "Update Resolver" that marks superseded relations invalid rather than deleting them, explicitly to preserve temporal/history reasoning — directly analogous to the vault's UPDATE operation's `## History` section. Mem0's extraction pipeline dedups via hashing for exact duplicates only, explicitly noting this doesn't catch semantically-similar-but-worded-differently facts (relevant caution for keyword-overlap dedup too). ([Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory](https://arxiv.org/html/2504.19413v1), [Mem0 — Overall Architecture and Principles](https://medium.com/@zeng.m.c22381/mem0-overall-architecture-and-principles-8edab6bc6dc4), [ADD-only architecture doesn't implement conflict resolution for semantically similar memories](https://github.com/mem0ai/mem0/issues/4896))
- Email spam/ham systems built around **per-sender/IP reputation aggregation** and **complaint feedback loops** (e.g., ISP feedback-loop services) that fold verified false positives/negatives back into future retraining — the general pattern of "aggregate signals per sender identity, retrain/update from confirmed labels" is exactly the shape task 821 wants for sender/domain memories. ([Machine learning for email spam filtering: review, approaches and open research problems](https://www.sciencedirect.com/science/article/pii/S2405844018353404), [Per-sender neural network classifiers for email authorship validation](https://arxiv.org/pdf/2509.00005), [Detecting Spammers via Aggregated Historical Data Set](https://arxiv.org/pdf/1205.1357))
- Recommender-systems literature on implicit feedback frames **repeat signals as confidence, not preference magnitude** — "a one-time event might be caused by various reasons ... a recurring event is more likely to reflect the user's opinion" — supporting a design where a single junk/keep decision for a sender should carry lower confidence than a pattern of repeated identical decisions, and where **temporal decay** balances short-term behavior shifts against long-term identity ("hybrid user profile updater ... dynamic weighting ... temporal decay functions to balance short-term responsiveness with long-term accuracy"). ([Modeling User Preferences in Recommender Systems](https://dl.acm.org/doi/10.1145/2512208), [An efficient system using implicit feedback and lifelong learning approach](https://link.springer.com/article/10.1007/s11227-022-04484-6))
- General LLM-agent-memory surveys confirm "procedural memory enables the assistant to learn user habits, while semantic memory stores general knowledge about the user's preferences" — supporting treating sender/domain email preferences as a distinct semantic-memory-like category, plausibly meriting its own topic namespace (e.g. `email/senders/*`, `email/domains/*`) separate from general project/coding memories, which also mitigates the retrieval-count cross-contamination risk (Key Finding #5) by making topic-prefix-based exemption/filtering natural. ([Memory Mechanisms in LLM Agents](https://www.emergentmind.com/topics/memory-mechanisms-in-llm-based-agents), [A Survey of Context Engineering for Large Language Models](https://arxiv.org/pdf/2507.13334))
