**Candidate name judgment**: `AMBIENT_BINDING_MISMATCH` vs. an "unreached observability marker" framing.
- Every one of the 13 existing table entries names the failure **mechanism**, never the specific motivating instance: `HOOK_REGEX_BOUNDARY_DEFECT` names "an unstated boundary assumption" (the mechanism), not "the digit-count quantifier bug" (the instance); `SESSION_LOCK_CONTENTION` names "a session-id keying mismatch" (mechanism), not "the batch-admission collision" (instance); `DEPLOY_ORPHAN_DRIFT` names "purely-additive deploy with no pruning" (mechanism), not "the stray index entry" (instance).
- The motivating case here is structurally: a downstream guard (`skill-base.sh`'s exit-6 annotation block) is keyed to reading an ambient/global shell variable (`TASK_DIR`) that only some callers happen to populate (set inside `skill_validate_input`, in the skill-context path; never set by `orchestrate-stage5-postflight.sh`, a bare script caller) — so the guard's condition silently evaluates false instead of erroring. That is an ambient-binding mismatch between caller and callee, and it is a general shape that could recur at any other guard keyed to an unexported convenience variable, not unique to this one incident.
- `AMBIENT_BINDING_MISMATCH` names that mechanism, reads correctly alongside the other 13 entries' naming style, and does not overlap `SESSION_LOCK_CONTENTION` (which is specifically about session-id lock keying, a narrower and different-shaped mismatch) or any other existing class.
- The competing "unreached observability marker" framing (something like `OBSERVABILITY_MARKER_UNREACHED`) names the **symptom** — a documented marker that never gets written — rather than the mechanism that causes it. It breaks the table's established naming convention and is less general (it describes this incident specifically, not the class of bugs that produce it).
- **Judgment: `AMBIENT_BINDING_MISMATCH` is recommended.** No detector needs to be wired for it at registration time — this matches the accepted precedent already set by `ARTIFACTS_MISSING_ON_SUCCESS`, `SESSION_LOCK_CONTENTION`, `HOOK_REGEX_BOUNDARY_DEFECT`, and `DEPLOY_ORPHAN_DRIFT`, all four of which are registered with "not currently computed anywhere."

### Part 2 — TASK_DIR binding defect

All specifics in the task description were re-confirmed against the current tree, with one caveat: `skill-base.sh` line numbers have already drifted by one line since the task description was written (its guard is now observed at line 537, not 536), consistent with the note that sibling tasks in this same batch are concurrently editing `skill-base.sh`. Findings below are anchored by surrounding text.

- `skill-base.sh`'s `skill_validate_input` function sets `TASK_DIR="specs/${PADDED_NUM}_${PROJECT_NAME}"` (in the block that also derives `TASK_TYPE`, `TASK_STATUS`, `PROJECT_NAME`, `DESCRIPTION`, `PADDED_NUM` from `state.json`, and exports all of them, including `TASK_DIR` and its absolute companion `TASK_DIR_ABS`). This only runs when a caller invokes `skill_validate_input`.
- `orchestrate-stage5-postflight.sh` binds the task directory only as a lowercase positional parameter, `task_dir="${4:-}"`, in its own arg-parsing preamble — it never sets, exports, or otherwise touches a variable named `TASK_DIR`. It calls `skill_postflight_update` at 3 sites (research, plan, implement branches), none of which forward `task_dir` in any form.
- `skill_postflight_update`'s exit-6 branch (fires when `update-task-status.sh`'s postflight call returns 6, the completion-deploy gate's refusal code) is guarded by `[[ -n "${TASK_DIR:-}" && -f "${TASK_DIR}/.return-meta.json" ]]`. Under `/orchestrate`, `TASK_DIR` is always unset at this point, so the guard is always false, and the `deploy_pending`/`deploy_pending_reason` annotation into `.return-meta.json` never runs — while the preceding `[deploy-check] deploy-pending: ...` stderr line still prints unconditionally, producing exactly the silent-annotation-loss symptom the task describes.
- `skill_postflight_update`'s signature is `task_number operation session_id status [phase_check_mode]` — 4 required positionals plus an already-optional 5th (`phase_check_mode`, empty-string default, forwarded to `update-task-status.sh` only when non-empty via an array-expansion pattern).

**Caller audit, re-confirmed against the current tree** (12 total `skill_postflight_update` call sites found repo-wide, all matching the task description's prior audit):
- Safe today (run inside skill context where `skill_validate_input` has already set `TASK_DIR` before the postflight call): `skill-planner/SKILL.md`, `skill-planner-hard/SKILL.md`, `skill-researcher/SKILL.md` (referenced in prose, no-op call not present but resume logic assumes the same context), `skill-team-research/SKILL.md`, `skill-team-plan/SKILL.md`, `skill-team-implement/SKILL.md`, `skill-web-research/SKILL.md`, `skill-web-implementation/SKILL.md`, `skill-epi-implement/SKILL.md`, `skill-epi-research/SKILL.md` (the epi skills live under `agent-system/extensions/epidemiology/`, not a directory literally named `epi/` — a path note for whoever edits next, matching the task description's own shorthand naming).
- Outlier: `orchestrate-stage5-postflight.sh`'s 3 call sites (research/plan/implement branches) — the only caller that invokes `skill_postflight_update` without first running through skill context.
- The coupling remains latent for any hypothetical future non-skill caller even after a fix targeted narrowly at `orchestrate-stage5-postflight.sh` — this is the argument in favor of option (b) over option (a), addressed below.

**Option (a) vs (b) judgment**:
- **Option (a)** — export `TASK_DIR` at the orchestrate caller before calling `skill_postflight_update` — is the smaller, more localized diff (touches only `orchestrate-stage5-postflight.sh`), but it satisfies the ambient-variable coupling rather than removing it: the guard in `skill-base.sh` continues to trust an unexported-by-default global, and the same silent-false failure mode is still one missed `export` away from recurring at the next non-skill caller (a future standalone script, a test harness, a different orchestration entry point).
- **Option (b)** — thread the task directory into `skill_postflight_update` as an explicit optional parameter — removes the ambient coupling at its root: the function no longer depends on an environment variable it does not itself require as an argument. Confirmed compatible with the existing positional contract: `phase_check_mode` is already the optional 5th argument (`local phase_check_mode="${5:-}"`), so a new 6th argument (e.g. `task_dir_override`, `local _td="${6:-${TASK_DIR:-}}"`) is purely additive — every existing 4-arg call (the majority of the 12 sites) and every existing 5-arg call (`orchestrate-stage5-postflight.sh`'s implement branch, which already passes `"warn"` as a 5th arg) continues to resolve `${6:-}` to empty and fall back to `${TASK_DIR:-}` exactly as today, unchanged byte-for-byte. Only `orchestrate-stage5-postflight.sh`'s 3 call sites need a new trailing `"$task_dir"` argument added; none of the other 11 call sites (9 distinct skill files, one of which — `skill-team-implement` — calls with a literal `"implemented"` status) need to change at all.
- **Judgment: option (b) is recommended**, matching the task description's own recommendation, for the reason stated above (removes the fragility rather than papering over it, at no additional cost to the other 11 callers).

**Existing reusable test fixture for the regression test**: `test-postflight-deploy-gate.sh` (a sibling file in the same `scripts/tests/` directory, not itself in this task's edit scope) already contains a complete, working fixture that drives `update-task-status.sh` to a genuine exit-6 refusal — its "Case 1: overlap + STALE" builds an isolated fixture repo (`build_fixture_repo`) plus a throwaway git repo standing in for the source store with a deliberately stale commit (`build_source_and_extensions`), producing the same `overlap + STALE` conditions the completion-deploy gate checks (modified_files overlapping `agent-system/extensions/**`, and `deploy_freshness_status` reporting `STALE`). The new regression test specified in the task (asserting `deploy_pending`/`deploy_pending_reason` land correctly) belongs one level up, in `test-skill-base-lifecycle.sh`'s existing "Group 4" section (`skill_preflight_update`/`skill_postflight_update` coverage, currently around lines 334-381) — it should call `skill_postflight_update` directly (not `update-task-status.sh`), reusing the same STALE-fixture construction technique, with `TASK_DIR` (or the new option-(b) parameter) pointing at a task directory that contains a `.return-meta.json`, then assert the file gains `deploy_pending: true` and a non-null `deploy_pending_reason` after the call. `test-skill-base-lifecycle.sh`'s own header comment (currently around line 25) already documents that `skill_preflight_update`/`skill_postflight_update` hardcode the bare relative path `.claude/scripts/update-task-status.sh` and therefore require the test to `cd` into a full isolated fixture repo rather than use the `SKILL_REPO_ROOT` override some other groups in the same file use — the new test must follow that same `cd`-into-fixture discipline.

## Decisions

- Recommend `AMBIENT_BINDING_MISMATCH` as the new class name over the "unreached observability marker" framing, on the grounds that it names the mechanism (matching the established convention of all 13 existing entries) rather than the symptom.
- Recommend option (b) — an additive 6th optional positional parameter to `skill_postflight_update` — over option (a) (exporting `TASK_DIR` at the caller), for the reason the task description itself gives: it removes the ambient-variable fragility rather than satisfying it for one caller while leaving it latent for the next.
- Recommend the new regression test live in `test-skill-base-lifecycle.sh`'s existing Group 4 (not a new file), reusing `test-postflight-deploy-gate.sh`'s STALE-fixture construction technique rather than reinventing it.
- Correction of record: the discrimination doc does not contain the literal word "thirteen" anywhere; the plan/implementation phase should not search for one to edit in place, but should add a new short paragraph following the doc's existing two-paragraph narration pattern (see Findings above) where a "thirteen" is newly introduced, not edited.
