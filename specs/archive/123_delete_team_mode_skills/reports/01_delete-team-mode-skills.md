### `--lit` wiring through Stage 3.6 Team Fan-Out

`agent-system/extensions/core/skills/skill-orchestrate/SKILL.md`:

- Stage 3.6 (`Team Fan-Out`, line 757) lists `lit_flag` among its documented inputs (line 774, sourced from Stage 1).
- The **spawn loop** (lines 813-834) is explicit: for **each tuple in `teammate_plan`** (i.e., per teammate, inside the loop), step 1 is "Run **Stage 3.5: Dispatch Prep** with `phase` (unchanged) and `hard_mode`/`clean_flag`/`lit_flag` passed through exactly as received by this stage." Stage 3.5 (line 597) is the single canonical copy of *both* memory-retrieval *and* literature-briefing resolution — it runs the full `lit-stage4a-flow.md` procedure (calling `literature-lit-flag-resolve.sh`, then branching to `literature-briefing-invoke.sh`) inline.
- Consequence: for a 3- or 4-teammate wave, the literature resolver and (when the directive requires it) the briefing-invoke script run **N times sequentially in the orchestrator's own execution**, not once. This is not an oversight — task 122's own research report (`specs/122_build_team_mode_fanout_stage/reports/01_team-fanout-stage-research.md`, Decision 5 and the Key Insights bullet at line 56) explicitly recommends and documents this as the design: *"Call Stage 3.5 per teammate dispatch, passing `hard_mode` through unchanged, so hard-mode contract injection and memory/`--lit` reach every teammate without new team-specific logic — this is what makes `--hard --team` composability... work for free."*
- **Whether the interactive directives can fire per teammate**: no. `SKILL.md` line 668-670 states that because `skill-orchestrate` always sets `orchestrator_mode: true`, the two interactive directives (`PROMPT_NEEDED`, and the interactive branch of `SPARSE_PROMPT_NEEDED`) are "unreachable" — the deterministic `[lit:auto]` autonomous fallback always applies instead. `lit-stage4a-flow.md` independently confirms this at the `AUTONOMOUS_GLOBAL` and `SPARSE_PROMPT_NEEDED` sections: both state "**MUST NOT call `AskUserQuestion`**" when `orchestrator_mode == "true"`. So the specific failure mode the acceptance criterion names — interactive resolution directives firing once per teammate — is categorically impossible today, independent of how many times Stage 3.5 runs, because `/orchestrate` never takes the interactive path at all.
- **What is NOT true**: the briefing is not "resolved ONCE by the dispatch-prep stage and injected into each teammate prompt." It is resolved independently by each teammate's own Stage 3.5 call. Each call should be deterministic and produce equivalent content (same `description`/query, same repo state, run serially before any Agent-tool dispatch — no concurrency/race risk), but the calls are redundant: up to 4x the subprocess overhead, and up to 4x any live corpus search that `AUTONOMOUS_GLOBAL`/`SPARSE_PROMPT_NEEDED` triggers via `literature-briefing-invoke.sh --global`.

**Assessment for the plan phase**: the acceptance criterion's named risk (repeated interactive prompting) does not exist in the current implementation and cannot be introduced by proceeding with the deletion — `orchestrator_mode` forecloses it structurally, with or without a refactor. Whether the "resolve once, not once per teammate" efficiency/consistency property is worth a Stage 3.6 refactor (hoist the lit-resolution portion of Stage 3.5 above the spawn loop, thread `lit_context` through each tuple's `delegation_extras` instead) before proceeding with deletion, or is accepted as-is (mirroring how `memory_context` already works identically, per-teammate, without objection), is a genuine judgment call this report surfaces but does not make.
