## Executive Summary

- **`lake build` confirmed to have no `-j`/`--jobs` flag** in this environment (Lake 5.0.0-src, both `lake build -j 2` and `lake -j 2 build` fail with `error: unknown short option '-j'`). The task's claim is verified, not assumed.
- **New nuance not in the task description**: the underlying `lean` binary *does* expose `-j, --threads=num` ("number of threads used to process lean files") in `lean --help`, but Lake does not forward any user flag to it — this is a dead end for a job-count lever via `lake build`, not a hidden escape hatch. Record it so a future reader doesn't rediscover it and get excited.
- **LEAN_NUM_THREADS experiment run and recorded** (task mandates this, not folklore): a controlled A/B test against a real Lean project (`~/Projects/BimodalLogic`, dependency fan-out of 49 files from one edited module) showed **identical max concurrent `lean --worker` descendant count (1) under `LEAN_NUM_THREADS=1` and `LEAN_NUM_THREADS=8`**. The inference in the task description is **falsified for this Lake/Lean version**: `LEAN_NUM_THREADS` does not govern Lake's build scheduling concurrency. A single `lean --worker` process's own thread count *did* respond to the ambient value (`Threads: 9` observed with `LEAN_NUM_THREADS=8` set), consistent with it being an **intra-process** elaboration thread-pool size, not a **job-count** lever. **Recommendation: do not ship LEAN_NUM_THREADS as a concurrency lever.**
- **`flock` and `systemd-run` are both present** at `/run/current-system/sw/bin/` on this machine, and `systemd-run --user --scope -p MemoryHigh=... -p MemoryMax=... -- <cmd>` works without root, propagates the wrapped command's exit code correctly, and is command-substitution-safe.
- **`/proc/pressure/memory` (PSI) is present and readable** on this machine — a materially better pressure signal than `free`'s "available" column, confirming the task's own caution about swap-blind availability checks.
- **A live, real example of the self-match/detection hazard was observed during testing**: four pre-existing `lean --worker` processes (ages 9,924s–41,292s, i.e. up to ~11.5 hours) were running in the same project directory the whole time — these are editor/LSP elaboration workers, not `lake build` processes, and a naive `pgrep lean` would have silently misattributed them to "an in-flight build." Any detection logic MUST discriminate `lake build`'s own descendant processes (or `--worker` invocations specifically tied to a build session) from long-lived LSP `--server`/`--worker` processes serving an editor.
- **Lake's staleness tracking is content-hash-based, not mtime-based.** `touch`ing a source file does **not** dirty the build — this matters for the guard's own testing/CI (`test-lake-build-guard.sh` must force a real content change, not a `touch`, to simulate a dirty tree) and for the "waiter's result predates the waiter's own edits" staleness policy the task calls out (a content-hash comparison, not an mtime comparison, is the right primitive to reuse from Lake's own model).
- No `latex-build-guard.sh` exists yet in the source tree — the sibling task has not landed. This task is the first of the "build guard" family in core; there are no existing conventions to match yet, so this script effectively **sets** the family precedent (subcommand shape, exit-code conventions, silent-when-no-conflict rule) rather than following one.
- The most directly reusable pattern in the codebase is `agent-system/extensions/core/scripts/claude-refresh.sh` (atomic single `ps` snapshot, narrow executable-identity predicate rather than argv-substring matching, `--force`-gated destructive action, SIGTERM→liveness-recheck→SIGKILL escalation) — read in full below.

## Findings

### Codebase Patterns

**`agent-system/extensions/core/scripts/claude-refresh.sh`** (406 lines) — the task explicitly names this as the reusable pattern to read first, and it earns that billing:
- Takes **one atomic `ps -eo pid,ppid,uid,tty,etimes,rss,comm,cgroup:200,args` snapshot** per invocation; every subsequent decision reads from that snapshot, never re-queries a candidate PID. This eliminates the TOCTOU window a naive "check then act" detector would have.
- Candidacy is gated on **`comm` (kernel executable identity)**, never an argv substring — this is exactly the discipline needed here, since `pgrep -f 'lake build'` is explicitly flagged in the task as vulnerable to the same trap that bit a companion task's `pgrep -af latexmk` (matched the task-creating agent's own bash wrapper because its argv merely *contained* the string).
- Defense-in-depth exclusions: system-slice cgroup, non-current-UID ownership, live-inhibitor-target liveness check (the one predicate that legitimately re-checks liveness, and only of a *different* PID than the candidate, so it introduces no snapshot-staleness race).
- `--force`-gated destructive action; default/`--dry-run` mode only reports.
- Escalation: `kill -15` → `sleep` → `kill -0` liveness recheck → `kill -9`.
- Fails loudly (exit 1) rather than silently degrading if `ps` doesn't support the `cgroup` column, rather than falling back to an unsafe argv match.

Directly transferable to `lake-build-guard.sh`: the single-snapshot discipline (for the status/detect subcommand), the executable-identity-over-argv-substring principle applied to distinguishing a genuine `lake build` (or its `lean --worker` descendants) from an unrelated `lean --worker`/`lean --server` LSP process, and the loud-refusal-over-silent-fallback posture when a required capability (`flock`, `systemd-run`, PSI) is missing.

**`agent-system/extensions/core/scripts/deploy-root-guard.sh`** — smaller, different concern (refuses to run from the source-store tree vs. a deployed `.claude/scripts/` tree), but shows the repo's established idiom for "fail loudly with an actionable message" rather than silently doing the wrong thing under a wrong assumption. Not directly needed for `lake-build-guard.sh` (which resolves paths relative to a Lean project root, not the agent-system deploy tree), but worth matching tone in comments/messages.

**`agent-system/extensions/lean/scripts/lean-sorry-census.sh`** (line ~181) and **`agent-system/extensions/lean/skills/skill-lake-repair/SKILL.md`** (Step 4) both capture builds synchronously via `BUILD_OUTPUT="$(lake build 2>&1)"` / `build_output=$(lake build 2>&1)`. These are the two concrete, named call sites the task's "command-substitution compatibility" requirement targets. A guard invoked as `lake-build-guard.sh build 2>&1` from inside a `$(...)` must: (a) still emit the underlying build's real stdout+stderr to its own stdout/stderr so the caller's capture is unchanged in content, and (b) still exit with the underlying build's real exit status (verified below that `systemd-run --scope` propagates a wrapped command's exit code correctly, so this composes cleanly with cgroup wrapping too).

**Test convention** (`agent-system/extensions/core/scripts/tests/`, 36 existing suites, e.g. `test-claude-refresh-matcher.sh`): `pass()`/`fail()`/`info()` helpers with `PASSED`/`FAILED` integer counters, `set -uo pipefail` (deliberately not `-e`, so the suite keeps running and reports a complete summary rather than aborting at the first failure), a `mktemp -d` workdir with a `trap EXIT` cleanup, and — where a script under test is meant to be both sourced (for direct predicate calls) and executed (`main`) — a `BASH_SOURCE[0] == $0` dual-mode guard at the bottom (see `claude-refresh.sh`'s final `if [[ "${BASH_SOURCE[0]}" == "${0}" ]]; then main "$@"; fi`). `run-all.sh` **auto-discovers** `test-*.sh` under `scripts/tests/` (and flat `scripts/test-*.sh`) — no manual registration is needed beyond the file existing with its exec bit set and (for deployment) the manifest entry. Loud-skip discipline: a non-executable suite is reported as `[SKIP]`, never silently dropped; zero discovered suites is itself a harness failure.

**`manifest.json`'s `provides.scripts` array** (131 entries currently — the task description's figure of 126 is stale but the shape is unchanged) is a flat, alphabetically-sorted array of relative path strings (`lib/*.sh` and `lint/*.sh` sort by their literal prefixed string, not specially). `lake-build-guard.sh` sorts alphabetically between `issue-grouping.sh` and `lib/common.sh` (`lake` < `lib` at the second character, `a` < `i`); its test entry `tests/test-lake-build-guard.sh` sorts among the existing `tests/test-*.sh` block alphabetically by name.

**No `latex-build-guard.sh` anywhere in the tree** (`agent-system/**`) — confirmed via search. The sibling task the task description references as a coherence target has not landed. There is therefore no existing "guard script family" convention to align with from that direction; this script is free (and, per the task text, obligated: "If the sibling lands first, follow its conventions rather than inventing new ones") to set a clean precedent — subcommand shape (a `build`/wrap mode plus a separable `status`/detect mode), exit-code conventions, and the **silent-when-no-conflict rule** (no stdout when nothing is wrong, since this runs on every build) should all be designed as if a LaTeX sibling will imitate them later.

**LEAN_NUM_THREADS controlled experiment (task-mandated, run and recorded):**

Setup: `~/Projects/BimodalLogic` (688 non-`.lake` `.lean` files, Lake 5.0.0-src / elan toolchain `leanprover/lean4:v4.33.0-rc1`, already fully built). `FormalSystem/Syntax/Formula.lean` has 49 dependent files. **Ambient `LEAN_NUM_THREADS=8` is set globally for this user** via `~/.config/fish/config.fish:26` (`set -gx LEAN_NUM_THREADS 8`) — this is itself worth recording, since a guard script that reads or overrides this variable needs to know it may already be set ambiently on deployment machines, not merely by the guard itself.

Method: appended a one-line comment to `Formula.lean` (a genuine content change — see the mtime-vs-hash finding above for why a `touch` would not have worked), launched `LEAN_NUM_THREADS=1 lake build` under `setsid`, and polled a process-tree walk (`pgrep -P` recursively from the launching shell PID, filtering strictly on `comm == lean` among *descendants only*) every 0.2s to find the maximum concurrent count — deliberately excluding `pgrep -x lean`'s global process-table view, because that view was contaminated by four pre-existing, long-running `lean --worker`/`lean --server` processes from an unrelated editor/LSP session in the same project directory (ages 9,924s–41,292s at observation time — up to ~11.5 hours old). This contamination is itself a live, concrete instance of exactly the self-match/detection hazard the task calls out for the `pgrep -f 'lake build'` case; discriminating build-owned descendants from ambient LSP workers proved to be a real, not hypothetical, requirement even for measurement, let alone for the shipped detector.

Result: **max concurrent descendant `lean` processes = 1** with `LEAN_NUM_THREADS=1`, and **max concurrent descendant `lean` processes = 1** with `LEAN_NUM_THREADS=8` (repeated on a fresh edit to rule out caching). Identical outcome under the only variable changed. Separately, a single `lean --worker` process's own thread count *did* vary with the ambient value (`Threads: 9` in `/proc/<pid>/status` observed with `LEAN_NUM_THREADS=8` in its environment) — consistent with the variable controlling **intra-process** elaboration parallelism (Lean's own internal thread pool for one file's elaboration), not the **number of files Lake schedules concurrently**.

Caveat, stated plainly per the task's own standard for this section: this specific edit's dependent fan-out may have had a narrow/chained true-parallelism ceiling (a mostly-sequential import chain among the 49 dependents), so "max observed = 1" is not by itself proof Lake never runs `lean` workers concurrently — the full from-scratch build's "2493 jobs" completing in a small fraction of what 2493 serial single-file elaborations would take is separate evidence Lake *does* parallelize when the module graph has width. What the controlled A/B *does* establish, because it held the module-graph/fan-out constant and varied only `LEAN_NUM_THREADS`, is that **this variable did not change the observed concurrency at all** — a genuine job-count lever would be expected to move that number between the two runs. **Conclusion for the deliverable: treat LEAN_NUM_THREADS as unverified-and-now-falsified; do not ship it as a concurrency control. If a future, wider-fan-out re-test on a different project ever shows a real effect, that would need its own fresh, recorded experiment before reversing this conclusion — don't take this report's caveat as license to ship the lever "just in case."**

### Recommendations

1. **Lock derivation**: resolve the Lean project root by walking up from `$PWD` (or an explicit `--dir`/`-C`-style argument, matching `lake`'s own `--dir, -d=file` convention) looking for `lakefile.lean` or `lakefile.toml`, then derive the flock lock path from that root's resolved `.lake` directory (e.g. `<root>/.lake/build-guard.lock`). Do not use `git rev-parse --show-toplevel` — a Lean package can be a subdirectory of a larger repo (this machine has exactly that shape: `Logos/Theory`, `Logos/Hardware`, `Logos/sparkle` each have their own `lakefile.lean` nested under one `Logos` git repo), so a git-root-based lock would over-serialize unrelated packages sharing one repo.
2. **Result sharing / staleness policy**: since Lake's own staleness tracking is content-hash-based (not mtime), reuse the same discriminator for the guard's "is the in-flight/most-recent build's result still valid for me" check rather than inventing an independent mtime-based staleness check that Lake itself would disagree with. A cheap, low-risk approach: record the build's own exit status/log plus a marker (e.g. the mtime *and* a quick tree-content fingerprint, or simply re-running `lake build` after acquiring the lock relying on Lake's own no-op-when-clean fast path) so a "share the result" decision never returns a result Lake itself would consider stale. Explicitly design and record (per the task's requirement) how an abandoned lock (killed session) is distinguished from a legitimately in-flight build — `flock`'s own semantics (the lock is released automatically on process exit, including a killed process) make this largely free: a stale lock file with no live holder is simply immediately acquirable, no separate PID-liveness bookkeeping needed, provided the lock is a `flock`-held file descriptor rather than a hand-rolled PID file.
3. **Cgroup bounding**: `systemd-run --user --scope -p MemoryHigh=<v> -p MemoryMax=<v> -- <build cmd>` is confirmed to work, propagate exit codes, and require no root/extra delegation setup on this machine. Probe availability with `command -v systemd-run` plus a cheap real invocation (e.g. wrapping `true`) rather than assuming presence; degrade to an unbounded build with a visible (stderr) notice on failure, per the task's explicit requirement. Derive `MemoryHigh`/`MemoryMax` from available memory (e.g. a fraction of `MemTotal`/`MemAvailable` from `/proc/meminfo`) or an explicit override flag/env var — never hardcode a byte value, since the task explicitly warns the script deploys to ~10 repositories with different memory profiles.
4. **RAM/PSI preflight**: prefer `/proc/pressure/memory`'s `some avg10`/`full avg10` fields (confirmed present and parseable on this machine) combined with swap-in-use from `/proc/meminfo` (`SwapTotal` − `SwapFree`) over a bare "available" check, matching the task's own diagnosis of why the originating incident (3.1GB available, 29GB swap in use) went undetected by a naive available-memory check.
5. **LEAN_NUM_THREADS**: **do not ship as a concurrency lever** — the controlled experiment falsified the inference in this environment. If it is surfaced at all, document it accurately as an intra-process elaboration-thread-count knob, unrelated to build job scheduling, and do not present it as a `-j` substitute.
6. **Detection safety**: match on process identity (resolved executable path / `comm`, optionally combined with checking the process's cwd or an argv path component that names *this* project's root) the same way `claude-refresh.sh` matches on `comm` rather than an argv substring — and explicitly exclude the guard's own ancestry (mirroring `claude-refresh.sh`'s zero-query `$$`/`$PPID` self-exclusion). Because this machine demonstrably has long-lived `lean --worker`/`lean --server` LSP processes coexisting with `lake build` invocations in the same project directory, any detector must not conflate the two — filtering to descendants of a tracked `lake build` invocation (as this research's own experiment script did) or to processes whose argv is specifically `lean --worker ... file://<root>/...` **launched after the guard's own lock acquisition timestamp** are both viable discriminators; a bare `pgrep lean` or `pgrep -f 'lake build'` is not.
7. **Command-substitution compatibility**: verify the shipped script never backgrounds itself in a way that detaches its own stdout/stderr from the caller (e.g. no un-waited `&` on the build invocation itself) — a plain `flock <lock> -c '<build+capture>'` or `flock <fd>` held for the duration of a foreground `lake build` composes correctly inside `$(...)`, matching the pattern already proven safe today by `lean-sorry-census.sh`'s and `skill-lake-repair`'s `$(lake build 2>&1)` call sites.
8. **Silent-when-no-conflict rule**: since this script is meant to run on every build (per the acceptance criteria), the "no output, exit 0" path when no conflict/pressure/memory issue exists must be tested explicitly and treated as a first-class behavior, not an incidental side effect — this is exactly the kind of thing `test-lake-build-guard.sh` should assert first.

## Decisions

- Treat `LEAN_NUM_THREADS` as a falsified concurrency lever for this deliverable; the planner/implementer should not spend design effort making it configurable as a job-count knob.
- Lock/result-sharing design should be anchored on a `lakefile.lean`/`lakefile.toml` directory walk-up, not `git rev-parse`, given confirmed multi-package-per-repo layouts on this machine.
- Cgroup bounding and the RAM preflight are both confirmed feasible with tools already present (`systemd-run --user --scope`, `/proc/pressure/memory`) — no additional dependency research is needed before planning.

## Risks & Mitigations

- **Risk**: a future re-test on a wider-fan-out module graph could show `LEAN_NUM_THREADS` *does* affect concurrency in some circumstance this experiment didn't reach. **Mitigation**: this report's conclusion is scoped to "do not ship it now, on this evidence" — a planner/implementer who wants to revisit it should run a fresh, recorded experiment on a wider-fan-out target before reversing course, not silently trust folklore either way.
- **Risk**: the LSP-worker contamination observed here (up to ~11.5-hour-old `lean --worker` processes) means a naive future test of the guard itself (in CI or locally) could similarly misattribute unrelated long-lived processes as "the guard's own build" if the test fixture doesn't isolate its process-tree walk. **Mitigation**: `test-lake-build-guard.sh` should use the same descendant-of-launcher-PID discrimination approach used in this research, or a disposable/synthetic Lean project fixture with no ambient LSP activity, rather than asserting against a bare `pgrep`.
- **Risk**: `systemd-run --user --scope` cgroup delegation, while confirmed on this machine, is not guaranteed on every one of the ~10 deployment repositories/machines. **Mitigation**: task already requires graceful degradation with a visible notice; this is a design requirement, not new information, but this research confirms the "requires no additional root/session setup" happy path is real on at least one representative machine, so the failure mode to design for is genuinely "missing/restricted," not "always broken."
