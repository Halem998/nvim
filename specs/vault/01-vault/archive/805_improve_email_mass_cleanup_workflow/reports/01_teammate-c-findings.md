# Research Report: Task #805 — Teammate C (Critic) Findings

**Task**: `805 - Improve email/ extension's mass-cleanup workflow for an entire mailbox`
**Role**: Teammate C — Critic (gap/risk/assumption analysis; no design proposal)
**Sources/Inputs**: `.claude/extensions/email/**` (this repo), `specs/803_email_claude_code_extension/reports/02_authoring-contract-verification.md`, commit `51bfda974`, and — critically — the live cross-repo source of truth `~/.dotfiles/modules/home/email/agent-tools.nix` (the frozen, as-built wrapper binaries task 805 references only by name).

## Key Findings

### P0 — The task's own mechanism description contradicts the as-built wrapper

**F1. `email-*-confirmed --execute` does not auto-chunk into ≤50 batches — it hard-refuses over the cap.** Task 805's item (2) describes "a batch-drain loop that runs `email-*-confirmed --execute` in repeated <=50 batches." The as-built `enforce_batch_size()` function does the opposite: if the approved manifest contains **more than 50** pending IDs for an action, the wrapper prints `"ERROR: N '<action>' ID(s) in manifest exceeds MAX_BATCH_SIZE=50 — split required"` and exits 1 — it never processes a partial batch and leaves the remainder. This means "loop, calling execute repeatedly against the same approved manifest" (the natural reading of the task description) simply does not work. The skill itself must pre-split the approved manifest into ≤50-ID **sub-manifests**, computing and passing a distinct sha256 (`--confirm-manifest`) for each. This is a materially different, much heavier piece of new orchestration logic than "loop the execute call," and it is not mentioned anywhere in the task description, the SKILL.md, or wrapper-contracts.md.

**F2. `PLAN_EXPIRY_DAYS=7` is enforced against raw filesystem mtime of the manifest file, not an approval timestamp.** `MTIME=$(stat -c %Y "$MANIFEST_FILE")` — plain `stat`. Combined with F1, splitting a 64k-message approved manifest into ~1,280 sub-manifest files means each split file gets a **fresh mtime at split time**, resetting its own 7-day staleness clock, unless the split step deliberately preserves the original approval's mtime (e.g. `touch -r original split-N`). Neither behavior is specified by the task:
- If splits inherit a fresh mtime, the "re-approve within 7 days" staleness guard the contract was built to enforce is silently defeated for exactly the highest-blast-radius scenario (a 64k-message drain) — the case it should protect hardest.
- If splits must inherit the original mtime, then the entire 64k drain (however many days a human takes to work through review/execute across multiple sessions) must complete within 7 days of the **original** approval or every remaining un-executed split silently starts failing with "manifest is N day(s) old — refusing to mutate," and there is no design in the task for detecting that a partial drain died mid-way and needs a residual-only re-approval flow.

**F3. `email-classify` itself is capped and paginated exactly like the mutation binaries — the task only designs a loop for the mutation side.** `email-classify`'s own `--limit` also defaults to `MAX_BATCH_SIZE=50` (`LIMIT="$MAX_BATCH_SIZE"`), and when the query matches more messages than the limit it logs `"NOTE: query matched N message(s); processing the first LIMIT... Re-run with a narrower QUERY or --limit to cover the remainder."` Classify's own limit is *not* hard-enforced the way `enforce_batch_size` hard-enforces mutation (it just truncates via `head -n "$LIMIT"`), so in principle one call with `--limit 70000` could classify an entire archive in one shot — but that is an unverified, never-exercised code path (looping `notmuch show`+`jq` per message 64k times in a single shell invocation) with unknown runtime/timeout behavior. Task 805's `--all`/`--archive` design (items 2–3) discusses looping *only* around `email-*-confirmed --execute`; it says nothing about how the **candidate manifest itself** gets built for a 64k-message scope in the first place. This is a whole missing pipeline stage.

### P0 — Undocumented folder-scope mechanism underlies the entire `--archive` proposal

**F4. `email-classify`, `email-census`, and `email-unsubscribe-extract` all default to `QUERY="folder:Gmail"` (INBOX only)**; reaching Gmail's All Mail requires passing an explicit notmuch query such as `folder:Gmail/.All_Mail` as a positional argument. **None of the in-repo email extension docs mention this parameter at all** — not `skill-email-cleanup/SKILL.md`, not `context/project/email/domain/wrapper-contracts.md` (§1–§9), not `README.md`/`EXTENSION.md`. The wrapper-contracts.md file explicitly states "Cross-repo coupling is documentation-only — this extension declares no machine dependency on `.dotfiles`," yet the entire `--archive` flag (item 3) is impossible to design correctly without knowing this undocumented QUERY convention, which currently exists only in the nix source. Anyone implementing task 805 strictly from files under `.claude/extensions/email/` (as the task description scopes it: "Likely touches .claude/extensions/email/...") will not discover this and may invent an incorrect or non-working folder-targeting mechanism.

### P1 — The confidence/classification model is far weaker than the task's framing implies

**F5. There is no LLM classification tier in the frozen, as-built binary — `email-classify` is a pure deterministic bash function with hardcoded confidence constants.** `classify_one()` checks, in order: a hardcoded 1-entry `CUSTOM_KEEP_SENDERS` list (confidence 0.98), a hardcoded ~13-domain `CUSTOM_DELETE_DOMAINS` list (confidence 0.98), a `NEWSLETTER_KEYWORDS` substring match (confidence 0.60, action=archive), a `NOTIFICATION_DOMAINS` substring match (confidence 0.55, action=archive), else `unsure|0.50|default-unsure`. `context/project/email/standards/recall-on-keep-bias.md` describes a 4th tier — "LLM judgment only on the residual" — but that tier is **not implemented in the wrapper**; it is aspirational documentation, not the deployed behavior. Consequences for task 805 specifically:
  - The delete-eligible confidence bar (≥0.90) is only ever reached for the ~13 hardcoded personal domains. For a 64k-message multi-year archive with a much larger and more diverse sender population than those 13 domains, the overwhelming majority of messages will land at 0.50 (`unsure`) or 0.55–0.60 (`archive`), never `delete`. Task 805's framing — "auto-propose delete only at confidence >= 0.90, else unsure" as a review-burden-reduction mechanism — barely engages for the archive-cleanup case; the real burden is reviewing a very large *unsure*/low-confidence-archive volume, not adjudicating a small residual of high-confidence deletes.
  - Where (or whether) an actual LLM classification pass would plug in to raise recall for the "unsure" bucket at 64k scale is entirely unaddressed by the task description, and is a prerequisite for the "recall-on-keep bias" framing to mean what items (1)/(2) imply.

**F6. Bucket-approval (item 1) doesn't address cardinality or intra-bucket false positives.** A multi-year, 64k-message archive plausibly has hundreds to low-thousands of distinct sender domains. `AskUserQuestion` is designed for a small, enumerable set of options per call; the task doesn't specify how domain-bucket enumeration would be paginated/prioritized (by count? by confidence? by recency?), nor how many rounds of prompting a full-mailbox pass would need. Separately, recall-on-keep bias only protects against losing wanted mail (biasing ambiguous cases to `keep`/`unsure`) — it says nothing about a bucket that is *mostly* correct but contains a minority of misclassified messages a user approves-in-bulk without seeing every subject line. Bulk-by-domain approval trades individual review granularity for throughput; the task doesn't acknowledge or bound that trade-off.

### P1 — Constraint compatibility: root-session execution vs. a long multi-stage drain

**F7. The "direct-execution in root session" invariant (needed so the interactive review gate can't live in a background subagent) is in tension with the scale this task targets.** A single full-mailbox pass at 50/batch is 1,280 mutation-execute calls before counting classify-pagination (F3) or manifest-splitting (F1) — each of which is its own Bash tool call plus manifest/hash bookkeeping, potentially over many separate `/email` invocations spanning days. The task asks for "per-batch progress reporting" but does not specify whether a single command invocation is expected to loop through all batches in one long root-session turn (context/turn-length risk) or whether the design should deliberately bound each invocation to a small number of batches and rely on repeated user-issued `/email --all` calls to resume (safer, but changes the UX contract and needs its own resume/state surfacing design). This is a live design fork the task doesn't decide.

**F8. `--sync`'s "freeze sync during bulk ops" rule is not reconciled with a multi-day drain.** `skill-email-sync`'s own docs (commit `51bfda974`) say `/email --sync` should run "only after a cleanup is complete and reviewed — never interleaved with an active cleanup batch." A 64k-message `--all`/`--archive` drain, per F1/F2/F7, plausibly spans multiple sessions over days. The task doesn't address whether the mailbox intentionally stays locally-diverged from the Gmail web UI for the entire drain (with no interim visibility), or whether periodic incremental sync windows would be safe (and if so, what "not mid-flight" means precisely — between splits? between full item-2/item-3 passes?).

### P2 — No field validation exists for anything this task is designing against

**F9. The email extension has never been loaded into any repository.** `.claude/extensions/email/README.md`: "This extension authors and ships the `.claude/extensions/email/` directory; loading it into a consuming repo... is a separate, later step and is out of scope." Per `specs/803_.../reports/02_authoring-contract-verification.md`, task 803 was "author + doc-lint, no load." That means: no manifest/state-file resume has ever actually been exercised end-to-end, no one has observed `email-classify`'s or `email-archive-confirmed --execute`'s real wall-clock time at any scale, and the progress-reporting UX for repeated batch calls has never been prototyped. Task 805 is designing a 64k-message, multi-day, multi-hundred-invocation workflow entirely on top of an unexercised system. This is a scope-completeness gap: the task description should probably require (or at least explicitly flag as a prerequisite) a small-scale pilot run — e.g., a bounded `--all` pass over a single low-stakes folder — before or alongside authoring the full `--archive` design, rather than speccing the large-blast-radius case first with zero empirical grounding.

### P2 — Scope completeness: aspects the task does not ask about

**F10. No circuit-breaker / stop-loss for anomalous classification behavior mid-drain.** If a notmuch index issue, a bad rule interaction, or unexpected sender data caused a spike in `unsure` or (worse) unexpectedly high-confidence delete classifications partway through a 1,280-batch drain, nothing in the task stops the loop or flags the operator; it only discusses steady-state batching and idempotent resume.

**F11. No aggregate audit/observability surface across many split sub-manifests and their `.state.jsonl` companions** (implied necessary by F1). A single execution-state diff per batch (per the existing Stage 6 "Verify") does not by itself give a human an overview of "38,000 of 64,000 processed, 40 failed, resuming at split #761" across a drain that may span dozens of split-manifest files.

**F12. No differentiated confirmation strength for `--expunge-trash` sourced from `--archive` (All Mail) vs. ordinary inbox triage.** The task explicitly acknowledges `--archive` has a "larger, near-irreversible blast radius" than inbox cleanup, but nothing in the proposed design adds a *distinct, stronger* gate specifically for permanently expunging All-Mail-sourced deletes (e.g. requiring a second, explicit "yes, permanently delete N archived messages older than Y" confirmation separate from the standard Stage 3 review) — the invariants list only re-states the existing single review gate.

### P2 — Cross-repo coupling risk is understated

**F13. `context/project/email/domain/wrapper-contracts.md` — the in-repo "frozen contract" summary this task is told to rely on — is already stale/incomplete relative to what mass-cleanup design requires**, independent of any future drift in `.dotfiles` task 72. Concretely, the in-repo summary omits: (a) the hard-refuse-over-`MAX_BATCH_SIZE` behavior of `enforce_batch_size` (F1); (b) that `PLAN_EXPIRY_DAYS` is checked via raw file mtime, not a logical timestamp (F2); (c) that `email-classify` has its own independent pagination/limit needing a separate drain (F3); (d) the `QUERY`/folder-scope parameter needed for `--archive` at all (F4); (e) that classify's confidence values are fixed per-rule constants from a deterministic bash function, not any kind of computed/calibrated score (F5). A researcher or planner who treats `wrapper-contracts.md` as sufficient ground truth (as the task's "referenced here by name only" framing invites) will design against an incomplete model of the system. Verifying directly against `~/.dotfiles/modules/home/email/agent-tools.nix` — as this critique did — should be a required research step, not an optional cross-check.

## Recommended Approach (what to verify or add to scope, not a design)

1. **Verify, don't assume, the manifest-splitting mechanism (F1).** Before designing the `--all`/`--archive` loop, confirm with a live (even single-digit-message) test run: does `enforce_batch_size` really hard-refuse over 50, and is manifest splitting + per-split sha256 the only way through? If so, scope this splitting logic explicitly as new skill-side work, not an afterthought of "looping execute."
2. **Decide and document the mtime-preservation policy for split manifests (F2)** before implementation — either deliberately propagate the original approval mtime (and accept possible early expiry over a >7-day drain, with an explicit re-approval-of-residual flow) or deliberately reset it per split (and explicitly own the resulting weakening of the staleness guard as an accepted trade-off, not a silent side effect).
3. **Add a classify-pagination design to scope** (F3): the candidate-manifest-building stage for a 64k-message scope needs its own explicit batching/looping story, parallel to (not merged with) the execute-side loop in item (2).
4. **Document the `QUERY`/folder-scope convention explicitly in this task's deliverables** (F4) — add it to `wrapper-contracts.md` or a new section, since `--archive`'s entire feasibility rests on it and it is currently absent from every file this extension ships.
5. **Re-scope the "confidence >= 0.90" framing** (F5) against the real `classify_one()` behavior — either explicitly note that the hardcoded personal-domain list is the only current source of delete-confidence and that a large "unsure" backlog is the expected normal outcome at archive scale, or add "extend/generalize the classifier" as an explicit prerequisite sub-task.
6. **Bound the bucket-approval UI's cardinality assumptions** (F6) — specify how many distinct sender/domain buckets are realistically expected and how `AskUserQuestion` rounds would be paginated/prioritized; acknowledge the bulk-approval-vs-granularity trade-off explicitly rather than leaving it implicit.
7. **Decide the root-session chunking model explicitly** (F7) — bounded-per-invocation-with-resume vs. single long-running loop — since this affects both context-exhaustion risk and the UX contract for `--all`/`--archive`.
8. **Specify the sync cadence during a multi-day drain** (F8) — either explicitly accept a long local/server divergence window, or define what "not mid-flight" means precisely enough to allow safe interim `--sync` windows.
9. **Add a pilot/validation prerequisite to scope** (F9) — a small, low-stakes bounded run of the new loop mechanics before greenlighting the full 64k `--archive` design, given the extension has zero field usage to date.
10. **Add circuit-breaker and aggregate-audit requirements to scope** (F10, F11) for any drain spanning hundreds of batches.
11. **Add a distinct, stronger confirmation gate for `--archive`-sourced `--expunge-trash`** (F12), proportionate to the blast radius the task itself calls out.
12. **Treat `~/.dotfiles/modules/home/email/agent-tools.nix` as the primary source during planning**, not the in-repo `wrapper-contracts.md` summary alone (F13) — re-verify every constant/behavior claim used in the plan against the live nix source.
