## Executive Summary

- Confirmed exactly **24 scripts** under `agent-system/extensions/core/scripts/` compute a
  root path via `${SCRIPT_DIR}/../..` (or equivalent) with no validation that the result is
  actually a repo root. The count matches the task description precisely.
- The bug is already partially self-documented: `check-extension-docs.sh` (one of the 24)
  carries a "known latent bug, flagged not fixed" comment describing this exact defect and
  instructing verification callers to override `REPO_ROOT` manually — i.e. this task is
  closing a gap the codebase already flagged but never fixed.
- The deploy tree is **not singular**: both `.claude/scripts/` and `.opencode/scripts/` are
  valid two-levels-deep deploy locations for (mostly) the same script family, deployed from
  the same `agent-system/extensions/core/scripts/` source. Any guard must accept either
  `.claude` or `.opencode` as the valid grandparent directory name, not hardcode one.
- Recommended guard: a **structural path check**, not a filesystem-existence check — verify
  `basename(dirname(SCRIPT_DIR))` is `.claude` or `.opencode` immediately after computing
  `PROJECT_ROOT`/`SCRIPT_DIR`, before any other use of the (possibly bogus) root (no mkdir,
  no file reads). This directly encodes the invariant the task description states, requires
  zero additional I/O, and needs no new shared file (matches the existing convention of
  fully self-contained, non-sourced scripts in this directory).
- The `.gitignore` fix is a one-line de-anchor: `/.agent-logs/` (line 10) -> `**/.agent-logs/`,
  matching the de-anchoring convention already used by sibling entries at lines 27-35
  (`**/.lock/`, `**/.orchestrator-handoff.json`, etc.).
- Regeneration is manual-only (`<leader>al`): fixing the 24 source-store files does not
  automatically propagate to `.claude/scripts/` — a human must run "Sync all" for the deployed
  copy to pick up the guard. `.opencode/scripts/` is independently git-tracked (not gitignored,
  not regenerated by the same picker) and is explicitly out of scope per this task's wording
  (mirrors a prior precedent where a similar `.opencode/` port was flagged "OUT OF SCOPE" and
  left as a recommended follow-up, not implemented inline).

## Context & Scope

**What was researched**: The exact set of scripts affected, the deploy-tree topology (source
store vs. `.claude/`/`.opencode/` deploy trees), existing conventions for root resolution and
error messaging in this script family, and the precise `.gitignore` anchoring convention.

**Constraints observed**:
- No shared/sourced bash library exists for root resolution today (only `skill-base.sh` is
  designed to be sourced, and only for skill lifecycle functions, not root discovery).
- `set -euo pipefail` is standard at the top of these scripts; the guard must run before any
  side-effecting operation (log-file `mkdir -p`, state-file reads) — several scripts (notably
  `generate-todo.sh`, `update-phase-status.sh`) currently create `.agent-logs/...` via
  `mkdir -p "$(dirname "$LOG_FILE")"` *before* validating `STATE_FILE` exists, which is exactly
  how the reported stray directory got created.
- `git rev-parse --show-toplevel` is used elsewhere in this script family (`git-snapshot.sh`)
  but was deliberately not considered as "the fix" here: the task explicitly wants a script run
  outside a valid deploy tree to **fail loudly**, not silently auto-correct to the true git
  root and proceed as if invoked correctly. Auto-correcting via git-toplevel would mask exactly
  the invocation-context bug this task exists to surface.

## Findings

### Codebase Patterns

**The 24 affected scripts** (all under `agent-system/extensions/core/scripts/`, confirmed via
`grep -rln '\.\./\.\.' agent-system/extensions/core/scripts/*.sh`):

```
archive-task.sh              manage-topics.sh              update-phase-status.sh
check-extension-docs.sh      memory-harvest.sh             update-task-status.sh
events-append.sh             memory-retrieve.sh            validate-context-budgets.sh
events-query.sh              reconcile-artifacts.sh        validate-context-index.sh
export-to-markdown.sh        reconcile-task-status.sh      validate-extension-index.sh
generate-task-order.sh       roadmap-sync.sh               validate-wiring.sh
generate-todo.sh             task-lock.sh                  vault-operation.sh
install-extension.sh         uninstall-extension.sh
literature-retrieve.sh
```

Variable naming is inconsistent across the set but the shape is identical:
- 20 scripts: `SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` then
  `PROJECT_ROOT="$(cd "$SCRIPT_DIR/../.." && pwd)"` (or `${SCRIPT_DIR}` braced variant —
  cosmetically different, semantically identical).
- `check-extension-docs.sh`: single-line `REPO_ROOT="${REPO_ROOT:-$(cd "$(dirname
  "${BASH_SOURCE[0]}")/../.." && pwd)}"` — already override-able via env var, with a comment
  block explicitly flagging this exact bug (see "Known Prior Art" below).
- `update-phase-status.sh`: lowercase `script_dir` / `repo_root`.
- `validate-context-budgets.sh`: `REPO_ROOT` instead of `PROJECT_ROOT`.
- `validate-extension-index.sh`: `PROJECT_DIR="${SCRIPT_DIR}/../.."` — the one outlier that
  skips the `cd ... && pwd` normalization (leaves `../..` unresolved in the string), but the
  same source-store-vs-deploy-tree ambiguity applies identically.

**Confirmed reproduction of the reported symptom**: `generate-todo.sh` computes `LOG_FILE`
from `PROJECT_ROOT` and does `mkdir -p "$(dirname "$LOG_FILE")"` (line 93) *before* checking
`[[ ! -f "$STATE_FILE" ]]` (line 106) and calling `log_error "state.json not found at
${STATE_FILE}"` (line 107) + `exit 1` (line 108). This ordering is exactly why the stray
`.agent-logs/` directory is created even though the script ultimately fails: the log directory
is materialized before the fatal check runs. `update-phase-status.sh` has the same
`.agent-logs` usage pattern. Any guard fix must run *before* this log-directory creation, not
just before the `specs/state.json` check.

**Deploy tree is byte-identical to source when in sync**: `diff
agent-system/extensions/core/scripts/generate-todo.sh .claude/scripts/generate-todo.sh` shows
zero diff — confirming `.claude/scripts/` copies are literal, unmodified copies of the source
store (regular files, not symlinks — verified via `ls -la`), so a guard added to the source
propagates verbatim on the next `<leader>al` "Sync all" regeneration.

**`.opencode/scripts/` is a second, only-partially-overlapping deploy target**: it contains
56 scripts, a strict subset/superset mismatch against the 24 core scripts (e.g. it lacks
`generate-todo.sh`, `events-append.sh`, `events-query.sh`, `literature-retrieve.sh`,
`manage-topics.sh`, `reconcile-artifacts.sh`, `reconcile-task-status.sh`, `task-lock.sh`,
`update-phase-status.sh` entirely — OpenCode uses different postflight scripts for some of
this). Of the files it does share, some are byte-identical to the source (`validate-wiring.sh`)
and others have diverged with OpenCode-specific edits (`generate-task-order.sh`, which even
carries an inline comment flagging ".opencode/ write-side... is OUT OF SCOPE... a recommended
follow-up, flagged but not implemented in this change" from a prior task that mirrored a
render-side fix there). `.opencode/` is git-tracked directly (not covered by the `/.claude/`
gitignore rule), so it is not regenerated by the same manual sync mechanism as `.claude/`.
**This confirms `.opencode/scripts/` is a legitimate second deploy-tree shape (`.opencode/scripts/`,
same two-levels-deep structure) that any guard must not exclude by hardcoding `.claude` only —
but porting the fix there is a separate, manual mirroring step outside this task's stated
24-script/`.gitignore` scope**, consistent with the precedent noted above.

### Known Prior Art (self-documented bug)

`check-extension-docs.sh` lines 74-80 already contain:

```bash
# NOTE (known latent bug, flagged not fixed -- see the plan this check-extension-docs.sh change
# shipped with): this auto-detect assumes BASH_SOURCE is deployed at .claude/scripts/<name>
# (two directories under REPO_ROOT). When this script is instead invoked directly from its
# extension SOURCE-STORE path (agent-system/extensions/core/scripts/check-extension-docs.sh),
# the auto-detect miscomputes REPO_ROOT. Verification and any source-store invocation MUST pass
# an explicit REPO_ROOT=$(pwd) override; the auto-detect is correct only for the deployed copy.
REPO_ROOT="${REPO_ROOT:-$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)}"
```

This is the same defect for the same script, already named and flagged, and is the strongest
available evidence that the fix approach (a validation guard, not a silent auto-correct) is
the intended and previously-endorsed direction — it just wasn't implemented yet. The
`REPO_ROOT="${REPO_ROOT:-...}"` env-var override pattern used here is orthogonal to (and
compatible with) adding a validation guard: the guard should only fire on the *computed*
default, not when a caller has explicitly overridden the root variable for verification
purposes.

### .gitignore Anchoring Convention

Current line 10: `/.agent-logs/` (root-anchored — a leading `/` in `.gitignore` matches only
at the repository root, so `agent-system/extensions/.agent-logs/` or any other nested
`.agent-logs/` created by a misresolved root is **not** ignored and would show up as an
untracked directory in `git status`).

The file already establishes a clear de-anchoring convention a few lines below (lines 27-35),
used specifically for other runtime/ephemeral artifacts that can appear at any depth:
```
**/.lock/
**/.orchestrator-handoff.json
**/.orchestrator-loop-guard
**/.continuation-loop-guard
**/.orchestrator-churn-state.json
**/.postflight-loop-guard
**/.orchestrator-multi-state.json
**/.return-meta-*.json
**/.events.lock
```
De-anchoring `/.agent-logs/` to `**/.agent-logs/` is a one-line change consistent with this
existing pattern, and ignores the directory "wherever it appears" as the task requests
(including the currently-tracked-clean `./.agent-logs/` at repo root, which stays covered).

### Recommendations

**Guard placement and content**: Insert immediately after the existing two-line
`SCRIPT_DIR` / `PROJECT_ROOT` (or `REPO_ROOT`) computation in each of the 24 scripts, before
any other statement that consumes the root (default-value assignments, `mkdir`, file checks).
A minimal, dependency-free structural check:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJECT_ROOT="$(cd "${SCRIPT_DIR}/../.." && pwd)"
case "$(basename "$(dirname "$SCRIPT_DIR")")" in
  .claude|.opencode) ;;
  *)
    echo "ERROR: $(basename "$0") must run from a deployed scripts/ tree (.claude/scripts/ or" \
         ".opencode/scripts/), not '${SCRIPT_DIR}'. This looks like the agent-system source" \
         "store -- deploy first via <leader>al ('Load Core' / 'Sync all'), then run the" \
         "deployed copy." >&2
    exit 1
    ;;
esac
```

Rationale for this shape over alternatives considered:
- **Structural (path-basename) vs. filesystem-existence check** (e.g. testing for
  `"$PROJECT_ROOT/.claude-extensions.json"` or `"$PROJECT_ROOT/specs"`): the structural check
  needs zero additional `stat`/`test` calls beyond string operations already computed, cannot
  produce a false negative on a fresh repo that hasn't run `/task` yet (no `specs/` dir) or
  hasn't loaded any extension yet, and directly encodes the exact sentence in the task
  description ("the script sits at `.claude/scripts/`... in the source store the same file
  sits at `agent-system/extensions/core/scripts/`"). A marker-file check is a viable fallback
  but is strictly weaker here (extra I/O, extra edge cases) for no accuracy gain.
  `basename(SCRIPT_DIR)` itself is not worth checking — it is always literally `scripts` in
  every location (source store and both deploy trees), so it carries no discriminating power;
  the only signal is the grandparent name.
  - `check-extension-docs.sh` should keep its existing `REPO_ROOT="${REPO_ROOT:-...}"`
    override capability for verification callers; the guard must only fire when the value was
    *not* explicitly overridden (i.e. gate the `case` on whether `REPO_ROOT` was pre-set,
    mirroring the existing `${VAR:-default}` idiom already in that file).
  - **Do not** use `git rev-parse --show-toplevel` as a "fix": it would silently make
    source-store invocation succeed by finding the true repo root, defeating the "fail loudly"
    requirement and masking the invocation-context error the task wants surfaced.
- **No new shared/sourced helper file**: the 24 scripts are currently fully self-contained
  (only `skill-base.sh` is designed to be sourced, for unrelated skill-lifecycle concerns).
  Introducing a new `resolve-root.sh` sourced by 24 files would reduce line count marginally
  but adds a new cross-file dependency/convention not used elsewhere in this directory, and
  the guard itself is already only ~6-8 lines — the DRY savings do not clearly outweigh the
  convention change for a "keep it clean and elegant, minimal code" goal applied per-script.
  This is presented as a considered alternative for the planner, not a final decision.

**Ordering fix for `.agent-logs` scripts specifically**: `generate-todo.sh` and
`update-phase-status.sh` currently `mkdir -p` their log directory before validating
`state.json`/other inputs exist. Placing the new root guard at the very top (right after
`SCRIPT_DIR`/`PROJECT_ROOT` computation, before any `LOG_FILE`/`STATE_FILE` derivation) makes
this ordering irrelevant for the source-store case — the script exits before any path derived
from the bogus root is ever used, so no stray directory is created regardless of each script's
internal mkdir-before-validate ordering.

**`.gitignore`**: change line 10 from `/.agent-logs/` to `**/.agent-logs/`. No other changes
needed; this is a single-line, self-contained fix.

## Decisions

- Guard is a structural path check (grandparent-directory-name test), not a filesystem-marker
  check or a `git rev-parse` auto-correct — chosen for zero extra I/O, no false negatives on
  fresh/partial repos, and direct correspondence to the task's stated invariant.
- Guard accepts **both** `.claude` and `.opencode` as valid deploy-tree grandparent names,
  since both are real, currently-populated two-levels-deep deploy targets for this script
  family, even though only `.claude/scripts/` regenerates automatically via `<leader>al`.
- `.opencode/scripts/` mirroring of the 24-script fix is **out of scope** for this task
  (task description scopes explicitly to "24 scripts under
  `agent-system/extensions/core/scripts/`" and the `.gitignore`/`.agent-logs` symptom); flagged
  as a recommended follow-up, consistent with an existing precedent comment already in
  `.opencode/scripts/generate-task-order.sh` for a prior, similarly-scoped fix.
- No new shared/sourced helper script is proposed; each of the 24 scripts gets its own
  self-contained guard block, consistent with the existing non-sourced convention in this
  directory. (Flagged as a considered-but-not-chosen alternative for the planner to revisit if
  it disagrees.)
- `check-extension-docs.sh`'s existing `REPO_ROOT="${REPO_ROOT:-...}"` override must remain
  functional for verification callers; the guard should only fire on the computed default, not
  on an explicit caller-supplied override.

## Risks & Mitigations

- **Risk**: Guard false-positives if a future third deploy-tree name (neither `.claude` nor
  `.opencode`) is introduced. **Mitigation**: the `case` statement is a single line to extend;
  document the two accepted names inline in each guard so a future addition is a mechanical
  one-line edit per script (or a signal to finally introduce a shared helper at that point).
- **Risk**: 24 near-identical edits risk copy-paste drift (subtly different messages/variable
  names). **Mitigation**: use one canonical guard block text (parameterized only by
  `SCRIPT_DIR`/`PROJECT_ROOT`/`REPO_ROOT` variable name already in use per file) and verify via
  `grep` that all 24 post-edit files contain the identical guard body modulo variable name.
- **Risk**: Editing the source store does not fix the currently-deployed `.claude/scripts/`
  copies until a human runs `<leader>al` "Sync all" (see
  `.claude/context/patterns/regeneration-is-manual-only.md` — no headless/CI path exists for
  this). **Mitigation**: none needed at the research stage; this is expected, documented
  behavior, not a defect to route around. Note it in the plan/summary so the user knows a
  manual regeneration step is required to see the guard live in `.claude/scripts/`.
- **Risk**: `validate-extension-index.sh`'s `PROJECT_DIR` is unresolved-string
  (`"${SCRIPT_DIR}/../.."`), not `cd`-normalized like the other 23. **Mitigation**: the
  structural guard operates on `SCRIPT_DIR` directly (via `dirname`/`basename`), not on the
  unresolved `PROJECT_DIR` string, so this script needs no special-casing — the guard logic is
  identical across all 24 files regardless of how each script's root variable itself is
  constructed downstream.
