## Key Decisions Made

- Discarded an initial extraction script whose colon-split `sed` pattern broke on maildir
  filenames containing literal colons (`...,U=1:2,S`), producing corrupted output that
  (falsely) showed near-100% label-only for every folder including ones later shown to have
  real overlap. Rebuilt using NUL-separated `grep -Z -H` before trusting any result.
- Independently spot-checked both a positive overlap case and multiple negative (label-only)
  cases using precise header-anchored re-search (not substring grep, which false-positives on
  `In-Reply-To`/`References` quoting) before finalizing the report.
- Per the plan's own Rollback/Contingency §Abort criteria ("if Phase 3 verification cannot
  confirm Labels redundancy, skip Phase 4 deletion... leave files inert... the config fix alone
  resolves the reconcile-blocking defects once Phases 5-6 complete"), decided Phase 4 will use
  the leave-in-place fallback rather than attempt a bulk move of ~37,412 messages, which is a
  human-judgment-requiring re-categorization decision out of scope for this plan's 1-hour Phase 4
  budget.

## Deviations from Plan

- **Major deviation** (documented, not silent): the label-only set is not a small exception list
  as the plan's Overview assumed — it is the overwhelming majority. This does not block the
  plan's actual goal (stop the mbsync-reconcile-blocking defects) since Phase 4's outcome (leave
  files inert) was explicitly pre-authorized by the plan's own contingency section for exactly
  this scenario.
- Recommend spawning a follow-up task (out of scope here) to decide, with human input, whether/
  how to fold the label-only messages into a durable canonical location.

## What NOT to Try

- Do NOT bulk-delete `.Labels.Important`/`.Labels.Letters`/`.Labels.EuroTrip`/`.Labels.CrazyTown`
  content — doing so would destroy ~37,412 messages with no other copy.
- Do NOT attempt an automated bulk-move of label-only messages into `.Archive` without human
  review of the target structure and collision handling — this is a separate, larger task.
- Do not trust a colon-split parse of maildir `grep -H` output — maildir filenames contain
  literal colons in the flag suffix; use `grep -Z` (NUL-separated) instead.
