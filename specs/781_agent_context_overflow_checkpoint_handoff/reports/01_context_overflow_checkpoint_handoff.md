The document defines: 4 detection signals (tool call volume >50 hard limit, re-read detection, pre-operation risk assessment before 3+ file reads, phase-boundary checks), a threshold table (context-used % vs. tool-call count vs. recommended action, escalating from "continue normally" at <30%/<15 calls to "emergency handoff" at >80%/>50 calls), a 4-step handoff-writing protocol (update progress file first, write handoff artifact per `handoff-artifact.md`, increment `handoff_count`, return `partial` with `handoff_path`), 5 anti-patterns (don't push to the limit, don't write vague handoffs, don't skip the progress file, don't inline full file contents, don't hand off mid-edit), and a model-specific tool-call-limit table (Haiku ~30/threshold 20, Sonnet ~50/threshold 35, Opus ~60/threshold 45). **3. What "checkpoint" currently means in the codebase — and what's missing**

`general-implementation-agent.md`'s Stage 4C ("E. Handoff on Context Pressure") is the closest existing thing to CHECKPOINT-BEFORE-OVERFLOW:
1. Update progress file to exact current state
2. Annotate plan file (checked-off items, in-progress marker, deviations) as a "final checkpoint" — explicitly so the **plan file itself** is a reliable resume point even if the handoff doc is lost
3. Write handoff artifact (`handoff-artifact.md` template: Immediate Next Action, Current State, Key Decisions Made, What NOT to Try, Critical Context, References)
4. Increment `handoff_count`
5. Skip remaining phase steps, jump to Stage 7 (metadata), return `partial` + `handoff_path`

**What this flow does NOT do, and what task 781 item (2) requires added:**
- **No git commit step.** The existing Phase Checkpoint Protocol (further down in the same file) commits *after a phase completes* (`git commit -m "task {N} phase {P}: {phase_name}"`), but the context-pressure handoff path (Stage 4C) is explicitly mid-phase and has no analogous commit step. A context-pressure handoff can currently leave uncommitted work in the tree with nothing capturing it — exactly the RED-tree failure mode task 781's motivating incident describes, minus the crash (the base agent doesn't crash, but it also doesn't commit/snapshot before terminating on `partial`).
- **No RED-vs-green branch.** Nothing in either implementation agent checks `git status`/build state before deciding whether to `git commit` (if green) or call `git-snapshot.sh` (if red) as task 781 item (2) specifies. This branch does not exist anywhere in the current agent files.
- **`general-implementation-hard-agent.md`'s Stage 4C** ("same as base agent, plus...") inherits the same gap — its own Stage 5 "final incremental commit" (`git add -A && git commit ...`) only fires after **all assigned phases complete**, not on the mid-phase context-pressure exit path. A hard-mode agent that hits context pressure mid-phase currently writes `.orchestrator-handoff.json` but does not commit or snapshot first.

**4. `git-snapshot.sh` — zero current agent consumers**

`.claude/scripts/git-snapshot.sh` (+ identical `.claude/extensions/core/scripts/git-snapshot.sh`) is a task-780 helper: no-ops on a clean tree; otherwise writes `specs/{NNN}_{SLUG}/working-progress-{ts}.patch` (via `git diff HEAD`) **and** `git stash push -u` (default mode) or a `wip-snapshot-{ts}` scratch-branch WIP commit (`--branch` mode), then writes a freshness-windowed (120s), single-consumption marker (`specs/{NNN}_{SLUG}/.git-snapshot-marker`) that `guard-destructive-git.sh` (the PreToolUse hook) checks before allowing a destructive git command. Usage: `git-snapshot.sh [--branch] [TASK]` where `TASK` is a task number, a `specs/{NNN}_{SLUG}` path, or (if omitted) inferred from the single task in status `"implementing"` in `state.json`.

`grep -rln "git-snapshot.sh" --include="*.md" .` (excluding archive) returns only: `git-workflow.md` (×2 copies) and task 780's own artifacts. **No agent file references it.** This means task 781's RED-path branch is not a "wire in an existing call," it is a genuinely new integration: on context pressure, if the tree is dirty AND the agent cannot verify green (build/tests), call `bash .claude/scripts/git-snapshot.sh {task_number}` instead of `git commit`, and record which snapshot mechanism was used (patch path / stash ref / branch name) in the handoff so a successor can recover the exact state. If green, the existing `git commit` path suffices — no snapshot call needed (a green commit already IS the safe checkpoint).

**5. `wrap-up.md` (H9) — schema and current audience**

Canonical path: `.claude/context/contracts/wrap-up.md`. Explicitly scoped: *"`--hard`-only: This entire contract is loaded exclusively by hard-mode dispatch paths (`skill-implementer-hard`, `general-implementation-hard-agent`, `skill-orchestrate-hard`); STANDARD mode never loads this file."* — `general-research-hard-agent` is **not** in this list, and does not reference `wrap-up.md` anywhere (`grep` confirms zero hits).

Schema (`.orchestrator-handoff.json`, max 400 tokens):
```json
{
  "status": "implemented | partial | blocked",
  "skeleton": false,
  "phases_completed": 2,
  "phases_total": 5,
  "sorry_inventory": [],
  "blockers": [{"phase": 3, "target": "...", "verbatim_goal": "...", "what_was_tried": "...", "why_it_failed": "..."}],
  "continuation_path": "specs/{NNN}_{SLUG}/handoffs/phase-{P}-handoff-{TS}.md"
}
```
`phases_completed`/`phases_total`/`sorry_inventory` are implementation-shaped concepts (phase-based execution, Lean sorries) that don't map cleanly onto a research dispatch, which has no "phases" in the plan-execution sense. If task 781 extends H9 to research-hard, the plan should either (a) define a research-appropriate subset/variant of this schema (e.g. `sections_completed`/`sections_total` instead of phases, no `sorry_inventory`), or (b) reuse the existing STANDARD-mode `partial` + `handoff_path` shape (already generic and already used by `general-implementation-agent.md`) for research instead of inventing a new hard-mode schema. Given research dispatches are single-pass (no phase list to resume mid-way), option (b) is likely the lower-friction fit — worth flagging as an open design decision for the planner rather than assuming (a).

The continuation markdown (required when `status != "implemented"`) has 6 required sections: Immediate Next Action, Current State, Key Decisions Made, What NOT to Try, Remaining Goals (verbatim from plan), References. This is a superset of `handoff-artifact.md`'s template (which has 5: Immediate Next Action, Current State, Key Decisions, What NOT to Try, Critical Context, References) — the two templates are similar but not identical; `wrap-up.md`'s "Remaining Goals (verbatim)" section has no direct analogue in `handoff-artifact.md`'s "Critical Context." Any research-hard continuation markdown should follow whichever of the two templates its parent agent's mode dictates (STANDARD → `handoff-artifact.md`; HARD → `wrap-up.md`'s continuation schema) rather than inventing a third shape.

**6. `subagent-continuation-loop.md` — the consumer side, and its total absence from research skills**

This pattern (`.claude/context/patterns/subagent-continuation-loop.md`) defines the **skill-level** loop that turns a `partial` + `handoff_path` return into an automatic successor spawn: a loop guard file (`specs/{NNN}_{SLUG}/.continuation-loop-guard`, tracks `continuation_count`/`max_continuations: 3`), a `continuation_context` object injected into the successor's delegation context (`is_successor`, `continuation_number`, `handoff_path`, `progress_path`, `previous_phases_completed`), and a status-transition table (`partial` + `handoff_path` + count < 3 → spawn successor and continue; `partial` + no `handoff_path` → break, report partial, user resumes; count ≥ 3 → break, max reached).

Verified by direct `grep` against both `SKILL.md` files:
- `skill-implementer/SKILL.md` and `skill-implementer-hard/SKILL.md`: **fully implement this loop** (loop guard init/update/cleanup, `handoff_path` extraction from metadata, successor spawn logic, the exact status-transition table from the pattern doc).
- `skill-researcher/SKILL.md` and `skill-researcher-hard/SKILL.md`: **zero matches** for `continuation`, `handoff_path`, or `context-exhaustion`. No loop guard, no successor-spawn logic, nothing.

**This is the most important scoping finding for the plan.** Adding context-pressure monitoring and handoff-writing to `general-research-agent.md`/`general-research-hard-agent.md` alone would produce handoffs that nothing ever reads — a write with no reader. For task 781 item (3) ("Ensure the handoff captures enough for a FRESH agent to resume with minimal context") to actually be actionable for research, `skill-researcher{,-hard}` need at minimum a way to detect a stale/incomplete prior research attempt on re-invocation (e.g., checking for an existing handoff in `specs/{NNN}_{SLUG}/handoffs/` before starting fresh) — full automatic successor-spawning (mirroring `skill-implementer`'s loop) is the more complete fix but roughly doubles the scope of the research half of this task. The plan should make an explicit choice here rather than silently defaulting to "write-only."

**7. Small-phase/skeleton coordination (item 4 of the task)**

`general-implementation-hard-agent.md` already has the strategic-sorry-skeleton mechanism from task 778 fully wired (own "## Strategic-Sorry Skeleton (Hard Mode)" section, Stage 5 Step 1 worked example with the full 7-field `sorry_inventory` entry schema, `follow_up_task` requirement). The coordination task 781 item (4) asks for ("if a phase's single goal state is too large, land a strategic-sorry skeleton and hand off rather than overflowing") is therefore mostly a **sequencing/documentation** concern, not new mechanism: the context-pressure monitoring stage (4.5) should explicitly note that when a goal state is oversized, the skeleton path (778) is the preferred escape valve *before* falling through to a context-pressure handoff — i.e., "try skeleton-and-continue, then handoff-if-still-pressured," not two independent, competing exits. This applies to the domain-specific (lean/cslib) implementation-hard agents primarily, since strategic sorries are a Lean-specific concept; the *general* implementation-hard agent's own inherited section is generic infrastructure that domain agents build on, so no change is obviously needed in `general-implementation-hard-agent.md` itself for this item — mainly a note/cross-reference addition.

### Recommendations

1. **Research agents (both variants) need the monitoring + handoff apparatus built, not just the doc reference.** Adapt `general-implementation-agent.md`'s Stage 4.5/4C pattern to a research-shaped flow: after Stage 3 (Execute Primary Searches) sub-steps, add a monitoring checkpoint; on pressure, write a partial report-in-progress note + a handoff (using `handoff-artifact.md`'s template for STANDARD, since research has no `wrap-up.md` access), and return `partial` + `handoff_path`. For HARD mode, decide (and document) whether to extend `wrap-up.md`'s consumer list to include `general-research-hard-agent` with a research-appropriate schema variant, or to keep research on the STANDARD `handoff-artifact.md` shape even in hard mode — recommend the latter (lower schema-invention risk) unless the planner has a concrete reason phases-style tracking helps research.
2. **Add the CHECKPOINT-BEFORE-OVERFLOW git branch to all four target agents' pressure-handling paths**: before writing the handoff, check `git status --porcelain`; if dirty and the agent can positively confirm a green state (build/tests passing, or no build applicable), `git commit` as today; if dirty and state cannot be confirmed green (or is confirmed red), call `bash .claude/scripts/git-snapshot.sh {task_number}` instead and record the resulting patch path/stash ref/branch name in the handoff's Current State section. This branch is currently absent from all four agents and is the literal mechanism named in task 781 item (2) ("commit current green state, or snapshot via task 780 if RED").
3. **Decide and document the research continuation-consumer scope** (item 3): minimally, `skill-researcher{,-hard}` should check for a prior unresolved handoff under `specs/{NNN}_{SLUG}/handoffs/` at the start of a `/research N` invocation and inject it as `continuation_context` if found (mirroring the `is_successor` shape from `subagent-continuation-loop.md`), even without full automatic successor-spawning. This closes the "write with no reader" gap identified in Finding 6 with substantially less scope than porting the entire `skill-implementer` loop.
4. **Update every touched file in both the deployed and extension-source copy** (`.claude/...` and `.claude/extensions/core/...`), consistent with the dual-copy discipline documented in task 780's report and demonstrated by task 782's summary. `.opencode/` mirrors are a separate system (OpenCode) and are out of scope unless the task description says otherwise — task 781's description only names `.claude/` agent files.
5. **For item (4)**, add a one-paragraph cross-reference in `general-implementation-hard-agent.md`'s Stage 4.5 (or a new sub-bullet) noting: "if the oversized goal state belongs to a formal-domain phase with the strategic-sorry skeleton mechanism available (778), prefer landing the skeleton over a context-pressure handoff; only handoff if the skeleton itself cannot be completed within budget." No new mechanism required — this is sequencing guidance layered onto existing infrastructure.

## Decisions

- Treat the four target agents as two clearly different starting points, not four symmetric edits: implementation agents need a **RED/green-branch commit-or-snapshot insertion** into an existing, mostly-complete handoff flow; research agents need the **entire monitoring + handoff flow built** by adapting the implementation-side pattern, since no research-side precedent exists to extend.
- Flag the `skill-researcher{,-hard}` continuation-consumer gap (Finding 6) as a required planning decision rather than silently scoping it out — writing research handoffs that nothing reads would not satisfy task 781 item (3)'s "captures enough for a FRESH agent to resume" requirement in any operationally meaningful sense.
- Recommend research-hard use the STANDARD `handoff-artifact.md` shape rather than inventing a phases/`sorry_inventory`-shaped H9 variant for research, since research dispatches don't have a phase list to resume from mid-way (open question for the planner, not a closed decision).

## Risks & Mitigations

- **Risk**: Scope creep — porting `skill-implementer`'s full continuation loop to `skill-researcher{,-hard}` is a substantial secondary task in its own right (loop guard, successor spawn, `continuation_context` injection) that could double this task's size. **Mitigation**: plan should explicitly bound this to the minimal "detect and inject prior handoff on re-invocation" version (Recommendation 3) unless the planner deliberately chooses full parity with `skill-implementer`.
- **Risk**: Re-inventing the H9 schema for research (`sorry_inventory`/`phases_*` fields that don't fit) produces an inconsistent, half-applicable contract. **Mitigation**: default to reusing the STANDARD `handoff-artifact.md` + `partial`/`handoff_path` shape for research in both STANDARD and HARD mode, reserving `.orchestrator-handoff.json`/`wrap-up.md` for phase-structured implementation dispatches only, unless a concrete need for hard-mode-specific research handoff fields is identified during planning.
- **Risk**: Single-copy edits (deployed only, or extension-source only) get silently reverted by a later unrelated sync, exactly as happened to `block-pr-submission.sh` (documented in task 780's report, still unresolved in current `HEAD`). **Mitigation**: plan must include an explicit dual-copy verification step (e.g. `diff` between deployed and extension-source copies of every touched file) as part of its own verification checklist, following task 780/782 precedent.
- **Risk**: Adding a git-status check + potential `git-snapshot.sh` call into four agents' hot paths (every context-pressure exit) could interact awkwardly with `guard-destructive-git.sh`'s freshness-windowed marker if an agent's later actions (e.g., an eventual retry) run a destructive git command outside the 120s window and get blocked unexpectedly. **Mitigation**: the plan should note this is an *additive* integration (agents calling the sanctioned snapshot helper, not running destructive commands themselves) and therefore does not interact with the guard hook's blocking logic at all — only `git-snapshot.sh`'s own success/failure path matters here.

## Context Extension Recommendations

- **Topic**: Research-side context-exhaustion handoff pattern.
  **Gap**: `context-exhaustion-detection.md` and `handoff-artifact.md` are both written with an implicit implementation/phase-execution framing (phase files, plan checklists); there is no documented adaptation for single-pass research dispatches (report sections instead of phases, no plan-file checklist to annotate).
  **Recommendation**: after task 781 implements the research-agent monitoring/handoff flow, consider whether a short addendum to `context-exhaustion-detection.md` (or a research-specific companion note) documenting the report-shaped adaptation would help future agents avoid re-deriving it.
- **Topic**: `git-snapshot.sh` agent-integration contract.
  **Gap**: the script's own header documents the hook-side consumption contract (marker format, freshness window, single-use consumption) in detail, but there is no documentation anywhere of how an *agent* (as opposed to the hook) should decide whether to call it (i.e., the green/red branch task 781 needs) — this knowledge currently only exists in task 780's research report and now in this report.
  **Recommendation**: once task 781 lands the first real agent-side callers of `git-snapshot.sh`, consider promoting the green/red decision logic into a short shared pattern doc (e.g. `.claude/context/patterns/checkpoint-before-overflow.md`) that both implementation and research agents (and any future hard-mode agent) can reference by `@`-import instead of re-describing the branch inline in four separate agent files.
