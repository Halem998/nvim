## Key Decisions Made

- Detectors 3-7 (the five raw-`$COMMAND` destructive-chain detectors) anchor their
  segment/match extraction on `(^|[;&|][[:space:]]*)` — start-of-string or a literal `;`/`&`/`|`
  character, NOT arbitrary preceding prose. An initial attempt at "message mentions git reset
  --hard" style fixtures (destructive phrase preceded only by ordinary prose, e.g. "the")
  reproduced GREEN pre-fix — not evidence of the defect. Per the plan's own Phase 2 instruction
  ("a case expected to expose the defect but observed GREEN pre-fix is a defective case, not
  evidence — fix the case before proceeding"), these were replaced with message text containing a
  literal `;` immediately before the destructive phrase, which DOES reproduce RED pre-fix for all
  five detectors (confirmed by direct reproduction outside the suite first, then in-suite).
- Recorded RED set against the unmodified hook (11 cases, exactly as expected):
  multi-line essential-refactor/auto-repair/multi-task (3), the five semicolon-punctuated
  message-text cases per vulnerable destructive detector (5) plus their two multi-line variants
  for clean and forced-switch (2, per plan requirement), and the `#`-comment `--staged`
  false-exemption case (1).
- SELF-REFERENTIAL HAZARD fired for real during this phase: an early reproduction attempt run
  directly via the Bash tool (not through the suite file) embedded literal `; git reset --hard`
  text inside the raw multi-line bash command sent to the Bash tool. Because the repo's own
  working tree was dirty (new untracked test file) and the harness's deployed
  `.claude/hooks/guard-destructive-git.sh` inspects the actual `tool_input.command` of every Bash
  call, it correctly blocked that reproduction command (exit 2, "BLOCKED: git reset --hard
  discards..."). This is the exact defect this task fixes, encountered live rather than only in
  the suite. Worked around by writing the reproduction to a script file
  (`/tmp/.../scratchpad/repro.sh`) and invoking it via `bash repro.sh`, so the trigger text lives
  in file content rather than in the literal Bash tool command string.

## What NOT to Try

- Do not use ordinary-prose message-text fixtures (no `;`/`&`/`|` immediately before the
  destructive phrase) for detectors 3-7 — they do not reproduce the defect given the current
  anchor and will silently pass as false "evidence".
