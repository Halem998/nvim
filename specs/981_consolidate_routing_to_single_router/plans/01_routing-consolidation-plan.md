## Overview

Six independent routing implementations currently coexist in `agent-system/extensions/core/`:
the canonical `command-route-skill.sh`, hand-rolled inline copies in `research.md` and `plan.md`,
two divergent agent-routing blocks in `skill-orchestrate` and `skill-orchestrate-hard`, and the
vestigial `skill-orchestrator`. This plan collapses them onto one shared routing library, adds
explicit agent-routing declarations to extension manifests so agent names are never derived by
string surgery, fixes the `effort_flag` argument omission at the one existing canonical call
site, and adds a wiring-validation gate plus a table-driven parity test so the defect class
cannot silently recur. Done means: one ladder implementation, one precedence rule, every routed
`(op, task_type)` pair resolving to an agent file that exists on disk, and both orchestrate
engines producing identical decisions by construction.

**All edits target `agent-system/extensions/**` (the source store). No file under `.claude/**` is
hand-authored by this plan** — `.claude/` is a disposable deploy artifact regenerated by the
loader. Verification steps that read `.claude/` do so only after a deploy, and only to confirm
propagation.

`parse-command-args.sh` and does export it. Phase 2 must therefore materialize the prose-parsed
value into a shell variable immediately before the `source` call, and must render the "no flag"
case as an empty string rather than the literal `null`.

## Goals & Non-Goals

**Goals**:

- One shared routing ladder implementation, sourced by every routing consumer.
- Explicit agent-name declarations on manifests (`routing_agents`, `routing_agents_hard`);
  zero derivation of agent names from skill names.
- `--hard` resolves the hard skill via the manifest mechanism for all three of `/research`,
  `/plan`, `/implement`.
- One documented precedence rule (first-match-wins, non-core before core) applied identically by
  every consumer, including both orchestrate engines.
- Core-manifest identification keyed on `.name == "core"`; `routing_exempt` retained with its
  exemption semantics only.
- `skill-orchestrator` deleted, its one consumer folded onto the canonical path, its two
  referencing guides corrected.
- A wiring-validation gate that fails when any routed `(op, task_type)` pair resolves to a
  non-existent agent, and a table-driven test asserting both orchestrate engines agree.

**Non-Goals**:

- Redesigning the manifest format beyond adding the two `routing_agents*` blocks.
- Changing which skill or agent any existing `(op, task_type)` pair resolves to, except where
  today's resolution is demonstrably broken (a non-existent agent, or a hard skill that never
  resolves). Behavior preservation is the default; every intentional change is called out in the
  phase that makes it.
- Touching `.claude/**` by hand, or running a deploy as part of a phase's own verification
  (deploy is the user's action; phases verify against the source store and, where a deployed
  copy is required to run a script, note it explicitly).
- Retiring `routing_exempt` itself.
- Creating or modifying `specs/ROADMAP.md`.

## Rollback/Contingency

Every phase is a self-contained commit against the source store, and `.claude/` is regenerated
rather than edited, so reverting is `git revert` of the phase commits plus a redeploy — no
deployed-state surgery is required.

Per-phase contingencies:

- **Phase 1 baseline diff is non-zero**: stop and reconcile before proceeding. A behavior change
  in the router blocks every downstream phase; do not paper over it in a later phase.
- **Phase 2 breaks a command**: revert that command file only. The three call sites are
  independent, and `implement.md`'s one-argument fix is separable from the two rewrites.
- **Phase 3 manifest edits break the extension loader**: manifests are pure data additions; revert
  the offending manifest. A single bad manifest does not block the others.
- **Phase 4 orchestrate regression**: both Stage 1b blocks are replaced wholesale, so reverting
  restores the (broken but known) prior behavior; the Phase 6 test is the detector.
- **Phase 5/6 gate or test proves too strict**: soften the specific check, never remove the gate.
  Report the softening explicitly rather than deleting the assertion.
- **Phase 7 breaks `/epi`**: restore `skills/skill-orchestrator/` from git and revert `epi.md`;
  the deletion is the last step of that phase precisely so the consumer fix can be validated
  first.
