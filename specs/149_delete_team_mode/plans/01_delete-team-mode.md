### Research Integration

The research report supplies a complete per-file site table that this plan sequences rather than
re-derives. Four findings drive the phase structure:

1. **The forks are not line-deletes.** Each of the five `team_mode` forks in Stage 4 is an
   `if [ "${team_mode:-false}" = "true" ]; then` ... `else` ... shape where the `else` branch
   holds the real single-agent dispatch. Deleting a fork means promoting the `else` body to the
   unconditional path. This is the highest-risk edit class and gets its own first phase.
2. **`synthesis-agent` has exactly one caller**, and it lives entirely inside the Stage 3.6a
   block. The task's MUST NOT ("do not remove `synthesis-agent` while a live caller exists") is
   therefore satisfied only *after* the SKILL.md block is gone -- hence the explicit dependency
   of the deletion phase on the SKILL.md phase, plus a re-grep gate inside it.
3. **No team-mode contract test file exists** under `scripts/tests/` (49 files surveyed, zero
   hits). WORK item 6's "delete, do not skip" instruction is N/A; the implementer must record
   this as verified-absent rather than invent a deletion.
4. **A documented false-positive class exists** (`general-implementation-agent.md`'s own
   `### Stage 3.6: Observation Duty`, `handoff-artifact.md`/`progress-file.md` generic
   "teammate" vocabulary, `founder`-extension `team_size` headcount metrics, `.opencode/**` and
   `.memory/**`). No bulk find/replace may run; every edit is site-targeted against the report's
   table.

## Rollback/Contingency

Every phase is its own commit (Phases 3 and 4 are single atomic commits by declaration), so
rollback is `git revert` of the offending phase commit followed by a redeploy. The two
highest-risk reversions:

- **Phase 1 (fork promotion) breaks Stage 4 control flow**: revert the phase commit, redeploy,
  and re-attempt one fork at a time with a separate commit per fork, verifying the surrounding
  handler reads correctly after each.
- **Phase 3 (shared parser) breaks any command**: revert that single atomic commit; every other
  phase is independent of it and stays landed, since Phases 1 and 2 already removed all readers
  of the `TEAM_*` exports (a parser that still exports them is inert, not broken).

If the deploy in Phase 7 produces an inconsistent `.claude/**`, redeploy from a clean checkout of
the source store rather than hand-repairing the deploy tree. Because seven dependent tasks run
after this one through the same orchestrator, a failed Phase 1 or Phase 7 must be fully reverted
and redeployed before the batch continues -- do not leave a partially-excised `skill-orchestrate`
deployed.
