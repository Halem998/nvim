## Executive Summary

- **The critical research question is answered with high confidence, and the answer is NO**: `@path` references inside agent definition **body** text do not auto-resolve when Claude Code spawns a subagent. This is proven two ways — (1) direct empirical evidence from this very session (my own agent-definition file's `@.claude/context/formats/return-metadata-file.md` bullet arrived in my system prompt as literal unexpanded text; I had to `Read` it myself to get its content), and (2) the official subagent docs state the subagent "receives only this system prompt plus basic environment details... not the full Claude Code system prompt" — no import-expansion step is described for subagent body content anywhere in the frontmatter/body spec. `@path` auto-import IS real, but only for CLAUDE.md/memory files — a completely different code path. **Consequence: the "shared @-imported include" strategy for items 1 and 5, if it means silent automatic injection, is unfounded.** The correct fallback is generated-copy-with-lint, using this repo's own CLAUDE.md-generation-from-merge-sources as the precedent (see Findings §1).
- **Item 2's load-bearing unknown is now resolved via official Claude Code docs, not assumption**: the real, documented subagent-frontmatter fields are `tools:` (allowlist, comma-separated string) and `disallowedTools:` (denylist, camelCase) and `mcpServers:` (camelCase). `allowed-tools:` and `mcp-servers:` (hyphenated) are **not** subagent fields at all — `allowed-tools` is the SKILL.md/slash-command field, a different artifact type. This means `synthesis-agent.md` and `literature-agent.md` are silently running with **unrestricted inherited tool access** today (their intended Read/Write-only restriction is a no-op), and the 5 founder/present agents' `mcp-servers:` declarations are silently ignored (their MCP servers never connect). These are correctness bugs, not just style drift — see Findings §2.
- Frontmatter `model:` gap is real for exactly **15 agents** (7 filetypes + 8 founder), matching the review's count. Two additional files that superficially "lack model" (`lean/context/project/lean4/agents/lean-*-flow.md`) are **not dispatchable agents** — they are `@`-loaded reference docs that happen to sit in a directory named `agents/`. Any new lint globbing `**/agents/*.md` must exclude these by content (no frontmatter, no `name:`) not just note them as a gap — see Findings §3.
- Body-skeleton drift is real but the review undercounted it in one direction and overcounted in another: **9 of 11** core agents (not all 11) lack `## Agent Metadata`/`## Allowed Tools` — `code-reviewer-agent.md` and `meta-builder-agent.md` already have both. Conversely, **13 agents** lack `## Error Handling` (not 6) — see Findings §4 for the full list and one near-miss (`latex-implementation-agent.md` has `## Common Errors and Fixes` instead, a naming variant worth folding into the standard rather than treating as absent).
- Two competing agent templates (`docs/templates/agent-template.md`, `context/templates/agent-template.md`) are confirmed **not** folded by any prior docs-truth-sweep work — they remain deliberately distinct (tutorial vs. machine-consumed-by-meta-builder-agent reference), and each already cross-references the other. Neither matches the actual skeleton used by the two most-hardened live agents (`general-research-agent.md`, `cslib-research-agent.md`). Recommend treating `context/templates/agent-template.md` as canonical-for-linting and reconciling section names/order with the two live reference agents, not merging the two template files into one — see Findings §5.
- Terminal-metadata contract audit: of 77 agents, **8** already carry the hardened Stage-7-style section (bare-string-array warning + status vocabulary), **62** mention `.return-meta.json` in some form (partial coverage, unaudited for correctness), and **13** have zero mention at all. Of those 13, at least three (`code-reviewer-agent.md`, `synthesis-agent.md`, arguably `meta-builder-agent.md`) may be legitimately using a different, non-task-lifecycle return contract (`/review`, team-synthesis, interactive task creation) rather than a gap — this needs a per-agent classification pass, not a blanket "add the section" sweep. See Findings §6.
- **Recommend splitting this task.** Item 4 (skeleton drift + lint) and item 5 (terminal-metadata audit + lint) are each independently large (13 + 13 + 62-to-audit files respectively, plus new lint logic) and have different risk profiles than items 1-3 (mechanical, scriptable, low-judgment). See Recommended Phasing / Splitting below.

## Findings

### 1. The `@`-import critical research question (resolved empirically + via docs)

**Empirical evidence from this session**: this agent's own "Custom Agent Instructions" system-prompt block is the literal, unexpanded markdown body of `general-research-agent.md`. It contains, verbatim and unexpanded:
```
## Context References

- `@.claude/context/formats/return-metadata-file.md` - Metadata file schema (always load)
- `@.claude/context/formats/report-format.md` - Research report structure (when creating report)
...
```
No content from `return-metadata-file.md` was present anywhere else in the system prompt until this agent explicitly called `Read` on it. This is direct, first-party proof that `@path` references embedded in an agent definition's body are **not** resolved/expanded by the Agent-tool spawn mechanism — they are inert pointer text that the agent itself must act on with an explicit tool call.

**Documentary corroboration**: the official Claude Code subagent docs (code.claude.com/docs/en/sub-agents, fetched live) state: "The frontmatter defines the subagent's metadata and configuration. The body becomes the system prompt that guides the subagent's behavior. Subagents receive only this system prompt plus basic environment details like the working directory, not the full Claude Code system prompt." No import/expansion step for subagent body content is documented anywhere in the frontmatter-fields table or body-handling section. By contrast, `@path` **is** a real, documented, auto-resolving mechanism — but only for CLAUDE.md / the memory hierarchy (project/user/enterprise memory files), a completely separate code path with its own approval-dialog and max-depth-4 recursion behavior. The two mechanisms share syntax but not behavior; conflating them is the exact mistake items 1 and 5 risk making.

**Source-store vs. deployed tree**: this distinction turns out to be moot for the auto-resolution question (resolution doesn't happen automatically in either tree), but it matters for a different, related reason: an agent file authored in the source store (`agent-system/extensions/core/agents/...`) must still write its `@`-pointer text using the **deployed** path (`@.claude/context/...`), because `agent-system/extensions/**` never exists in the runtime working directory an agent actually operates in — only `.claude/**` does. This is already the existing, correct convention (confirmed: `cslib-research-agent.md`'s source-store copy already writes `@.claude/context/formats/return-metadata-file.md`, not an `agent-system/...` path). Any new shared-include mechanism must preserve this.

**Existing precedent for what actually works**: `lint-contract-compliance.sh`'s Check A already validates hard-agent contract references by `grep -qF "@.claude/context/contracts/anti-analysis.md"` against the agent file — i.e., the codebase's own lint infrastructure already treats a `@`-reference as **a textual pointer whose presence is checked**, not as something that auto-expands. This is consistent with the finding above and gives a ready-made pattern: presence-of-pointer-text is lintable; content-auto-inclusion is not.

**Recommendation for the planner**: for item 1 (no-task-references bullet) and item 5 (terminal-metadata section), do not rely on `@`-import auto-expansion. Two viable alternatives, not mutually exclusive:
1. **Generated-copy-with-lint** (recommended for item 1, the short MUST-NOT bullet): keep the canonical bullet text in exactly one shared fragment file, and either (a) have a small script splice it into each target agent's `## Critical Requirements` section at a marked insertion point (checked into the source store, run like `generate-context-line-counts.sh` is), or (b) accept literal duplication of a **one-line** bullet across ~73 files, kept in sync by a lint that diffs each agent's bullet text against the canonical source. This repo already has a working precedent for build-time content generation distinct from runtime `@`-import: `.claude/CLAUDE.md`'s own header states "This file is generated automatically from loaded extensions. Do not edit directly," driven by the `merge-sources/` mechanism. That is the right model to point to, not `@`-import.
2. **Read-directive pattern** (viable but weaker, not recommended for MUST-NOT prohibitions): instruct the agent to `Read` a shared file at a fixed stage. This preserves single-source-of-truth for prose but costs an extra tool call every dispatch and is less robust for a default-behavior prohibition (an agent under context pressure is more likely to skip an optional-sounding "read this" instruction than to violate a bullet already sitting in its active Critical Requirements list). This is closer to what item 5's terminal-metadata section already does informally today (agents reference `return-metadata-file.md` for the *full* schema while carrying a short worked example inline) — appropriate for a large reference doc, not for a one-line prohibition.

For item 5 specifically: the terminal-metadata section is not pure shared literal text anyway — it needs per-agent specifics (status value `researched` vs. `implemented`, the agent's own name in `delegation_path`, its report vs. implementation artifact type). The right unit to standardize is a **worked template with required elements**, not a byte-identical shared string — see Findings §6's recommendation for a presence-and-shape lint rather than a text-diff lint.

### 2. Frontmatter key normalization — RESOLVED (official docs, not assumption)

Live grep of all 77 agent files found four spellings in use:

| Spelling | Files | Status per official docs |
|---|---|---|
| `tools:` | `core/agents/spawn-agent.md` (YAML block-list form) | **Valid field name.** Documented example form is a comma-separated string (`tools: Read, Glob, Grep`), not a YAML list. `spawn-agent.md` uses `tools:\n  - Read\n  - Write\n  - Glob\n  - Grep\n  - Bash(jq:*)`. Recommend normalizing to the documented comma-string form to match the verified-working example exactly, since the docs never demonstrate the list form and its parsing is unconfirmed. |
| `allowed-tools:` | `core/agents/synthesis-agent.md`, `literature/agents/literature-agent.md` | **Invalid for subagent files.** `allowed-tools:` is the SKILL.md / slash-command frontmatter field, a different Claude Code artifact type. Not in the subagent supported-fields table at all. **Correctness bug**: these two agents are very likely running with full inherited tool access today, not the `Read, Write`-only restriction their frontmatter appears to declare. |
| `disallowedTools:` | `web/agents/web-research-agent.md`, `web/agents/web-implementation-agent.md` | **Valid and correctly spelled already.** camelCase, denylist semantics, matches docs exactly. No migration needed for these two; this is the field to standardize on. |
| `mcp-servers:` | `founder/agents/financial-analysis-agent.md`, `founder/agents/market-agent.md`, `founder/agents/analyze-agent.md`, `founder/agents/founder-spreadsheet-agent.md`, `present/agents/budget-agent.md` | **Invalid — wrong casing.** Correct field is `mcpServers:` (camelCase). **Correctness bug**: these 5 agents' declared MCP server access (e.g., `market-agent.md`'s `sec-edgar` entry) is silently ignored; the servers never connect for these subagents today. |

Full documented subagent frontmatter field set (for the standard doc update): `name`, `description` (required); `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `effort`, `isolation`, `color`, `initialPrompt` (all optional). This repo's `agent-frontmatter-standard.md` currently documents only `name`/`description`/`model` as the complete field set and doesn't mention `tools`/`disallowedTools`/`mcpServers` at all (nor prohibit the invalid `allowed-tools`/`mcp-servers` spellings) — that's the actual standard-doc gap, distinct from and prerequisite to fixing the 7 files above.

**Recommendation**: (a) update `agent-frontmatter-standard.md` to document `tools`, `disallowedTools`, `mcpServers` with their real semantics and explicitly list `allowed-tools`/`mcp-servers` as invalid-for-agents (valid only in SKILL.md); (b) migrate `synthesis-agent.md` and `literature-agent.md` from `allowed-tools:` to `tools:` (same intended value, correct key); (c) migrate the 5 founder/present agents from `mcp-servers:` to `mcpServers:` (same intended value, correct key); (d) normalize `spawn-agent.md`'s `tools:` to comma-string form as a low-risk clarity fix. (b) and (c) are the highest-value fixes in this whole item — they silently restore intended behavior, not just satisfy a lint.

### 5. Lint script landscape (for the "extend which lint" decision)

- `lint-contract-compliance.sh` is narrowly scoped to **hard-mode** agents/skills/contracts only (6 checks, A-F) — it's the right shape of script to extend (existing `grep -qF "@..."` presence-check pattern, existing pass/fail/warn accounting) but currently has zero awareness of the base (non-hard) 77-agent population, frontmatter keys, or section skeletons.
- `check-extension-docs.sh` is a much broader, already-large doc-lint (manifest completeness, dangling `@.claude/context/contracts/` references project-wide, deploy-drift, orphan detection, index-entries schema, line-count truth) with an existing pattern for "dangling reference" and "deployed-file-has-no-source" checks that item 4's new frontmatter/section/terminal-metadata checks would fit alongside conceptually, but it's already very large (the header comment alone lists ~12 distinct check categories) — adding 3 more substantial check families (frontmatter-key validity, required-section presence, terminal-metadata section presence) risks making an already-sprawling script harder to reason about.
- **Recommendation**: don't force a single choice between the two. Add the new "Tier 1 static agent-contract checks" (frontmatter key validity, required sections, terminal-metadata presence) as a **new, narrowly-scoped script** (e.g., `lint-agent-contracts.sh`) modeled directly on `lint-contract-compliance.sh`'s existing pass/fail/warn/log helper functions and Check-lettering convention, rather than bolting onto either existing file. Register it the same way `test-handoff-reader-parity.sh` was registered in `core/manifest.json` (task 982's Phase 6 precedent) and wire it into `scripts/verify-deploy.sh` the way `check-task-references.sh` is wired in as "gate 4" per `no-task-references-in-deliverables.md`'s Enforcement section. This keeps the new checks independently testable (with the rogue-key and missing-terminal-metadata fixtures the verification bar calls for) without growing either existing file past its current scope.

The filetypes agents (7 of the 13) and `literature-agent.md`/`slide-planner-agent.md` look like real gaps at first read (they are domain research/implementation workers) but deserve the same one-line classification check before editing.

## Decisions

- Treat the `@`-import shared-include strategy in items 1 and 5 as **unfounded for automatic injection**; use generated-copy-with-lint (item 1) and a presence/shape lint against a worked template (item 5) instead. This is the single most consequential decision this report makes, since it invalidates the premise the task description asked to verify empirically.
- Treat item 2's field-spelling question as **resolved**, not requiring further empirical probing at implementation time — the official docs are authoritative and current (fetched live this session).
- Recommend a **new, narrowly-scoped lint script** rather than extending either existing lint file, to keep the new checks independently testable and avoid further bloating `check-extension-docs.sh`.
- Recommend **not** merging the two agent-template files; reconcile their content against the two live reference agents instead.

## Risks & Mitigations

- **Risk**: treating the review's "6 agents lack Error Handling" / "all 11 core agents lack skeleton sections" counts as ground truth would under-scope the plan. **Mitigation**: this report's corrected counts (13 and 9-of-11 respectively) are already re-verified by direct grep; use these, not the review's numbers, for phase sizing.
- **Risk**: a mechanical "add the terminal-metadata section to all 13 zero-mention agents" pass could incorrectly force a task-lifecycle contract onto `code-reviewer-agent.md`/`synthesis-agent.md`, which have their own legitimate, different return contracts. **Mitigation**: require an explicit one-line classification note per agent in the plan/implementation before editing any of the 13.
- **Risk**: migrating `synthesis-agent.md`/`literature-agent.md` from `allowed-tools:` to `tools:`, and the 5 founder/present agents from `mcp-servers:` to `mcpServers:`, changes *actual runtime tool/MCP access* (not just cosmetic frontmatter) — these agents may currently be relying on the broader inherited-tool-access their invalid key accidentally grants. **Mitigation**: flag this explicitly in the implementation plan as a behavior change requiring a quick sanity check (e.g., confirm `synthesis-agent.md`'s intended Read/Write-only scope doesn't break its actual usage in `skill-team-research`) rather than a pure lint-satisfying rename.
- **Risk**: renaming/moving the two lean4 flow files (Findings §3 option b) touches live `@`-reference call sites in `lean-research-agent.md`/`lean-implementation-agent.md` — low risk but real coordination surface. **Mitigation**: prefer option (a) (frontmatter-gated lint) as the required fix; treat the rename as optional cleanup, not a hard requirement.

## Recommended Phasing / Splitting

Given the "flag anything that should be a separate task" instruction, here is the sizing breakdown a planner should work from:

1. **Item 2 + item 3 (frontmatter fixes)** — small, mechanical, low-judgment: 7 key-spelling migrations (2 `allowed-tools:`→`tools:`, 5 `mcp-servers:`→`mcpServers:`, 1 `tools:` normalization) + 15 `model: sonnet` additions + 1 standard-doc rewrite (`agent-frontmatter-standard.md` to document the real field set). Good single phase, maybe two (standard doc first, then the 22 file edits it licenses).
2. **Item 1 (no-task-references bullet, ~73 agents)** — mechanical once the generated-copy-with-lint mechanism (Findings §1) is designed; the design work itself (where the shared fragment lives, how splicing/lint works) is the real cost, not the 73 edits. One phase for the mechanism + rule-file Enforcement-section update, one phase (or a scripted batch) for the rollout.
3. **Item 4 (skeleton drift + lint)** — candidate for a **separate task**: requires a real design decision (reconcile two templates against two live reference agents, decide the `## Common Errors and Fixes` vs `## Error Handling` naming question, build the new lint script, handle the lean4-flow-file glob-ambiguity fix) before touching any of the ~20 affected files (9 core Metadata/Tools retrofits + 13 Error Handling additions, with overlap).
