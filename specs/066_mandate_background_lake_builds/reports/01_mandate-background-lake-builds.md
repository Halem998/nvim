## Findings

### Codebase Patterns

**Guard script mechanics** (`agent-system/extensions/core/scripts/lake-build-guard.sh`, read in full):
- Three subcommands: `status` (exit 0/10, detect in-flight build via non-blocking `flock`, never via `pgrep`), `preflight` (exit 0/11, PSI + swap-in-use memory-pressure check), `build` (the wrapper).
- `build` mode: resolves the project root by walking up from `--dir` (default `$PWD`) to the nearest `lakefile.lean`/`lakefile.toml` (never `git rev-parse --show-toplevel` — a Lean package can be a subdirectory); acquires an `flock` on `<root>/.lake/build-guard.lock`; on contention, waits up to `--timeout` (default 600s) then exits 75; on acquiring the lock (immediately or after waiting) checks a 4-condition staleness policy (`state=complete`, fingerprint match, age < 900s, `--no-share` not passed) and, if all pass, **replays** the prior holder's captured stdout/stderr/exit code instead of rebuilding; otherwise runs `"$LAKE_BIN" "$@"` in the foreground *inside the guard process*, tee-ing output to capture files.
- Exit codes: 0/lake's own code on success; 75 lock-wait timeout; 76 deferred on memory pressure (`--defer-on-pressure`); 77 usage error; 78 no Lean project found; 79 missing capability (e.g. no `flock`/`lake` on PATH).
- `--memory-bound` opt-in wraps the build in `systemd-run --user --scope` with `MemoryHigh=60%`/`MemoryMax=80%` (degrades to unbounded with a stderr notice if `systemd-run` lacks user-scope cgroup delegation).
- **Recorded dead ends baked into the script's own header** (must not be contradicted by anchor text): Lake 5.0.0 has no `-j`/`--jobs` flag; Lake does not forward Lean's own `-j`/`--threads`; `LEAN_NUM_THREADS` was experimentally falsified as a concurrency lever (an A/B held module graph constant, varied only that env var, and max concurrent `lean` descendant processes was 1 in both arms — it sizes one process's *internal* thread pool, not Lake's scheduler).
- The guard is silent on the no-conflict path in every mode (composes safely inside `$(...)`), and is explicitly documented as adding **no call-site wiring** — callers must opt in by invoking `lake-build-guard.sh build ...` themselves. That opt-in is exactly this task's contract-text job.

Prose-and-table style, not terse. The task's own "~40 lines" estimate for the new anchor is almost certainly too low given the required content (cap explanation, caching mechanism, the run_in_background mandate, the guard mandate, 4 passive checks with a caveat, and the cross-reference note) — the sibling anchor is 96 lines for a narrower topic. Recommend the planner budget closer to 90-130 lines and treat "~40" as a stale estimate, not a hard ceiling (the task text itself flagged this exact miscalibration already happened once for `rules/lean4.md`, whose actual required edit is "more than one line" against a "one-line pointer" estimate).

### Recommendations

1. **Anchor content** (`operations/long-builds.md`, target ~90-130 lines, `multi-instance-optimization.md`-style structure): Overview -> the 10-minute foreground cap (Bash tool's max explicit `timeout` is 600000ms; the *default* is 120000ms, but the operative constraint agents hit is the harness's hard cap on a plain foreground call) -> Lean's per-module `.olean` caching and why a cap-killed build caches nothing (livelock, not slowdown) -> the normative statement "any single module may exceed the foreground cap" with the ~11-minute figure demoted to an illustrative footnote only -> the docstring-edit-is-ordinary-not-exotic point (whole-file hashing invalidates downstream `.olean`s on any edit, including comment-only) -> the run_in_background mechanism (detached, survives turns, harness-notified) -> the build-guard mandate and *why both must land together* (uncapping without serialization makes the measured ~10-concurrent-duplicate-build/29.9GB-RSS/swap-thrash scenario from the addendum strictly worse) -> the four passive progress checks -> the liveness-vs-termination caveat -> a short cross-reference paragraph to `multi-instance-optimization.md` (state the detachment-amplifies-concurrency point in writing here since this task owns this file, and flag in the report — done below — that the sibling anchor should grow a reciprocal pointer as coordination, without editing it here).

2. **Four passive progress checks** to document (content confirmed available to an agent without disturbing a running build):
   - Fresh `.olean` files by mtime under the project's `.lake/build/` tree — a moving mtime frontier is progress.
   - The live `lean` worker PID's `/proc/PID/cmdline` — shows which module is currently being elaborated.
   - Accumulated CPU time via `ps -o times=` (or reading `/proc/PID/stat` fields 14/15, utime/stime) — the tiebreaker specifically for the case where the `.olean` list looks frozen because the build is still inside one very long module; rising CPU time still indicates the process is working, not hung.
   - `VmRSS` trend from `/proc/PID/status` — both a progress signal and an OOM early-warning (pairs naturally with the guard's own PSI/swap preflight check).
   - **Caveat to state explicitly, verbatim in spirit**: these four signals prove *liveness* (the process is doing something), never *termination* (that it will finish, or finish correctly) — a process consuming CPU and growing RSS can still be stuck in a genuinely divergent tactic search. Note these are for interim troubleshooting/observability (by a human, or by an agent choosing to peek via Monitor/Bash mid-wait), not a required substitute for the harness's own completion notification, which remains the actual termination signal the contract sites should wait on.

3. **Guard invocation shape** for the contract sites (illustrative, not final plan text): `Bash(run_in_background: true)` running `bash .claude/scripts/lake-build-guard.sh build --timeout 1800 -- <lake args>` (module name after `--` for scoped builds, no trailing args for full). Recommend the contract prose fix `--timeout` explicitly at a value comfortably above the measured single-module figure (e.g. 1800s/30min) rather than relying on the guard's 600s default, since a second session's lock-wait could otherwise itself time out (exit 75) waiting on a first session's legitimately-long build — this would reintroduce a livelock-adjacent failure just one layer up the stack. This is a genuine new finding, not stated in the task description, and should be called out to the planner as a concrete parameter choice rather than left implicit.

4. **Scoped-build decision (open item flagged by the task)**: recommend resolving in favor of the task's own suggested direction — extend the mandate to cover *any* `lake build` invocation, scoped or full, since (a) the measured single-module time already exceeds the cap on its own, so "scoped = safe" is false, and (b) the guard's lock is project-granular regardless of whether the invocation is scoped, so there is no *safety* reason left to special-case scoped builds. Record explicitly, as a named tradeoff in the anchor, that this means phase-end scoped builds from concurrent sessions on the *same* package now serialize against each other project-wide (previously they could run in true parallel if targeting different modules) — this is the direct cost of closing the memory-pressure gap from the scope addendum, not a hidden regression. `rules/lean4.md`'s "Prefer scoped (faster)" framing and MUST DO item 7's "(scoped, faster)" parenthetical should be revised to drop the implication that scoped exempts a build from the cap/serialization discussion — scoped remains preferred for doing *less work*, not for being categorically safe.

5. **`skill-lake-repair/SKILL.md` resolution**: adopt the addendum's Option (c) — leave the repair loop's two command-substitution sites (L69, L71) synchronous (command substitution is incompatible with `run_in_background`, which is why the base agent's mandate cannot mechanically apply here), but rewrite each to call through the guard: `build_output=$(bash .claude/scripts/lake-build-guard.sh build --timeout 1800 -- "$module" 2>&1)` and the unscoped twin. This resolves the addendum's stated goal (serialization + memory bounding) while explicitly carving the loop **out of the detachment mandate only**. Add a short inline comment/note at the top of "Step 4: Run Build" documenting the residual foreground-cap exposure (this loop can still be killed mid-build at the cap on a heavy first-time build; unlike the detached agents, a killed iteration here is not silently invisible — it surfaces as a failed `lake build` command substitution the loop's own error handling already has to deal with) so the carve-out is recorded rather than silently left as-is, satisfying the acceptance criterion.

6. **Twin-file discipline for the new MUST NOT item**: the base agent gets a new MUST NOT item (per task text, verbatim in intent: prohibiting a foreground `lake build`). The hard-agent twin's MUST NOT list (L520-533, 12 existing items) currently has no equivalent — add a matching new item there too, located by content near the existing build-related items (7 "Run full lake build before returning implemented status" at L515 is the nearest MUST DO anchor point), consistent with the Acceptance criterion "the -hard twin carries equivalent changes located by content."

7. **Residual out-of-scope gap to flag in the anchor's caveats, not fix**: `mcp__lean-lsp__lean_build` (present in `lean-implementation-agent.md`'s Allowed Tools list, "SLOW - use sparingly", and in both research agents' tool lists) is a *second* code path that also runs `lake build` internally but is invoked as an MCP tool call, not a Bash command — `run_in_background` does not apply to it, and its own timeout behavior (if any) is outside this task's visibility. The task's own DELIVERABLE 2 site list does not include these `lean_build` MCP tool-list lines, so this is confirmed out of scope for edits, but the anchor should note the gap so a future reader does not assume `lean_build` is covered by this mandate.

## Decisions

- **Anchor length**: recommend ~90-130 lines against the task's own "~40" estimate, matching the sibling anchor's actual size for comparable scope; flag the original estimate as stale rather than binding.
- **Scoped-build safety framing**: recommend dropping "scoped = exempt from the cap/mandate" framing extension-wide (agents + rules/lean4.md); scoped remains preferred for doing less work, not for being categorically safe.
- **`skill-lake-repair` carve-out**: recommend Option (c) (guard-routed, still synchronous, detachment mandate does not apply, residual cap exposure documented inline) over Options (a)/(b) from the original task text.
- **Guard `--timeout`**: recommend the contract sites pass an explicit value well above the measured single-module duration (e.g. 1800s) rather than the guard's 600s default, to avoid a second waiter timing out on a legitimately-long first build.
- **`lean_build` MCP tool**: recommend documenting as a known, deliberately out-of-scope residual gap in the anchor rather than silently leaving it unmentioned.

## Risks & Mitigations

- **Risk**: mandating the guard for scoped phase-end builds serializes previously-parallel work across concurrent sessions on the same package. **Mitigation**: document this tradeoff explicitly in the anchor as a deliberate, recorded cost (per the addendum's own memory-pressure evidence), not an unintended regression.
- **Risk**: guard's default 600s lock-wait timeout could itself time out a waiting session on a legitimately long (>10 min) first build, reintroducing a livelock-adjacent failure one layer up. **Mitigation**: contract sites pass an explicit, generous `--timeout`.
- **Risk**: `skill-lake-repair`'s carve-out could be read later as "this file was simply missed" rather than a deliberate decision. **Mitigation**: inline comment documenting the choice and reason, per Acceptance criteria.
- **Risk**: twin-file drift on the new MUST NOT item (a known recurring defect class per the task text). **Mitigation**: locate by content in both files, not by mirrored line number; verify both edits together before considering the pass done.
- **Risk**: `lean_build` MCP tool remains a silent second path with unaddressed cap exposure. **Mitigation**: name it explicitly as an out-of-scope caveat in the anchor so it is not mistaken for "covered."
