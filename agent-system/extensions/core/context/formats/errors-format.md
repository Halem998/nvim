# Errors Store Format

## Overview

`specs/errors.json` is the persistent error-tracking store for the agent system. It records
individual errors encountered during command execution -- delegation hangs, timeouts, validation
failures, git/build failures, jq parse errors, and more -- so `/errors` can analyze patterns and
so downstream tooling (`orchestrator-postflight.sh`, `hooks/events-log-artifact.sh`) can cross-link
an event to the error that produced it.

This document specifies the document and record shape. The formal machine-checkable contract
lives in `context/schemas/errors-schema.json` (draft-07 JSON Schema); the two must stay in sync.

## File Location

```
specs/errors.json
```

Repo-root-relative, sibling to `specs/events.jsonl`, `specs/state.json`, and `specs/TODO.md`.

## Lazy Creation and Never-Gitignored

- The file is **not** pre-created in general. It comes into existence the first time
  `scripts/errors-append.sh append` is invoked in a given repo, creating it with `{"errors": []}`.
  (This repo additionally bootstraps it eagerly, so `/errors` has something schema-valid to read
  immediately without waiting for the first real error.)
- Once created, it is a normal tracked file and is **never gitignored**.
- Both `append` and `update` tolerate the file's various states: `append` creates it lazily if
  absent; `update` never creates it -- it fails loudly if `specs/errors.json` does not already
  exist, since there is nothing to update.

## Why Object-with-Array, Not a Bare Array

The top level of the document is `{"errors": [...]}`, an object holding the array -- never a bare
top-level array. This is a deliberate reconciliation decision, not an arbitrary choice:

- **Both live readers already assume this shape.** `orchestrator-postflight.sh`'s `error_ref`
  cross-link query reads `.errors[]? | select(...)`, and `hooks/events-log-artifact.sh` reads
  `.errors[-1].context.session_id` / `.errors[-1].id` / etc. Adopting object-with-array costs zero
  reader changes.
- **It admits future top-level metadata** (e.g. `schema_version`) without a breaking shape change
  later -- a bare array has no room for anything but records.
- A bare-array `specs/errors.json` has been observed live in at least one sibling repo. That is
  the drift this schema corrects, not a precedent to follow. The `fix_status` enum's deprecated
  `resolved` value exists precisely so that such already-written data stays schema-valid on read
  without requiring a cross-repo migration.

## Mutability Contrast with `events.jsonl`

`specs/events.jsonl` is strictly append-only: lines are never rewritten in place, only added.
`specs/errors.json` is different -- **error records are living state, mutated in place** as a fix
progresses: `fix_status` transitions `unfixed -> in_progress -> fixed`, and `fixed_date` /
`fix_task` are added once a fix lands. This is why `errors-append.sh` has two subcommands instead
of one: `append` (a near-direct port of `events-append.sh`'s validated, `flock`'d,
`jq -c -n`-built shape) and `update` (an original read-modify-write design, holding one `flock`
across the entire read -> transform -> temp-write -> validate -> atomic-`mv` sequence, validating
the MERGED document rather than the delta before the `mv`).

## The `errors-append.sh` CLI Contract

### `append` -- create a new error record

```
errors-append.sh append --type TYPE --severity SEVERITY --message "..." \
  [--session SESSION_ID] [--command CMD] [--task N] [--phase N] [--checkpoint NAME] \
  [--agent NAME] [--file PATH] \
  [--delegation-path-json '["a","b"]'] [--failed-at-depth N] \
  [--suggested-action "..."] [--auto-recoverable true|false]
```

- Required: `--type`, `--severity`, `--message`.
- Optional context flags populate `context.{session_id,command,task,phase,checkpoint,agent,file}`
  -- only the supplied keys are emitted; `context` is always present but may be `{}`.
- Optional trajectory flags (`--delegation-path-json`, `--failed-at-depth`) populate an optional
  `trajectory` object; omitted entirely (not emitted as `{}`) when neither flag is supplied.
- Optional recovery flags (`--suggested-action`, `--auto-recoverable`) populate an optional
  `recovery` object; omitted entirely when neither flag is supplied.
- `id` and `timestamp` are always generated by the script (`err_{timestamp_ms}_{random6}`, ISO
  8601 UTC) -- there is no `--id` or `--timestamp` flag for `append`.
- `fix_status` is always initialized to `unfixed`.
- Prints the new record's `id` to stdout on success (exit 0).

### `update` -- mutate an existing record's fix status

```
errors-append.sh update --id ERR_ID --fix-status STATUS \
  [--fixed-date ISO8601] [--fix-task N]
```

- Required: `--id`, `--fix-status`.
- `--fix-status` accepts `unfixed | in_progress | fixed` -- **not** `resolved`. `resolved` is
  schema-valid for reading (see below) but is REJECTED as an `update` input, with a message
  stating it is a deprecated synonym for `fixed`. This is what stops the deprecated value from
  re-propagating into new writes.
- `--fixed-date` defaults to the current time when `--fix-status fixed` is given and the flag is
  omitted.
- `--fix-task` is an optional bare integer identifying which fixing task's implementation
  resolved the error.
- Fails loudly (exit 1, file untouched) if `specs/errors.json` does not exist, if no record
  matches `--id`, or if the merged result would fail schema validation.
- Prints the updated record's `id` to stdout on success (exit 0).

Both subcommands are hand-validated in the `events-append.sh` idiom -- required-arg presence,
closed-enum `case` checks, integer regex checks, and `jq`-shape checks -- never a runtime
JSON-Schema-library call (`ajv`, `python3 -m jsonschema`). Nothing in `core/scripts/` uses one;
`errors-append.sh` follows the same idiom as `events-append.sh` for consistency, not a new
validation dependency.

## Reconciliation Decisions

This schema/format pair reconciles three previously inconsistent documented shapes
(`rules/error-handling.md`, two blocks in `commands/errors.md`, and the live inline writer in
`skills/skill-planner/SKILL.md`) into one. The key decisions:

- **`recurrence_count` is not a persisted field.** No writer has ever populated it. `/errors`'
  Analysis Mode computes recurrence at query time by grouping records on `type` -- it is derived,
  not stored. Keeping an unwritten schema field would just be a second dead-field defect of the
  exact kind this document exists to eliminate.
- **`resolved` is a deprecated-but-schema-valid synonym for `fixed`.** It exists in the `fix_status`
  enum only so already-written cross-repo data continues to validate on read. `errors-append.sh`
  never emits it, and `update` actively rejects it as an input value.
- **`context` is a union superset with no individually required sub-fields.** `session_id`,
  `command`, `task`, `phase`, `checkpoint`, `agent`, `file` are all optional -- no single writer
  populates all seven, and requiring any one of them would make the schema reject valid records
  from writers that never populated it.
- **`fixed_date` / `fix_task` are real, implemented fields**, not aspirational ones:
  `commands/errors.md`'s Fix Mode already specifies writing them; `errors-append.sh update` is the
  first implementing script for that documented behavior.

## Example Document

```json
{
  "errors": [
    {
      "id": "err_1736700000123_a1b2c3",
      "timestamp": "2026-07-15T10:22:31.123Z",
      "type": "jq_parse_failure",
      "severity": "medium",
      "message": "jq parse error in postflight artifact linking",
      "context": {
        "session_id": "sess_1736700000_abc123",
        "command": "/plan",
        "task": 259,
        "checkpoint": "GATE_OUT"
      },
      "recovery": {
        "suggested_action": "Use two-step jq pattern from jq-escaping-workarounds.md",
        "auto_recoverable": true
      },
      "fix_status": "unfixed"
    }
  ]
}
```

Running `errors-append.sh update --id err_1736700000123_a1b2c3 --fix-status fixed
--fix-task N` (naming the fixing task's number) transitions that record to:

```json
{
  "id": "err_1736700000123_a1b2c3",
  "...": "... unchanged fields ...",
  "fix_status": "fixed",
  "fixed_date": "2026-07-15T11:05:02.000Z",
  "fix_task": 260
}
```
